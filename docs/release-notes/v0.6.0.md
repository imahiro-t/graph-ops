## Highlights

- **HTTP custom data source.** A third storage backend, `dbBackend: "http"`, hands every one of graph-engine's 32 storage operations (tickets, nodes, edges, artifacts, projects, labels and the current project) to a plugin -- an HTTP server you run -- so GraphOps can keep its data in a system your team already uses. The CLI and the Web UI server both use it, and the engine, `process-ticket` and the Web UI work unchanged. Configure it with `httpDataSourceUrl` and `httpDataSourceToken` in `graph-config.json` (or `GRAPH_HTTP_DATASOURCE_URL` / `GRAPH_HTTP_DATASOURCE_TOKEN`), or in App Settings. The token accepts `${ENV_VAR}` references.
- **Published, versioned protocol.** The plugin interface is specified in `docs/http-datasource/openapi.yaml` (protocol version 1.0): endpoints, JSON schemas, the error format and how error codes map to GraphOps errors, partial-update semantics, atomicity, and timeouts. graph-engine checks the plugin's protocol version at startup and stops with a clear error when it is incompatible.
- **Jira Cloud sample plugin.** `examples/jira-datasource` is a standalone, standard-library-only Go plugin that stores tickets as Jira issues and shows each execution-graph node as a **sub-task** of its ticket, with the node's artifacts as comments and attachments on that sub-task. A node's status is shown as exactly one `graphops-status-*` label on its sub-task and, best effort, as its workflow status (configurable status names; a failed move is logged and never fails the write). A ticket holds up to 99 nodes and about 300 edges. It was verified end to end against a real Jira Cloud site with a 70-node graph.

## Changes

- **`graph-engine update-ticket`** changes a ticket's title, description and/or priority without touching its status: `update-ticket <ticketId> [--title <text>] [--description <text|->] [--priority <HIGH|MEDIUM|LOW>]`. Fields you don't pass stay as they are, and so do the status, `refined_at`, labels, assignee, `auto_executable` and `blocked`, so an `IN PROGRESS` ticket can be corrected without falling back to `REFINED` (which `refine-ticket` always does). `--description -` reads stdin byte for byte, like `create-ticket`. No field given, an empty title, a priority other than `HIGH`/`MEDIUM`/`LOW`, an unknown flag or an unknown ticket ID (`TICKET_NOT_FOUND`) is an error and changes nothing. It prints the updated ticket as JSON.
- **`graph-engine delete-ticket <ticketId> --yes`** deletes a ticket together with its nodes, edges, artifacts and label attachments -- the same scope as the Web UI's delete -- so a duplicated or mistaken ticket can be cleaned up without opening the Web UI. `--yes` is required; without it nothing is deleted and the command fails. It works from any status, including `IN PROGRESS`. An unknown ticket ID is an error (`TICKET_NOT_FOUND`) on every storage backend (SQLite, MySQL and HTTP). It prints `{"id":"<ticketId>","deleted":true}`.
- Both commands are listed in `graph-engine help`. As with every command, a `-h` or `--help` argument prints the help instead of running the command, so a title or flag value that is literally `-h` or `--help` cannot be passed (a description can still be given through stdin).
- CI and the release workflow now run on Node.js 24 with the Node 24 based versions of the GitHub Actions they use (`checkout`, `setup-node`, `setup-go`, `upload-artifact`, `download-artifact`), ahead of Node.js 20 being removed from GitHub's runners. Release builds now also skip the Go module cache, as they already did for npm, so a tag build never reads a cache saved by the default branch.

## Fixes

- `graph-engine create-ticket "<title>" -` now reads the description from stdin, like `refine-ticket` and `add-artifact` already did. Previously the `-` was silently saved as the ticket's description. Stdin is saved byte for byte, so long Markdown with quotes, `$` or backquotes can be passed through a quoted heredoc (`<<'EOF'`) without shell-escaping. Empty or whitespace-only stdin, or a failed read, is an error and no ticket is created. Passing the description as an argument works as before. The `create-ticket` skill now uses stdin for long descriptions.
- `graph-engine refine-ticket <id> -` with empty or whitespace-only stdin is now an error that changes nothing. Previously empty stdin left the description as it was but still set the status to `REFINED`, and whitespace-only stdin replaced the refined description with the blanks. `create-ticket` and `refine-ticket` now also reject a description argument that is only whitespace (e.g. `"   "`), with the same error wording; for `refine-ticket` the description, priority, labels, status and `refined_at` all stay as they were. An empty argument (`""`) works as before: `create-ticket` creates the ticket without a description and `refine-ticket` leaves the description unchanged. Non-empty stdin is still saved byte for byte.
- `$HOME/.graph-ops` is no longer read as both the user tier and the team tier. For a project under your home directory without its own `.graph-ops/`, every extension file used to be loaded twice (for example, the onboarding language block appeared twice in `get-skill-context` and `get-node-type-context`). Project-scoped settings for such a project now go to `<project>/.graph-ops/`; if the project *is* your home directory, the Web UI and settings API refuse project-scoped writes with `PROJECT_TEAM_ROOT_IS_USER_ROOT` instead of silently writing your personal settings.
- Windows: the generated launch script (`.ps1`) is written as UTF-8 with a BOM, so Windows PowerShell 5.1 no longer garbles Japanese prompts and working-directory paths on Japanese-locale systems. The macOS `.command` script is unchanged.
- Web UI: the settings modal now opens on the project currently selected in the header instead of the one (usually none) that was current when the page first loaded.
- Web UI: in the ticket list filters, selections that are not among the current options (for example an assignee that dropped out of the list during polling) are kept when another option is checked, and whitespace-only assignee names are treated as unassigned.
- Web UI (Japanese): the prompt placeholder now names the "送信" button that actually submits it, and the HTML artifacts tab is spelled HTML成果物 consistently.
- `graph-engine help` no longer points at a README section that does not exist.

## Security

- Plaintext `http://` is accepted only for loopback data sources (`localhost`, `127.0.0.0/8`, `::1`). A remote data source must use `https://` and a bearer token; otherwise graph-engine refuses to start.
- TLS certificates are always verified, redirects are never followed, and there is no fallback to plaintext.
- The Web UI never shows the saved token, and changing the endpoint URL requires the token to be entered again (like the MySQL password).
- Tokens are redacted from error messages coming back from the plugin.

## Accessibility

- The data source fields in App Settings have visible labels, mark invalid fields with `aria-invalid`, announce errors and the token re-entry prompt as status messages, and explain why saving is blocked.
- Ticket list filters: after the clear button disables itself, focus moves to the filter's trigger so Escape still closes the panel, and `aria-controls` is set only while the panel it names is actually present.

## Documentation

- New developer manual for custom data source authors: `docs/http-datasource/README.md` (configuration, security model, the protocol, local development and verification, and a walkthrough of the Jira sample).
- The Jira sample's README documents its storage mapping (nodes as sub-tasks, the status labels and the workflow status mapping), its configuration (including localized workflow status names), its limitations (node and edge limits, command durations, best-effort clean-up on detach, the trust boundary) and its real-Jira verification with before/after timings.
- README links to the manual and the sample from both the English and Japanese sections.
- README (English and Japanese) describes `update-ticket` and `delete-ticket`. The `refine-ticket` skill now points to `update-ticket` for corrections that should not reset the status to `REFINED`, and the `create-ticket` skill mentions `delete-ticket` for removing a ticket created in the wrong project, after the user confirms.
- Refreshed the README screenshots of the execution graph and the artifact preview.
- Contributors: `dev/mysql/` provides a Docker Compose MySQL (with TLS) and `dev/mysql/test.sh`, which runs the MySQL store tests against it in a throwaway database, from any worktree.

## Upgrade notes

- HTTP data source: no action needed. Existing SQLite and MySQL configurations are unaffected, and the HTTP settings are ignored unless `dbBackend` is `"http"`.
- `npm test` now also runs `go vet` and `go test` for `examples/jira-datasource` (CI never contacts a real Jira).
- Jira sample only: data written by pre-release builds of `examples/jira-datasource` (the whole graph in the ticket's `graphops.graph` property, artifacts on the ticket's issue) is not read by this version and is not migrated; such tickets show an empty graph. Finish or detach them with the build that created them.
- `$HOME/.graph-ops/workflow.yaml` is no longer read by any tier. If you kept team settings there, move them into a project's `.graph-ops/workflow.yaml` (or your user settings in `config.yaml`).
