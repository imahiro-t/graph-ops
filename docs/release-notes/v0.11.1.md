## Changes

- **Autopilot child sessions stay in Terminal.app tabs instead of drifting into new windows.** In Terminal.app, a child session is meant to open as a new tab of the orchestrator's window, but it often opened in a new window instead -- sometimes leaving an empty tab behind -- and once that started, it tended to go on for the rest of the run. The likely causes, from the code and the run files: the tab script sent one Apple event per tab of every Terminal window, so with 20-30 busy tabs it could run past its 15-second limit, and every timeout disabled the tab for the rest of the run; a timeout after Cmd+T left the new tab empty; and the new tab's window had to have exactly the same bounds as the orchestrator's, which it sometimes did not while the tab bar appeared (error 9102, again leaving an empty tab). Now (DFLT-00361):
  - The script finds the orchestrator's window and the new tab's window with a fixed number of Apple events, however many tabs are open.
  - A timeout disables the tab at once only when Terminal or System Events had not answered yet (an Automation permission prompt nobody answers, as before). A timeout after both answered is taken as Terminal answering slowly: that launch opens a new window and the next one tries the tab again, and only the second such timeout in a row (with no tab opened in between) disables the tab for the run.
  - The new tab counts as being in the orchestrator's window when its left, top and right edges are within 4 points of it, checked for about 2 seconds (the bottom edge, which moves when the tab bar appears, is not compared). A 9102 now gives both windows' bounds.
  - When a tab cannot really be opened, the session still opens in a new window, as before.
- **Each Terminal.app tab fallback is recorded in the run file.** A launch that tried a tab and fell back to a new window is now kept in the run file (`$HOME/.graph-ops/autopilot/<projectId>/runs/<runId>.json`) under `terminal_tab_failures`, the latest 50: when, which ticket and role, the kind (`script-error`, `timeout` or `lock-busy`), the error number, the message, the last phase the tab script reached, whether Cmd+T had been sent (`keystroke_sent`) and whether that launch disabled the tab for the run (`disabled_run`). `terminal_tab_slow_timeouts` counts the slow timeouts in a row. Both fields stay in the local run file and are not shared with other members, and a run file of an earlier version reads as before. The orchestrator's stderr warning also gives the kind, the phase and whether an empty tab may have been left. docs/autopilot.md explains how to read the record ("Tracing each fallback") and how to check tabs by hand on a real Mac ("Checking tabs on a real Mac") (DFLT-00361).
- **Autopilot child sessions no longer try a Terminal.app tab while the screen is locked.** With the changes above, a tree run still opened 8 of its 17 child sessions in new windows, now and then: 6 with 9103 (Terminal did not come to the front) and 2 with 9102 (no new tab appeared). Matched against loginwindow's log, all 7 launches made while the screen was locked had failed: while the screen is locked, macOS lets no app but loginwindow come to the front, so Terminal cannot be brought forward by any means (6 × 9103), and when Terminal had been in front as the screen locked, the script went on and its Cmd+T was typed into the lock screen (1 × 9102). With the screen unlocked, another app in front or a child tab being selected did not keep Terminal from coming to the front. Now `graph-engine` reads the screen lock (`CGSSessionScreenIsLocked` from `ioreg`, a read only, bounded to 2 seconds) right before the tab script; while the screen is locked it runs no script -- no activation, no keystroke -- and opens the session in a new window at once, recorded as kind `screen-locked` without disabling the tab, so the next launch tries the tab again. A key that is missing or cannot be read counts as unlocked and the tab is tried as before. Sessions launched while the screen is locked therefore still open in new windows: this is a macOS restriction, and counting a locked screen as outside the normal conditions in which sessions should always open as tabs is an interpretation made for this change, explained in docs/autopilot.md ("Fallbacks while the screen is locked"). The detection was confirmed on macOS 26.3, locked and unlocked; other macOS versions have not been checked (DFLT-00362).
- **A tab that opens late is used instead of being left empty.** The one fallback seen with the screen unlocked was a 9102 whose Cmd+T had reached Terminal while no new tab appeared within the 6-second wait; it was probably a tab that opened late, but this was not reproduced. When the wait runs out, the tab script now takes one more look 2 seconds later and runs the session in a tab that has appeared by then, instead of leaving it empty and opening a new window as well. Such tabs are counted in the run file as `terminal_late_tabs`, with one warning line on stderr (DFLT-00362).
- **More detail on why a session opened in a new window.** Each record in `terminal_tab_failures` now has `diagnostics`: the screen lock before the script and after a failure (`screen_lock`, `screen_lock_after`), and, depending on how far the script got, the frontmost app when it gave up and just before Cmd+T (`frontmost_app`, `frontmost_app_before`), Terminal's front window and the orchestrator's window (`front_window_id`, `front_window_bounds`, `target_window_id`, `target_window_bounds`), the number of tabs before Cmd+T (`tabs_before`) and whether the new tab was found only in the last look (`late_tab`). The stderr warning adds the frontmost app, and notes when the screen had locked by the time the tab failed. Launches that open a new window without trying a tab are now counted too: `terminal_window_launches` counts them by reason (`not-darwin`, `terminal-command`, `tmux`, `tab-disabled`, `no-tty`, `invalid-tty`), `terminal_tty_reason` says why the orchestrator has no tty (`term-program`, `tmux`, `not-darwin`, `ps-failed`, `ps-unparsable`, `invalid-tty`, `not-found`), and the first launch that goes to a new window because the tab was disabled for the run prints one warning saying so. `screen-locked` launches stay in `terminal_tab_failures`, one record per launch, so their times can be checked against loginwindow's log; beyond 50 records the oldest `screen-locked` one is dropped first, so a long screen lock does not push out the failures of tabs that were tried. All the new fields stay in the local run file and are not shared with other members, and run files of earlier versions read as before. docs/autopilot.md explains how to read them, how to tell a 9102 apart, and how to check tabs and the screen lock by hand without disturbing other runs, and lists what has not yet been checked on a real Mac with the screen unlocked (DFLT-00362).
- **The tab script's time limit goes from 15 to 20 seconds, and the wait for the tab lock from 20 to 25 seconds.** This makes room for the last look (2 seconds) and the diagnostic reads (each bounded to 1 second). A launch can now take about 59 seconds at worst instead of about 45: 25 for the tab lock, 2 for reading the screen lock, 20 for `osascript`, 2 for reading the screen lock again after a failed tab, and 10 for `open -a Terminal` (DFLT-00362).
- **Long artifact names stay inside the artifact card at desktop widths, and Download gets the blue focus ring.** At 80rem and wider (for example 1280px at 100% text), an artifact name with no break opportunity pushed the header row of the artifact card -- in the node tab's artifact accordion and in the Artifacts tab -- 15-24px past the card, and squeezed the Download link and the type badge down to one character per line. The long name now wraps inside the card, while Download and the type badge stay on one line. Short names keep the same one-row layout as before, and the layout below 80rem (including 320px at 200% text, fixed in DFLT-00334) is unchanged. The Download link's keyboard focus now shows the same blue ring as the other controls (`ring-blue-500`, `ring-blue-400` in dark mode, on focus-visible only) instead of the browser's default outline (DFLT-00345).
- **"Open in new tab" and "Download all artifacts" get the same blue focus ring.** In the artifact panel, the "Open in new tab" link (in the node, Gherkin, HTML and Artifacts tabs) and the "Download all artifacts" link at the right end of the tab row now show the same blue ring as Download and the other controls on keyboard focus (`ring-blue-500`, `ring-blue-400` in dark mode, on focus-visible only) instead of the browser's default outline. In the Artifacts tab, an HTML artifact's "Open in new tab" link is now only as wide as its label, so the ring no longer spans the whole card (DFLT-00363).
- **In the Gherkin and HTML tabs, the "Open in new tab" focus ring no longer overlaps the artifact name, and long names wrap in the header row.** The header row of each Gherkin and HTML artifact had no space between the name and "Open in new tab", so the link's blue focus ring overlapped the end of a long name by about 2px, and a name with no break opportunity could push the link out of the card. The name and the link (with the date in the Gherkin tab) now keep at least 8px apart, a long name wraps inside the row, and below 80rem the link moves to the next line, right-aligned, when it does not fit -- down to 320px at 200% text. Short names keep the same one-row layout, and the other tabs are unchanged (DFLT-00365).
- **An icon button's tooltip opens on the first hover right after the content under a resting pointer changes.** When the content under a pointer that had stopped moving was replaced -- right after switching tabs in the settings modal, for example -- the first hover on an icon button there did not open its tooltip, for enabled and disabled buttons alike, until the pointer left and came back. It now opens after the usual delay. The other hover behaviour is unchanged: a pointer that only crosses the button still opens nothing, and a tooltip dismissed with Escape stays closed until the pointer leaves and comes back (DFLT-00342).
- **In the Gherkin tab, the artifact's date no longer runs past the header row at 320px with 200% text.** With a narrow window and large text (320px at 200% text), the right side of a Gherkin artifact's header row is only about 90px wide, narrower than the date itself, so the date ran 7-13px (Japanese/English) past the row into the card's padding. It now wraps inside the row; at 80rem and wider it stays on one line as before. The "Open in new tab" label that a long artifact name used to squeeze (two lines at 1457px, two characters a line at 375px) was checked in Chrome at 1457px, 1280px, 375px and 320px, light and dark, Japanese and English: since DFLT-00365 it stays on one line there for long and short names, and at 320px with 200% text it wraps over two or three lines because it is wider than the row, never one character a line. The link itself, the HTML tab and the other tabs are unchanged (DFLT-00366).
