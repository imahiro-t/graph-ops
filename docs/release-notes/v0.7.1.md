## Highlights

- **Labels can now be listed and registered from the CLI, and the ticket skills use this to suggest labels.** Until now `create-ticket` / `refine-ticket --label` could only attach labels that were already registered, the only way to see which ones existed was the `LABEL_NOT_FOUND` error message, and registering a new label meant a trip to the Web UI's Settings → Labels. Two new commands close that gap: `graph-engine list-labels` and `graph-engine create-label`. `/graph-ops:create-ticket` and `/graph-ops:refine-ticket` now list the project's labels, suggest the existing ones that fit the ticket, propose a new label (name and color) only when none fit, and register it only after you approve it. Renaming and deleting labels are still done only in the Web UI.

## Changes

- **`graph-engine list-labels [--project <id>]`** prints the project's registered labels as a JSON array, sorted by name ignoring case, each with `id`, `project_id`, `name`, `color` and `ticket_count`; a project with no labels prints `[]`. An unknown project is an error (`PROJECT_NOT_FOUND`).
- **`graph-engine create-label <name> [--color <color>] [--project <id>]`** registers a new label and prints it as JSON. Validation is the same as the Web UI's: the name is trimmed, 1-50 characters and unique within the project ignoring case, and the color must be one of the palette keys `gray red orange amber green teal blue indigo purple pink`. An invalid name (`INVALID_LABEL_NAME`) or color (`INVALID_LABEL_COLOR`), a taken name (`LABEL_NAME_TAKEN`) or an unknown project (`PROJECT_NOT_FOUND`) is an error and creates nothing.
- **`create-label` picks a color when `--color` is omitted**: the first palette color, in the order above, that no label in the project uses yet. When every color is already taken it picks the least-used one (the earliest in palette order on a tie), so the new label shares a color with an existing one rather than failing. This applies to the CLI only; the Web UI's new-label form still starts at gray and lets you choose.
- **Both commands pick the project the same way `create-ticket` does**: without `--project`, the project whose local path contains the current directory, else this environment's current project (`use-project`), else an error. The choice is reported as one `resolved project: ...` line on stderr, and stdout stays JSON only; with `--project` nothing is written to stderr. They work with every data source: SQLite, MySQL and the HTTP custom data source. The HTTP data source protocol is unchanged, since they use its existing label endpoints.
- **The ticket skills' label step now follows four steps**: list the project's labels, suggest existing ones, propose a new one only if nothing fits, and register it only with the user's explicit approval. `/graph-ops:refine-ticket` always passes the ticket's own `project_id` as `--project`, so a label can't land in a different project when you run it from another project's directory.
- **The `LABEL_NOT_FOUND` message for a project with no labels** now reads `(none; register labels with "graph-engine create-label" or in the Web UI settings)` instead of pointing at the Web UI only. The error code is unchanged.

## Fixes

- **Parallel runs on SQLite no longer fail with `database is locked` when two commands change the same ticket at once.** SQLite transactions now begin with `BEGIN IMMEDIATE`, so a command that reads a row and then writes it takes the write lock up front and waits for another process to finish (up to the existing 5-second busy timeout) instead of failing on the spot. This mostly affected `get-executable` and `complete-node` run by parallel node subagents: when both moved a ticket to a new status at the same moment, one of them could fail (about 2-3% of processes under six-way contention). MySQL and the HTTP data source are unaffected.
- **A failed `get-executable` no longer leaves nodes looking "in progress" with nobody running them.** `get-executable` marks each node `IN PROGRESS`/`IN REVIEW` as it hands it out and then updates the ticket status. If a later step failed, the nodes it had already marked stayed that way, were never handed to anyone, and blocked the ticket until someone ran `unstick-node`. Now a failed call puts every node it marked back to its previous status before returning the error. A node that someone else has moved on in the meantime is left alone. When the error does not mention `unstick-node`, simply calling `get-executable` again is enough. If putting a node back fails too, the error lists the node IDs that are still marked (`failed to release claimed node(s) ...`); run `unstick-node` on those, then call `get-executable` again. If the failure was in claiming a node in the first place, the error names that one node (`claiming node <id>: ...`) and the engine does not put it back, because it cannot tell whether only reading the row back failed after the write or another `get-executable` call legitimately claimed the node first. Check it with `get-ticket`, and run `unstick-node` on it only if it shows `IN PROGRESS`/`IN REVIEW` and was not handed to any worker; if it is still `TODO`, just call `get-executable` again. One error can report both cases. The `process-ticket` skill now follows the same rule.
- **Settings: switching the selected item in the Node Types and Skills tabs now asks before discarding unsaved edits.** Picking another node type or skill in the list used to throw away the text you had typed without a word. It now asks first, with the same "unsaved changes" confirmation the Templates tab already used. Cancel keeps both the selection and your edit; OK switches and discards it, and the settings dialog then treats the tab as clean, so changing tabs right afterwards does not ask again. Picking the item that is already selected does nothing.
- **Settings: deleting a node type's override now asks first.** The delete button in the Node Types tab removed the saved instructions for a custom node type on a single click, with no way to get them back. It now asks for confirmation, naming the node type, and nothing is deleted if you cancel.
- **Settings: a review gate with an empty ID is no longer silently dropped on save.** A row whose gate ID was empty (or only spaces) used to be skipped while the tab still showed "Saved". Saving now stops with an error instead: nothing is written, "Saved" is not shown, and everything you typed stays in place so you can add the ID or delete the row. Screen readers announce the error, and the empty ID field is marked invalid and linked to it.
- **Settings: editing one field of a review gate no longer freezes the whole gate.** Changing a single field of a plugin-default gate (for example its max iterations) used to save every field of that row as an override, so later updates to the plugin's defaults for that gate -- its criteria, its max iterations, and so on -- silently stopped reaching it. Only the fields you actually change are saved now; a field changed and then changed back is not saved, and editing a gate you had already overridden keeps the fields that override already had. The ID of a plugin-default gate can no longer be edited, even after you have overridden it, since the fields the override leaves out come from that default (use "Add Review Gate" for a new ID; custom gates can still be renamed). A field an override leaves empty now shows the default it inherits as a placeholder ("Default: ...") instead of looking blank. Overrides already saved as a full copy of a row are not migrated automatically: to go back to the default for a field, empty that field and save.

## Documentation

- `PRIVACY.md` now lists the HTTP custom data source (`dbBackend: "http"`) under network access, in both English and Japanese: what is sent (tickets, execution graphs, artifacts including their content, projects, and labels), where (only the URL you configure), and how it is authenticated (the configured token as an `Authorization: Bearer` header; HTTPS and a token are required for any non-loopback URL, and redirects are not followed). The same policy's "where your data is stored" and "deleting your data" sections now cover the HTTP data source too. This had been missing since v0.6.0.
- `graph-engine help` and the README (English and Japanese) describe `list-labels` and `create-label`, and no longer say that labels can only be registered in the Web UI. Renaming and deleting are still done only there.
