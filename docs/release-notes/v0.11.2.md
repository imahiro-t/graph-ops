## Changes

- **"Download all artifacts" numbers the node folders in execution order and includes the ticket's description.** In the zip from a ticket's "Download all artifacts" (`GET /api/tickets/{id}/artifacts/download`), each node's folder is now named `NN_<node name>` (for example `01_Plan`), numbered in the order of the Web UI's node list -- the execution graph's topological order, with parallel nodes in creation order -- so a file manager sorting by name shows the folders in the order the work was done. Only nodes with at least one artifact in the zip are numbered, starting at 01 with no gaps; a node without artifacts gets no folder and no number. The numbers are two digits, and with 100 or more numbered nodes every prefix is widened to the same number of digits. The ticket's description is added at the top of the zip as `00_チケット説明.md` (the Markdown as written; `000_` with three-digit numbers), and is left out when the description is empty. Artifacts with the same name in one folder still get `-2`, `-3` suffixes, and artifacts that cannot be decoded are still skipped. README.md describes the zip's layout (DFLT-00373).
- **The Autopilot settings tab has a project selector, like the Labels tab.** Settings > Autopilot no longer edits only the project the app has open: the tab now has the same project selector as the Labels tab and can load and save any registered project's autopilot settings (`GET`/`PUT /api/projects/{id}/autopilot-settings`). It starts on the app's current project (or the first project when none is selected) each time the tab is opened. When there are no projects, only the selector is disabled: the tab still opens and shows a no-projects message instead of the settings form. Switching projects shows the loading line instead of the previous project's values until the new settings arrive, and saving goes to the project selected at that moment. With unsaved changes, switching asks for the same discard confirmation as switching tabs: discarding switches, cancelling keeps the current project and the edits. The tab's heading no longer includes the project name. README.md describes the selector (DFLT-00374).
- **Each node type runs on its own model, and a model cap can be chosen at launch.** `process-ticket` now starts each node's subagent on the model assigned to its node type: `report` on `haiku`, `gherkin_test` and `release` on `sonnet`, and every other node type -- custom ones included -- on `inherit`, the top tier. A node type gets a lower model only when its input is fixed by earlier artifacts or a template, its procedure is fixed, and its mistakes are caught by a later review or check; the default `workflow.yaml` documents these criteria. The assignments can be overridden per node type with `node_models` (`haiku`, `sonnet`, `opus` or `inherit`) in your own `config.yaml` or the team tier's `workflow.yaml`, merged key by key with the team tier winning; an invalid value makes `graph-engine` refuse the file, and Settings reports it as `NODE_MODEL_INVALID` and refuses to save it. `graph-engine get-workflow-catalog` prints the merged `node_models`. `/graph-ops:process-ticket`, `/graph-ops:autopilot-ticket` and `/graph-ops:autopilot-tree` take `--model haiku|sonnet|opus`, and the Web UI has a "Model cap" selector next to "Run" and in the "Autopilot" confirmation. The chosen model is a cap: every node runs on `min(its node type's assignment, the cap)`, and the cap is passed on to the subagents and, in an autopilot run, to every child and grandchild session (started with `claude --model <cap>`). A session launched from the Web UI, and the autopilot's orchestrator, run on the chosen model themselves. Without a cap nothing changes for the top-tier nodes: the launching session's own model is the cap, and a node whose model is the session's own family gets no model and inherits the session as it is (version and 1M-context variant included); a session whose model family cannot be recognised is treated as having no cap. `get-executable` takes `--model-cap` and `--session-model` and prints each node's `model` (`""` for none). Autopilot runs record the cap as `model_cap` (shown by `autopilot start`, `status`, `worker-context`, the runs API and the summary); resuming from the CLI without `--model` keeps it and `--model inherit` removes it, while resuming from the Web UI with "Not specified" sends `inherit` and removes it. `POST /api/claude/launch` and `POST /api/tickets/{id}/autopilot` take an optional `model`. README.md and docs/autopilot.md describe the assignments and the cap (DFLT-00375).

## Upgrade notes

- **Existing setups get the new default assignments.** User and team tiers without `node_models` inherit the plugin's defaults, so after updating, `report` nodes run on Haiku and `gherkin_test` / `release` nodes on Sonnet even when no cap is chosen. To keep a node type on the launching model, set it to `inherit` in `node_models`. There is no automatic retry on a higher model when a node fails on a lower one.
