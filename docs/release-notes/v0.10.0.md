## Highlights

- **Autopilot: run a ticket, or a whole tree of tickets, from refinement to release without waiting for anyone.** `/graph-ops:autopilot-ticket <ticketId>` takes one ticket through refinement, its execution graph, release and the decision on follow-up tickets with no human input. `/graph-ops:autopilot-tree <ticketId>` does the same for the ticket and then, one at a time, every ticket derived from it, including the ones created along the way, and ends with a summary of the whole tree. The session you start it in does no ticket work: each ticket is worked on by a child Claude Code session in its own terminal, git worktree and branch, and the starting session keeps only a three-line summary per ticket, so a tree of 20 or more tickets fits in one session. An interrupted run continues where it stopped when you run the same command again. Both can also be started from the Web UI, which shows which ticket is being worked on. See the autopilot reference, `docs/autopilot.md`.
- **Tickets can have a parent.** `graph-engine create-ticket --parent <ticketId>` creates a ticket as a child of another one, `get-ticket` shows `parent` and `children`, and the Web UI shows both on an expanded ticket and lets you move between them.

## Changes

- **Parent and child tickets.**
  - `create-ticket --parent <ticketId>` sets the parent at creation; it cannot be changed later. Without `--project` the ticket goes into the parent's project; a `--project` naming another project is `VALIDATION_ERROR` and an unknown parent is `TICKET_NOT_FOUND`, and no ticket is created in either case.
  - `get-ticket` and `GET /api/tickets/{id}` add `parent_ticket_id`, `parent` (`{id, title, status}` or `null`) and `children` (the same shape, in creation order). Every ticket of `GET /api/tickets` carries `parent_ticket_id`, and `POST /api/tickets` accepts it (without `project_id`, the ticket goes into the parent's project). The Web UI's "New Ticket" form does not set a parent.
  - An expanded ticket in the Web UI shows a "Parent ticket" link and a "Child tickets (n)" list with each ticket's status. Clicking one opens that ticket, clearing the list filters (with an announcement) if they hide it.
  - Deleting a parent leaves its children in place with no parent.
  - `/graph-ops:create-ticket` now documents `--parent` for a ticket derived from an existing one.
- **Autopilot commands.** Three new skills: `autopilot-ticket` and `autopilot-tree` (the orchestrators you invoke) and `autopilot-worker` (the internal skill of the child sessions, not meant to be invoked by hand). A run:
  - processes a tree depth first, one ticket at a time, skipping `DONE` / `CLOSED` tickets (but not their children) and tickets in progress elsewhere (with their subtrees), up to `maxTickets` and `maxDepth`. The ticket you start from is always processed; a new run cannot start from a `DONE` or `CLOSED` ticket (`AUTOPILOT_ROOT_FINISHED`).
  - decides what a person would otherwise decide: it adopts the recommended completion criteria and "why" in refinement, approves or rejects `approval_gate`s, grants at most one extra review round per loop target at an iteration limit, releases as the project's settings say, and decides which open items become follow-up tickets (created as children of the ticket). Every decision is saved with its reasons as an `autopilot-decision-refine` / `-approval` / `-iteration` / `-release` / `-handoff` artifact, and the tree's summary as `autopilot-tree-summary`.
  - follows `onFailure` when a ticket fails or is blocked: `stop` stops the run, `continue` skips that ticket's subtree and goes on. A child session that shows no activity at all (no autopilot CLI call, no change to the ticket in the database, no change in its worktree) for `stallTimeoutMinutes` is failed as `unresponsive`; a session that cannot be launched twice in a row is failed as `launch_failed`.
  - is refused with `AUTOPILOT_ALREADY_RUNNING` when an active run already owns the ticket or its tree. Runs of different projects never interfere.
- **Branch strategy.** Every ticket is worked on in `<local path>/.claude/worktrees/<ticketId>` on the branch `worktree-<ticketId>` (the names `EnterWorktree` uses). A tree's children branch off their parent's branch and, when finished, merge their parent's branch in and fast-forward it, without approval. When a subtree is finished, its top ticket is fast-forwarded into its parent's branch again (merge-up), so the work of every finished descendant, at any depth, reaches the root's branch; when a fast-forward is not possible, a merge session merges instead. Only the root is brought into the main branch, as `mainReflection` says.
- **Per-project autopilot settings.** A new Settings > Autopilot tab edits, for the project in the header, `mainReflection` (`branch` / `pull_request` / `merge`; default `branch`), `permissionMode` (`acceptEdits` / `auto` / `dontAsk` / `bypassPermissions`; default `auto`), `autoApproveGates` and `autoCreateTickets` (default on), `maxTickets` (1-100, default 20), `maxDepth` (0-10, default 3), `onFailure` (`stop` / `continue`, default `stop`) and `stallTimeoutMinutes` (15-1440, default 60). Your values are saved in `$HOME/.graph-ops/config.json` under `autopilotSettings`.
  - A team can set them in `autopilot.yaml` at the root of `teamExtensionsDir` (`version: 1`, `defaults`, `projects.<projectId>`). Each key resolves as: the team file's `projects.<projectId>`, then its `defaults`, then your local value, then the built-in default. A key the team sets is locked: shown read-only in the Web UI, and a save that includes it is refused as a whole with `400 AUTOPILOT_SETTING_LOCKED`.
  - `permissionMode: bypassPermissions` is never taken from the team file; it is ignored with a warning. Invalid team values are ignored with a warning instead of failing.
  - `graph-engine autopilot settings [--project <id>]` prints the values in effect with their sources. It is read-only; values are saved through `PUT /api/projects/{id}/autopilot-settings`.
- **Web UI.** An expanded ticket has "Autopilot (single)" and "Autopilot (tree)" buttons, which open the orchestrator in a new terminal with the project's permission mode after a confirmation. The confirmation is an in-app dialog, not the browser's native `confirm`, so browser automation and UI tests can answer it: focus starts on "Cancel", and Escape or a click outside cancels. If a refresh makes the start impossible while it is open, it closes without starting. Badges in the ticket list and on the expanded ticket show a run's root ("Autopilot running"), the ticket being worked on ("Processing"), a session waiting for a person ("Waiting for a person"), and the tickets still to come ("Waiting"). The buttons are disabled, with the reason, where a start would duplicate an active run. A stopped run can be resumed from its root's button even after the root has become `DONE`. An "Automatic decisions (n)" section lists a ticket's `autopilot-` artifacts.
- **Copy a ticket's ID and title from the ticket list.** In the Web UI's ticket list, the ID and the title in a ticket's header row can now be selected by dragging or double-clicking and copied as text; a click that makes or ends a selection no longer expands or collapses the row, while a plain click (or the chevron from the keyboard) still does, even when a selection is left over. Double-clicking selects one hyphen-separated part of the ID; drag or triple-click to select all of it. A new button next to the ID copies the ID to the clipboard and briefly shows whether it worked (also announced to screen readers). Where the browser offers no Clipboard API (for example over plain HTTP other than localhost), the button shows that the copy failed, and the ID can still be selected and copied by hand. The chevrons of a ticket row and of a node row are now named buttons ("Toggle details for <id>") that report whether the row is expanded, and the ticket row's chevron and its reopen/close/delete buttons, and the node rows' chevrons, have enough contrast in light and dark mode (WCAG 1.4.11).
- **App Settings edits the team settings directory instead of your own settings directory.** The "Node/Workflow Config Directory" field, which edited `userExtensionsDir`, is now "Team Settings Directory" and edits `teamExtensionsDir`, the shared directory whose settings take precedence over your own. Its description says what the team tier covers, that a blank field means no team tier (only your own `$HOME/.graph-ops` is used), and that the path must be absolute; a relative path is flagged in the field and blocks saving. Blank removes the key from `config.json`, keeping every other key. The team tier can set node-type instructions, workflow settings (review gates and the review iteration limit in `workflow.yaml`), templates, skill instructions and `autopilot.yaml`; it cannot set the database connection, project local paths, `myName`, the current project or the language.
  - `userExtensionsDir` is no longer edited from the Web UI or saved by `PUT /api/settings/app`. A value already in `config.json` and `GRAPH_USER_EXTENSIONS_DIR` are still read, and saving App Settings keeps the value in the file; a `userExtensionsDir` sent in a `PUT` body is ignored.
  - `PUT /api/settings/app` accepts `teamExtensionsDir`. Unlike the other fields the page owns, leaving it out of the body (or sending `null`) keeps the saved value; an explicit `""` (or whitespace) removes it. A non-empty relative path is refused with `400 VALIDATION_ERROR` and nothing is written. `GET` adds `effective.teamExtensionsDir`, the team directory in effect (`""` when there is no team tier, including when it names your own directory).
- **The language is a personal setting.** The working language is now resolved from your own tier (`language` in `$HOME/.graph-ops/config.yaml`, set by `/graph-ops:onboarding`) and an explicit `--language` only. A `language` in the team tier's `workflow.yaml` is ignored, and `graph-engine` prints a `graph-ops: warning: team workflow.yaml sets language "...", which is ignored: the working language is a personal setting (...)` line on stderr (the JSON output and exit codes do not change). `get-language-settings` reports `source` as `"user"` or `"none"`; it no longer returns `"team"`. The `onboarding` and `process-ticket` skills and `graph-engine help` describe the new behavior.
- **See which projects are waiting for your approval from the project switcher.** When you open the Web UI's project menu, each project with tickets awaiting approval shows how many: a ticket counts when it has an `approval_gate` that has been reached (every non-loop node feeding into it is `DONE`) and is still `TODO` -- the same gates that blink yellow in the ticket list. A ticket with several such gates counts once, and a project with none shows no badge. `CLOSED` tickets are not counted, because their nodes cannot be completed; tickets in any other status, `DONE` included, are. The counts are fetched again every time the menu opens; while they load, or if they cannot be loaded, the menu works as before, just without badges. Each badge is named for screen readers ("2 tickets awaiting approval") and meets WCAG 1.4.3 contrast in light and dark mode. The counts come from a new endpoint, `GET /api/projects/pending-approvals`, which returns `{"counts": {"<projectId>": n}}` for every project with at least one such ticket (projects with none are left out, and `counts` is `{}` when there are none anywhere); `GET /api/projects` is unchanged.
- **The project switcher works with the keyboard and screen readers.** The Web UI header's project button now tells assistive technology whether its menu is open (`aria-expanded`) and that it opens a popup (`aria-haspopup="dialog"`; the menu is a non-modal dialog named "Switch project", linked with `aria-controls` while open). Pressing Escape while the menu is open closes it and puts focus back on the button, whether focus was on the button or on an item in the menu; Escape does nothing extra while the menu is closed. Opening, closing and choosing from the menu with the mouse work as before. In the menu, the current project's item is marked with `aria-current`, so screen readers announce which project is current rather than relying on the check mark's color; the check mark itself is decorative and not read out.
- **New CLI: `graph-engine autopilot`.** `start`, `next`, `launch`, `wait`, `merge-up`, `summary`, `status` and `settings`, plus the commands the child sessions use (`worker-context`, `record-decision`, `attach-decisions`, `touch`, `report`, `merge-into-parent`). Each run subcommand prints one line of compact JSON (`summary` prints Markdown); `wait` exits 2 on a timeout like `wait-node`. Runs are kept in `$HOME/.graph-ops/autopilot/<projectId>/`.
- **New HTTP API.** `POST /api/tickets/{id}/autopilot` (`{"mode":"ticket"|"tree"}`) reserves a run and opens the orchestrator; `GET /api/autopilot/runs?project_id=<id>` returns the active runs and the five most recent other runs, each with its tickets' states, `members` (the tickets an active run owns, used to disable the buttons) and `pending` (the tickets it may still process); `GET` / `PUT /api/projects/{id}/autopilot-settings`. API errors can now carry a `details` object (for example `details.keys` for a settings error).
- **HTTP custom data source protocol 1.1.** `Ticket` gains an optional `parent_ticket_id`, accepted by `createTicket`. 1.1 is a minor addition: a 1.0 plugin keeps working for everything else, but a ticket with a parent is refused with `PARENT_TICKET_UNSUPPORTED` before anything is sent, so the parent is never dropped silently. There is no new endpoint; children are derived from `listTicketsByProject`. The Jira sample plugin speaks 1.1 and keeps the parent in its `graphops.ticket` issue property (Jira's own `parent` field is not used).
- **The existing skills defer to the autopilot where it runs them.** `process-ticket`, `refine-ticket` and the `release` / `approval_gate` node-type instructions now note that, when an autopilot child session uses them, the `autopilot-worker` rules take precedence. Their behavior is otherwise unchanged.

## Fixes

- **Saving `config.json` no longer drops the top-level keys this version does not know.** `graph-engine` -- the CLI and the UI server alike -- rewrites `$HOME/.graph-ops/config.json` whenever it saves a setting there -- for example when switching projects (`use-project`, or in the Web UI), setting a project's local path (when creating the project or later), deleting a project, saving App Settings, or, once, copying the current project recorded in the database into `config.json` when the file does not have one yet. It used to write back only the settings its own version knew, so a binary of another version silently deleted the rest. That is how a v0.9.0 UI server that was still running after an update removed the new `autopilotSettings` the moment someone switched projects. Every save now keeps each top-level key it does not know, with its value written back exactly as it was read: nested objects, arrays, integers beyond 2^53, `1.0`, `null`, and escaped forms such as `\u003c` are not re-encoded (only whitespace and indentation are normalized). Unknown keys are written after the known ones, in key-name order. A key that differs from a known key only in case (for example `DBBackend`) is still treated as that known key and written back once, under its correct spelling. When there is no unknown key, the file is written byte for byte as before. Only the top level is preserved. That is enough because every setting this version knows is either a plain value or a plain JSON map, so rewriting it drops nothing nested; a test now fails if a setting whose value could drop nested keys is ever added.
- **App Settings' "currently in effect" and hint lines are readable in light and dark mode.** The small lines under the App Settings fields -- the value currently in effect (including "not set (personal settings only)" under the team settings directory) and the hints for the DB backend, MySQL password, TLS mode and CA, and the HTTP data source URL and token -- now have at least 4.5:1 contrast against their background in both themes (WCAG 1.4.3). Only their colour changed.
- **Screen readers announce App Settings' inline messages reliably.** The messages that appear under App Settings fields while you type -- MySQL's required fields, CA file and password-retype hints, the MySQL connection test result, the HTTP data source's token-retype hint and URL/token problems, and the team settings directory's relative-path warning -- are now announced through status regions that are present from the moment the tab opens, instead of regions that appeared together with their text, which some browser and screen reader combinations did not announce (WCAG 4.1.3). Each message is still read as the field's description, and is not read twice. Nothing changes on screen.
- **Icon-only controls in the Web UI have enough contrast in light and dark mode.** The archive icon next to a closed ticket's close reason, and the delete buttons for review gates, projects and node types in Settings, were drawn in a light gray that fell short of WCAG 1.4.11's 3:1 non-text contrast against a white background (about 2.5:1). They now rest at the same gray as the text beside them, which clears 3:1 on every background they sit on in both themes (at least 4.55:1). Their red hover color and the dimming of a disabled delete button are unchanged.
- **Screen readers no longer announce the Web UI's decorative icons, and the ticket list's page buttons have names.** Every icon in the Web UI only repeats the text beside it or the name of the button around it, so each one is now hidden from assistive technology (`aria-hidden="true"`), in line with WCAG 1.1.1. The ticket list's previous/next page buttons, which showed only an arrow and had no accessible name, are now announced as "Previous page" and "Next page" (WCAG 4.1.2). Nothing changes visually.
- **The dropdown arrows and the search icon in the Web UI header have enough contrast.** The arrows on the project switcher and on the status, assignee, priority and label filter buttons, and the magnifier in the ticket search field, are the only visual signs that those controls open a list or take a search. In light mode they were drawn in a gray that fell short of WCAG 1.4.11's 3:1 non-text contrast (about 2.5:1). They are now a darker gray in light mode and keep their gray in dark mode, clearing 3:1 on every background they sit on in both themes (at least 4.55:1).
- **A CLOSED ticket's approval gates no longer blink or offer approve/reject in the ticket list.** A reached `approval_gate` that is still `TODO` blinked yellow and showed Approve/Reject buttons even when its ticket was `CLOSED`, although the engine refuses to complete any node of a `CLOSED` ticket, so both buttons always failed. The ticket list now treats such a gate as not awaiting approval -- no blink, no "awaiting approval" tooltip, no buttons -- which matches the project switcher's pending-approval counts, where `CLOSED` tickets are already left out. A reject reason being typed when the ticket turns `CLOSED` is discarded, so it does not come back if the ticket is reopened. Tickets in any other status, `DONE` included, behave as before.
- **Focus no longer falls off the page when an approval gate's reject prompt closes.** In the ticket list, the reason field of an `approval_gate`'s Reject prompt dropped keyboard focus to the page body whenever it disappeared, with nothing telling a screen reader what had happened (WCAG 2.4.3, 4.1.3). After a rejection is sent -- including when the list refreshes and removes the prompt before the request itself has answered -- focus now moves to that gate's expand/collapse toggle in its node row, and the rejection is announced. When the prompt disappears because the ticket turned `CLOSED` or the gate was decided elsewhere, the same happens, announced as the gate no longer awaiting approval -- but only if focus was inside the prompt; otherwise focus stays where it is and nothing is announced. Cancel returns focus to the gate's Reject button. Opening another gate's prompt keeps focus in the new one, as before. A response that arrives after the prompt is already gone never pulls focus back from wherever the user has moved in the meantime, and rejects sent on two gates at once are settled independently.
- **Decisions on two approval gates at once no longer interfere with each other.** In the ticket list, when an approve or reject on one `approval_gate` finished while another gate's decision was still being sent, or while another gate's Reject prompt was open, two things went wrong. The reason being typed in the other gate's Reject prompt was wiped, and the gate still being sent went back to looking idle -- its spinner gone and its Approve, Reject and confirm buttons enabled again -- so it could be sent a second time. A finished decision now closes and clears only its own gate's Reject prompt, each gate keeps showing that it is being sent until its own response arrives, and a second decision on a gate whose first one is still being sent is not sent. Decisions on a single gate behave as before.
- **An approval gate's reject prompt closes with Escape, and a failed rejection returns focus to its reason field.** In the ticket list, closing an `approval_gate`'s Reject prompt from the keyboard meant tabbing to its Cancel button, and when a rejection failed and the prompt stayed open, focus could be left on the page body -- some browsers drop it from the confirm button while that button is disabled during the request (WCAG 2.1.1, 2.4.3). Pressing Escape in the reason field or on either of the prompt's buttons now does what Cancel does: the prompt closes, its reason is discarded and focus returns to the gate's Reject button. Escape does nothing while the rejection is being sent (Cancel is disabled then) or while an input method is composing text, and an Escape the prompt handles goes no further. When a rejection fails, focus moves back to the reason field if it was on the page body or still inside the prompt; if the user had moved it somewhere else while the request was being sent, it stays there.
- **The node row's expand/collapse toggle shows a focus ring.** In the ticket list, the toggle that focus returns to after an approval gate's reject prompt closes relied on the browser's default outline, which can be faint or missing; it now shows a blue focus ring (a lighter blue in the dark theme, so it stays visible on the hovered row) when focused from the keyboard or moved to by the app, and none on a mouse click (WCAG 2.4.7).

## Security

- **On a shared backend, a tree run executes other people's tickets with your permissions.** With MySQL, Jira or another HTTP data source, `autopilot-tree` processes every unfinished descendant in the database, including child tickets other people created (even during the run), on your machine, with your permission mode, and with approval gates decided automatically. Use tree mode there only when you trust whoever can create tickets under the root, and never together with `bypassPermissions`.
- `bypassPermissions` cannot be imposed from the shared team directory, and the Web UI warns when you choose it yourself. The permission mode is validated against a fixed list and quoted for every way the terminal is launched (a `terminalCommand`, tmux, Terminal.app, PowerShell).
- Ticket IDs are checked before they are used as worktree paths and branch names (letters, digits, `.`, `_` and `-`, starting with a letter or digit, no `..`).

## Known limitations

- **An untrusted project folder stops the run at Claude Code's workspace trust prompt.** The first session the autopilot opens in a new terminal (the orchestrator from the Web UI, otherwise the first child session) waits there for a person. Open the project's folder in Claude Code once and accept the prompt before the first run; the ticket worktrees under it are not asked again. The autopilot does not detect an untrusted folder.
- **The ticket you start from is not skipped when it is in progress.** Descendants that are `IN PROGRESS` elsewhere are skipped, but the root is not: do not start from a ticket someone is working on on another machine.
- **`pull_request` and `merge` need `git push` and `gh`.** If the child sessions' permission mode refuses them, the ticket ends `failed` (`permission_denied`) or stops at the last stage that worked. Check your permission settings before choosing these values.
- **Stopped runs are kept until you delete them.** Finished runs are pruned whenever a new run is created (the newest 20 are kept), but the latest stopped or interrupted run of each root and mode stays so that it can be resumed. Delete its file under `$HOME/.graph-ops/autopilot/<projectId>/runs/` if you will not resume it. A run file that cannot be read makes every start in that project fail with `AUTOPILOT_REGISTRY_CORRUPT` until it is repaired or deleted; the warning (CLI stderr, or the server log) names it.
- **The dirty check ignores untracked files.** A fast-forward into a parent's branch is refused (`PARENT_WORKTREE_DIRTY`) only for uncommitted changes to tracked files; an untracked file in the way makes git itself fail.
- **Child terminals stay open**, one per ticket, until you close them. Close the ones left from an interrupted run before resuming it.
- **The Web UI considers only the five most recent inactive runs** when it decides whether a `DONE` ticket's stopped run can be resumed; an older one can still be resumed with the slash command.
- **The "Waiting" badge can briefly miss tickets** that will be processed after a failed ticket is retried. Processing is not affected.
- **Processing several tickets of one tree in parallel is not supported.**

## Upgrade notes

- **The database gains a column.** The first time this version opens an existing SQLite or MySQL database, it adds `tickets.parent_ticket_id` (with an index and, on MySQL, a foreign key that sets it to `NULL` when the parent is deleted). Existing tickets have no parent. Teams sharing a MySQL database should upgrade together, so that everyone sees and keeps the parent tickets.
- **HTTP data source plugins** keep working at protocol 1.0; update them to 1.1 to use parent tickets.
- **Restart the UI server right after updating, before you change any autopilot setting** (see "Updating to a new release" in the README). An old server has neither the autopilot buttons nor the new API, and a server from 0.9.0 or earlier does not have the `config.json` fix above: if one is still running after you update to 0.10.0 and you save 0.10.0 settings such as `autopilotSettings`, they disappear the next time that old server writes `config.json` -- for example when you switch projects in its Web UI. Settings that have already disappeared cannot be recovered; set them again after the restart.
- **A team `workflow.yaml` no longer sets the language.** If your team distributed the working language through `language` in the shared directory's `workflow.yaml`, it is now ignored (`graph-engine` prints a `graph-ops: warning: team workflow.yaml sets language ..., which is ignored: ...` line on stderr) and the language falls back to your own setting, or English when you have none. Each person should run `/graph-ops:onboarding` once to set the language personally. Scripts that read `source: "team"` from `get-language-settings` will no longer see it.
- **The team settings directory can now be set from App Settings.** If you had set `userExtensionsDir` through App Settings, it stays in `config.json` and keeps working; change it by hand from now on. A client of `PUT /api/settings/app` other than the bundled Web UI should send `teamExtensionsDir` only when it means to change it.
