## Changes

- **"Select all" in the ticket-list filters.** Each of the four filters of the Web UI's ticket list (status, assignee, priority, label) now has a "Select all" button next to "Clear selection" at the bottom of its panel. It checks every option of that filter in the order the panel lists them, including the assignee filter's "Unassigned", keeps any selected value that is no longer offered as an option (such as an assignee who disappeared on a refresh), and leaves the panel open, so you can uncheck the few options you do not want -- for example, show every status except Done and Closed. The button is disabled when every option is already checked or the filter has no options; focus stays in the panel when it becomes disabled, so Escape still closes the panel.
  - With every option checked, the filter still reads "n selected", not "All". Checking everything is not always the same as no filtering: the label filter matches tickets that have any of the selected labels, so it hides tickets that have no label at all, and an assignee who appears on a later refresh is not included. For status, priority and assignee, checking every option shows the same tickets as selecting none.
- **Screen readers hear what "Select all" and "Clear selection" did.** In each of the ticket-list filters, pressing "Select all" now announces "All options selected (n)" and pressing "Clear selection" announces "Selection cleared" (in Japanese: "n 件すべてを選択しました" / "選択を解除しました") through a polite live region. Before, only the control that received focus was read out -- the first checkbox or the filter button -- so it was not clear that the whole selection had changed. n is the number of options in the panel (DFLT-00267).
- **For contributors: a new worktree without `npm ci` fails fast.** In a checkout where dependencies are not installed (typically a fresh git worktree), `npm run lint`, `npm test` and `npm run build` in `packages/web` now stop at once with a message telling you to run `npm ci` in the checkout's root, instead of picking up the parent repository's tools and failing with `ERR_MODULE_NOT_FOUND` for `@eslint/js` (or hanging in vitest). The README's Troubleshooting section describes it (DFLT-00267).
- **For contributors: the Node.js version needed for development is declared and checked.** Developing GraphOps needs Node.js 24 or later, the version CI uses; it is now declared as `engines.node` in `package.json` and `packages/web/package.json` and in a new `.nvmrc`. On an older Node.js (such as 20.10), `npm run lint`, `npm test` and `npm run build` in `packages/web` stop before starting eslint, vitest or tsc, with a message showing the required and the current version and how to switch, instead of failing with dozens of fake-timer timeouts. Contributors who used Node.js 22 need to switch to 24. What you need to run the plugin itself is unchanged. The README's Troubleshooting section describes it (DFLT-00273). `npm run dev` and `npm run test:watch` in `packages/web` now run the same checks first (Node.js version, then dependencies), so they no longer start vite or vitest on an older Node.js or in a worktree without `npm ci`; the root `npm run dev:web` and `npm run dev` stop the Web UI side with the same message, while `npm run dev`'s Go server side keeps running (DFLT-00289).
- **Web UI dependencies updated: React 19, Vite 8 and Tailwind CSS v4.** The Web UI now builds with React 19, Vite 8 (with `@vitejs/plugin-react` 6) and Tailwind CSS 4, replacing Dependabot's separate major-update pull requests, which could not pass CI on their own. The UI is meant to look and work as before: Tailwind v3's colors, breakpoints, line heights and default font are kept, and so are its spacing between stacked items, its default border and placeholder colors, the pointer cursor on buttons and the browser's own form-field styling; a few shadows, rounded corners and the blur behind dialogs that v3 never drew (their class names did not exist in v3) stay undrawn. Tailwind is now configured in `packages/web/src/index.css` through `@tailwindcss/vite`; `tailwind.config.js` and `postcss.config.js` are gone. One small difference: on a touch-only device, `hover:` styles no longer stick after a tap. Building the Web UI from source needs Node.js 24 or later, the version CI uses (see the item above).
- **The Web UI's JavaScript is split into smaller files.** The Web UI used to ship as one 765 kB JavaScript file, and every build warned that it was over Vite's 500 kB limit. React is now in its own file and the other libraries in another (about 220 kB each), next to the app's own code (about 320 kB), so the build no longer warns and the browser can keep the rarely changing React file cached across releases. The UI looks and works as before (DFLT-00275).
- **For contributors: Web UI tests tolerate a heavily loaded machine.** `packages/web`'s Vitest time limit per test and per hook is now 30 seconds instead of 5. With a load average above 200 (for example while several autopilot reviews run at once), 40-56 async UI tests used to fail on the 5-second limit and pass again once the load dropped. A passing test takes as long as before; only a test that really hangs is reported up to 30 seconds later (DFLT-00275).
- **For contributors: `App.labels.test.tsx` and `App.family.test.tsx` no longer depend on which request the fake backend answers first.** Several of their steps checked something right after the first ticket appeared that comes from a different request -- the label filter's options (`GET /api/projects/{id}/labels`), the project list in the settings modal and the project switcher (`GET /api/projects`), and the page size (`GET /api/settings/app`) -- so they failed whenever that answer landed later. They now wait for the checkbox, option, button or page count they are about to use. With the fake backend's answers delayed at random, the two files failed in 9 of 20 runs before and in none of 42 runs after (DFLT-00284).
- **For contributors: `packages/web`'s Vite and Vitest config files are type-checked.** `npm run build` in `packages/web` now also runs `tsc -p tsconfig.node.json`, which type-checks `vite.config.ts` and `vitest.config.ts`, so a type error in either config file fails the build (and CI) instead of going unnoticed; the app's own `tsconfig.json` still covers only `src/`. `vitest.config.ts` now imports `defineConfig` / `mergeConfig` from `vitest/config`, so its `test` block is typed, and imports `./vite.config.ts` with its extension, so `vitest` no longer prints Vite's warning about an import without a file extension (DFLT-00291).
- **For contributors: the rest of the `App.*.test.tsx` files no longer depend on which request the fake backend answers first either.** Following DFLT-00284, all 16 `packages/web/src/App.*.test.tsx` files were run with the fake backend's answers delayed at random (0-30, 0-100 and 0-300 ms), and every step that checked something right after the first ticket appeared although it comes from a different request now waits for it: the label filter's options in `App.filters.test.tsx` (`GET /api/projects/{id}/labels`), the pager wherever a test sets a page size (`GET /api/settings/app`, in `App.filters`, `App.headerNarrowReflow`, `App.largeTextReflow` and `App.ticketDelete`), the project switcher's items and pending-approval badges (`GET /api/projects`, `GET /api/projects/pending-approvals`, in `App.largeTextReflow`, `App.pendingApprovals`, `App.projectSwitcher.a11y` and `App.project`), the settings modal's app-settings form (`App.project`), and the autopilot runs (`GET /api/autopilot/runs`, in `App.autopilot`). In `App.autopilot`, a test whose poll changed both a ticket's status and its runs now changes them in separate polls (their answers are separate requests too), and the tests where a poll closes the confirmation dialog wait for focus to come back. Waiting until the app has read a given answer's body is now one shared helper, `trackBodyReads` in `packages/web/src/test/waitForAnswers.ts`, instead of a copy per test file. With 0-100 ms delays the 16 files had 3-9 failing tests in each of 10 runs before and none in 10 runs after (DFLT-00296).
- **The Web UI supports windows down to 320 CSS px with text up to 200%.** The Web UI's supported range is now a window 320 CSS px wide with the browser's text at up to 200% (a 32px default font), the size WCAG 1.4.10 Reflow asks for. Adjustments that only took effect in narrower windows or with larger text were removed: the icon-only header and its touch long-press tooltips in a window of 200 CSS px or less, the smaller padding and extra wrapping of the page, the expanded ticket, its node rows, its Markdown lists and the untrusted-folder notice at 200 CSS px or less and from 7.5rem down, and the two-line items of the project switcher's popup below 8rem. Earlier release notes, including v0.10.0's, describe some fixes as measured in a 160px window; the parts of those fixes that still apply at 320px with 200% text stay, and anything narrower or larger is now out of scope and may scroll sideways or be cut off. At 320px and wider, with text up to 200%, the Web UI looks and works as before. For contributors: the `upto-200px:`, `upto-7_5rem:` and `cq-below-8rem:` Tailwind variants, `IconButton`'s `longPressTooltip` and `title` options, the `useMediaQuery` hook and the `touchLongPress` test helper are gone, and the Web UI's tests use windows of 320px or wider with a root font of at most 32px (DFLT-00319).
- **Autopilot drops open items not worth a ticket instead of filing them all in the backlog.** When an autopilot run hands off a ticket's open items, it used to sort them only as in scope (child tickets) or out of scope (one backlog ticket), so every review note ended up in a backlog ticket and each run left 4-6 more items behind. A third kind, **Drop**, is now checked first: an item that only happens outside the project's supported range (as the project states it, for example through the `autopilot-worker` skill's extension, its settings or its README/docs; not used when no range is stated), a wording or style difference with no real effect, a check that needs a real device or environment with no defect found, a problem that has not been reproduced or observed, or a risk or trade-off the plan or a review explicitly accepted. A dropped item gets no ticket: the `autopilot-decision-handoff` artifact keeps its kind and its Drop reason (the criterion it matched, or "no reason worth working on"), and the run's summary only gives the number of dropped items. Each item that does go into a backlog ticket now carries one line on why it is worth working on, and an item without one is dropped with the reason "no reason worth working on". With `autoCreateTickets` off, the list shown to you includes the dropped items with their kind and reason, and one you pick still goes into the backlog ticket. (DFLT-00324)
- **Autopilot runs are shared between members, so two members can no longer start the same tree.** On a database several members share -- MySQL, a shared SQLite file, or an HTTP data source of protocol 1.2 -- every autopilot run is now also kept in the database, and `graph-engine autopilot start` and the Web UI's launch refuse a start that overlaps another member's active run with `AUTOPILOT_ALREADY_RUNNING`. The error names who started that run (`started_by` in `details`, and in the message), and the Web UI shows another member's run as "<name> is running" and names them when it disables the "Autopilot" button; `GET /api/autopilot/runs` returns other members' runs with `started_by` and `mine`. On MySQL and SQLite two overlapping starts at the same moment never both pass. Another member's run stops blocking you once its heartbeat is more than 10 minutes old; nothing rewrites its state. A stopped or interrupted run is resumed only on the machine that started it: another member's neither blocks nor is taken over (your start creates a new run). What only means something on the running machine -- the terminal, worktree paths, branch names -- stays in the local run file, which remains each machine's source of truth. Git branches are still not shared: reflect finished work with `mainReflection` `pull_request` or `merge`, and update your local default branch before starting (docs/autopilot.md, "Runs shared between members") (DFLT-00326).
  - Each machine now has an ID, kept in `$HOME/.graph-ops/machine-id` and created the first time it is needed. Deleting it makes your interrupted runs impossible to resume; a copied home directory gives two machines the same ID. A machine-id file that is not a valid ID is never replaced silently: starts fail with `AUTOPILOT_MACHINE_ID_UNREADABLE` (the Web UI says which file to restore or delete) until you restore or delete it.
  - A run that comes back after its heartbeat expired -- the orchestrator's machine slept, say -- while another member started an overlapping run stops itself with the reason `overtaken` before its next launch, so the two do not go on side by side. A child session it had already launched keeps running until it reports; keep the machine awake during a run on a shared database.
  - The database keeps at most 20 settled runs (finished, stopped or expired) per project; older ones are deleted when a run starts, whoever started them. Run files on each machine are not affected.
    - On an HTTP data source a start deletes at most 2 of them, the oldest first, and the rest go on later starts, so a slow data source no longer holds up the machine's other autopilot operations for as long as there are records to delete. A delete that fails is now logged ("deleting settled shared autopilot runs of project <id>: ..."), once while the same failure repeats, instead of being dropped silently; the start still succeeds (DFLT-00337).
  - A failure to read or write the runs in the database is logged once while it repeats, and "the shared autopilot runs are reachable again" is logged when it clears. This is tracked per kind of operation (listing the runs, sharing a run, putting back a cancelled launch's record, deleting settled records), so a success of one kind no longer logs "reachable again" while another kind is still failing (DFLT-00337).
  - The name shown for a member is their `myName` (App Settings), or `<OS user>@<host>` marked "(name not set)" when it is empty.
    - The name is cleaned before it is recorded and again before it is shown on any machine: tabs and line breaks become a space, other control characters (including ESC, so no terminal escape sequences) and all invisible format characters (Unicode category Cf: bidirectional controls, zero-width characters including ZWNJ and ZWJ, the BOM, ...) are removed, and the name is cut to 128 characters. Names written by an earlier version or straight into the database are cleaned when read. A name left empty is treated as unknown. Ordinary names are unchanged; an emoji joined with ZWJ shows as its separate emoji, and a name that spells with ZWNJ loses it (DFLT-00336).
- **Who is running a node is recorded, and `unstick-node` no longer releases another member's node by mistake.** On SQLite, MySQL and HTTP data sources of protocol 1.2, `get-executable` now records on each node it hands out who took it (the member's name, marked "(name not set)" when it is a stand-in), a claim token, the processing session and the time. `get-ticket` shows it on running nodes, and the Web UI's node list shows "Running: <name> · claimed N min ago · last heartbeat M min ago" (with "not responding" once the holder's lease has run out). The record is cleared whenever a node leaves `IN PROGRESS` / `IN REVIEW` -- completion, loop-back, `unstick-node`, `reopen-nodes` -- so no `TODO` node shows a holder (DFLT-00327).
  - New command `graph-engine begin-session <ticketId> [--run <runId>]` starts a processing session and prints its ID; `get-executable`, `get-ticket`, `complete-node`, `unstick-node`, `wait-node` and `add-artifact` take `--session <id>`, which refreshes the session's heartbeat (`wait-node` at most once a minute; on SQLite and MySQL a refresh within 30 seconds of the stored heartbeat writes nothing). A person's session stays live for 60 minutes after its last heartbeat; an autopilot worker's session follows its run -- live while the run is neither stopped nor finished and its heartbeat is at most 10 minutes old, so a stopped or finished run's claims expire at once -- and falls back to its own heartbeat and the 60 minutes when the run's record cannot be read. Expired claims are never released automatically. `begin-session` warns -- without stopping -- when another session is processing the ticket, naming who.
  - `unstick-node` refuses to release a node another session is still working on with `NODE_CLAIMED_BY_OTHER` (HTTP 409 from the Web UI server), naming the holder, and releases it with `--force`. Your own claims (same session, or the same autopilot run), expired claims, claims made without a session, claims whose session cannot be found and claims with no record (from an older graph-engine or an HTTP data source older than 1.2) are released, the last four with a warning (naming the holder where it is recorded). A claim on the same machine is not taken to be yours: restarting `process-ticket` in a new conversation shows the old one's claims as "(another session on this machine)".
  - `get-executable`'s output gives each node its `claim_token`, and `complete-node --claim <token>` refuses (`INVALID_NODE_STATE`, nothing written) a completion whose token no longer matches the node's claim. The token appears in no other output.
  - The `process-ticket` and `autopilot-worker` skills and the `graph-node-agent` agent begin a session and pass `--session` and `--claim`; an autopilot worker never uses `--force` and reports `blocked` on another member's live claim. A command run without `--session` records no session, so its claims are not protected.
  - This guards against mistakes between cooperating members; it is not access control. Session IDs are visible to everyone sharing the database, and passing another member's to `--session` releases their claims without `--force`. `--session` and `--claim` accept only the UUIDs graph-engine prints, and names, IDs and times written by other members are cleaned (or shown as `(invalid id)` / `(unknown time)`) before they are shown. See the README's notes, "Several members on the same tickets".
  - A session silent for more than 7 days that holds no claim is deleted by the next `begin-session` on the same ticket, at most 5 at a time.
- **An older graph-engine is stopped with `CLIENT_TOO_OLD` instead of writing to a database a newer one has migrated.** SQLite and MySQL databases now record their schema version and the oldest graph-engine allowed to read and write them, in a new one-row table `graphops_schema`. Both are schema versions, plain integers rather than release numbers; schema version 1 is graph-engine 0.11.0 and later, and covers everything 0.11.0 adds for members sharing a database (shared autopilot runs, node claims and processing sessions, atomic graph creation, conditional completions and recorded deciders, conditional ticket edits). Every command that opens the database checks the record before its start-up schema step; a graph-engine older than the record allows writes nothing, prints `Error: CLIENT_TOO_OLD: ...` asking you to update graph-engine (the GraphOps plugin), and exits non-zero. Only a newer graph-engine raises the record, one that is still allowed never lowers it, a database without a record gets one from the first 0.11.0 that opens it, and members starting at the same moment only ever leave the higher values. A Web UI server that is too old does not start; one already running notices a raised record within 30 seconds and from then on answers every request under `/api/` except `/api/health` and `/api/settings/` with HTTP 503 and `CLIENT_TOO_OLD`, including requests that do not use the database (only the health check and the settings API under `/api/settings/`, which works on the files in your home directory, still answer), the Web UI shows a banner above the ticket list asking to update graph-engine and restart the UI server, and `/graph-ops:ui`, which reuses a running server, stops with `CLIENT_TOO_OLD` and tells you to stop that server and run it again. HTTP data sources are not covered: there the plugin owns the schema, and the protocol version check (MAJOR refused, MINOR accepted) stands in for it -- the two are separate version numbers. graph-engine 0.10.x and earlier cannot be stopped this way; see Upgrade notes and the README's notes, "Several members on the same tickets: graph-engine versions" (DFLT-00331).
- **For HTTP data source plugin authors: protocol 1.2.** graph-engine now speaks HTTP data source protocol 1.2, which adds the `autopilot-runs` endpoints: `GET /projects/{projectId}/autopilot-runs`, `PUT /autopilot-runs/{runId}` and `DELETE /autopilot-runs/{runId}` -- the latter also used for other members' settled records beyond the retention (see `docs/http-datasource/README.md` and `openapi.yaml`). A plugin that reports 1.1 or 1.0 keeps working unchanged: graph-engine sends none of the new requests, judges duplicate starts from each machine's own runs only, and says once per process that other members' runs cannot be seen. The Jira sample stays at 1.1 (DFLT-00326).
  - 1.2 also adds node claims: five nullable fields on nodes (`claimed_by_name`, `claimed_by_name_is_fallback`, `claim_token`, `claim_session_id`, `claimed_at`), which graph-engine sends with every node `PATCH` that carries `status` -- values when it claims the node, all `null` otherwise -- and which a plugin stores as given, and the `processing-sessions` endpoints: `PUT`, `GET` and `DELETE /processing-sessions/{sessionId}`, `POST /processing-sessions/{sessionId}/heartbeat` (moves the heartbeat forward only) and `GET /processing-sessions?ticket_id=...` (several tickets in one request). They were added before 1.2 was released, so the version stays 1.2. Against 1.1 or 1.0 graph-engine sends and reads none of them, and nodes are handed out and released as before, with no record of who holds them; `begin-session` and `unstick-node` say so (DFLT-00327).
  - 1.2 also adds graph batch creation: `POST /tickets/{ticketId}/graph` creates a ticket's seed nodes or the rest of its graph, with their edges, in one atomic request -- only if the ticket still has the expected number of nodes (and, for an expansion, no `graph_expanded_at` yet); otherwise it writes nothing and answers 409 with the new error code `GRAPH_CHANGED`, which graph-engine absorbs. A plugin that reports 1.2 must implement it. Against 1.1 or 1.0 graph-engine keeps creating the graph one `createNode` / `createEdge` at a time, which is not atomic (see `docs/http-datasource/README.md`); the Jira sample stays at 1.1 (DFLT-00328).
  - 1.2 also adds node transitions and decisions: `POST /tickets/{ticketId}/node-transition` (`applyNodeTransition`) carries a completion, a loop-back, `reopen-nodes`, `grant-iterations` or `unstick-node` -- the artifacts, the node writes (`set_status`, `increment_iteration` and `add_max_iterations`, which add to the stored value, `touch`, `decision`) and the ticket's `set_blocked` -- together with the conditions graph-engine read (`if_status_in` / `if_status_not_in`, `if_claim_token`, `if_iteration_count`, `if_updated_at`, `require_ticket_open`, `if_blocked`), and must be applied atomically: when a condition of a required step or of the ticket does not hold, write nothing and answer 409 `INVALID_NODE_STATE`. Nodes gain four nullable decision fields (`decided_by_name`, `decided_by_name_is_fallback`, `decided_at`, `decided_by_autopilot`), written only through that endpoint and sent as `null` with every node `PATCH` that carries `status`, and a ticket `PATCH` gains `if_status` (write only if the status is still that, else 409 `TICKET_STATUS_CHANGED`). `INVALID_NODE_STATE`, `TICKET_STATUS_CHANGED` and `CONCURRENT_WRITE_CONFLICT` (optional: nothing written, the user may run the command again) join the known error codes. **`updated_at` must now become a different string on every write to a node**: store it with sub-second precision (graph-engine's own backends use RFC 3339 with nanoseconds), advance it when the clock would repeat the previous value, and compare `if_updated_at` with the stored string exactly, never as a time. A plugin that rounds to whole seconds lets a simultaneous approve and reject of a `release` or custom manual node both through. The version stays 1.2, and a plugin that reports 1.2 must implement all of this. Against 1.1 or 1.0 graph-engine sends none of it and completes, reopens, grants and unsticks with separate requests as before -- not atomic, and no decider is recorded -- and says so once per process (see `docs/http-datasource/README.md`, "Atomicity") (DFLT-00329).
  - 1.2 also adds `if_updated_at` on a ticket `PATCH`: write nothing -- `label_ids` included -- unless the ticket's stored `updated_at` is exactly that string, and answer 409 with the new error code `TICKET_CHANGED` otherwise, atomically; with `if_status` as well, write only when both hold. **A ticket's `updated_at` must now also become a different string on every write** -- `updateTicket` and the ticket writes of `createNode`, `createGraphBatch` and `applyNodeTransition` -- with the same sub-second, never-repeating rule as a node's. The version stays 1.2, and a plugin that reports 1.2 must implement both. Against 1.1 or 1.0 graph-engine never sends it: it reads the ticket, compares `updated_at` itself and sends the `PATCH` only on a match -- not atomic -- and says so once per process (DFLT-00330).

## Fixes

- **Starting the same ticket from two sessions at once no longer creates its graph twice.** When two members (or two sessions) ran `process-ticket` on the same ticket at the same moment, both could create the seed nodes (plan, plan review) on their first `get-executable`, or both could expand the graph, leaving duplicate nodes and edges that were then run twice; a failure halfway could also leave a partial graph. On SQLite, MySQL and HTTP data sources of protocol 1.2, the seed and the expansion are now each written in one transaction (one request), serialized per ticket, and a failure writes nothing. The session that loses the race creates nothing: its `get-executable` carries on with the seed that is there, and its `expand-graph` ends with the usual "ticket ...'s graph has already been expanded" error, which `process-ticket` now reads as "someone else expanded it" and continues with the existing graph. `get-executable` on a ticket that already has nodes takes no extra lock. On MySQL this transaction runs at READ COMMITTED, so a server that writes binary logs needs `binlog_format` set to `ROW` (the default since MySQL 8.0) or `MIXED`: with `STATEMENT`, MySQL refuses the creation with Error 1665, and graph-engine's error adds that cause and fix after MySQL's own message (see Upgrade notes). The database schema does not change (DFLT-00328, DFLT-00346).
- **Approve and reject of the same gate at the same moment no longer both get through, and who decided is recorded.** When two members shared a database (MySQL, a shared SQLite file or an HTTP data source) and pressed "Approve" and "Reject" on the same approval gate at once, both were accepted: the node ended with one result while the other's `rejection_reason` or loop-back was also written. On SQLite, MySQL and HTTP data sources of protocol 1.2, completing a node (`complete-node`, the Web UI's Approve / Reject) now checks the node and writes everything -- artifacts, statuses, loop-back, the ticket's blocked flag -- in one atomic step conditioned on what it read (the node's status, its claim token, and for a manual node its `updated_at`). The first decision wins; the other is refused with `INVALID_NODE_STATE` (HTTP 409 from the Web UI server, which now says another member may have decided first) and writes nothing. This applies to every manual node -- `approval_gate`, `release` and custom `is_manual` nodes -- and was checked with concurrent approve/reject tests on SQLite and MySQL. Any other write to a manual node between reading it and deciding (another member changing its assignee, say) also refuses the decision with `INVALID_NODE_STATE`; reload and decide again. See the README's notes, "Several members on the same tickets: approvals and who decided" (DFLT-00329).
  - A decision on a manual node records who made it and when: the member's `myName` (or `<OS user>@<host>`, "(name not set)"), resolved by the graph-engine that records it -- the CLI's, or the Web UI server's own settings, never a name sent by the browser. The Web UI's node list shows "Approved by <name> · <time>", "Rejected by ...", "Completed by ..." (a release or another manual node) or "Sent back by ..." (a rejection that looped back), with " (autopilot)" for an autopilot run's decision (`complete-node --session` in the run's session; the `autopilot-worker` skill now passes it). `get-ticket` shows `decided_by_name`, `decided_by_name_is_fallback`, `decided_at` and `decided_by_autopilot`. Only the latest decision is kept: it is cleared whenever the node's status changes again (loop-back, `reopen-nodes`, `unstick-node`, a new claim). A rejection of a `release` or a custom manual node that blocks the ticket leaves the node's status unchanged and records no decider; its artifacts are kept.
  - An automatic node's old worker can no longer record its verdict on a node that was rewound by a loop-back and handed out again: `complete-node --claim` is checked in the same atomic step. `complete-node` without `--claim` on a node `get-executable` handed out now warns on stderr.
  - `reopen-nodes` is conditioned on the ticket still being blocked and on each node's status and iteration count, so two at once spend one iteration, not two (the second is refused with `INVALID_NODE_STATE`); `grant-iterations` adds to the stored limit, so two at once both count; `unstick-node` releases only the claim it checked. A ticket's status is written only if it has not changed since it was read, so another member's `close-ticket` is no longer overwritten.
  - On MySQL, a deadlock between such a write and other writes to the same ticket is retried (up to three attempts, 10-50 ms apart); if it persists the command fails with the new `CONCURRENT_WRITE_CONFLICT` (HTTP 409) and writes nothing, and can simply be run again. A protocol 1.2 HTTP plugin may return the same code. `TICKET_STATUS_CHANGED` (HTTP 409) is the other new code, for a ticket status write whose condition no longer held.
- **Two members editing the same ticket no longer silently overwrite each other.** `refine-ticket` rebuilds a ticket's whole description from what `get-ticket` returned, so when two members (or sessions) refined or updated the same ticket, the one who wrote last erased the other's change without a word; the same held for the Web UI's label changes, which replace the whole label set from what the page showed. `update-ticket` and `refine-ticket` now take `--if-updated-at <updated_at>` (the value `get-ticket` printed): if the ticket has been written since, the command fails with the new error code `TICKET_CHANGED` and nothing changes -- a refused `refine-ticket` does not mark the ticket `REFINED` either. What they show when there is nothing to load (no project for the Autopilot or Labels tab, an empty or failed list in Node Types or Skills) is unchanged. (2) When the app settings could not be loaded, the tab showed its form filled with defaults, and saving it would overwrite the stored settings with them. It now shows the error and a Retry button instead of the form; a successful retry shows the form and moves keyboard focus to it, and a failed one keeps focus on the button. (3) The app settings tab's loading line is now a status message (role="status"), so screen readers can tell the settings are loading (WCAG 4.1.3) (DFLT-00343).
- **Commands started at the same moment on a SQLite database file that does not exist yet no longer fail with "database is locked".** Each graph-engine that opens a new SQLite file switches it to WAL mode, and when several did so at once -- for example parallel commands on first use, or `GRAPH_DB_PATH` pointing at a new file -- the ones that lost the race failed straight away with `database is locked (5) (SQLITE_BUSY)`; the 5-second busy timeout does not apply to that step. graph-engine now retries opening the connection while it gets `SQLITE_BUSY`, for up to 5 seconds, and returns any other error at once. In a test of 6 processes starting together on a new file, 40 times, failures went from 17 of 240 to none. An existing file, already in WAL mode, was never affected, and the database settings (WAL mode, foreign keys, the busy timeout, immediate transactions) are unchanged (DFLT-00354).

## Upgrade notes

- The database schema gains one table, `autopilot_runs` (SQLite and MySQL). It is created by graph-engine's usual start-up schema step; existing data is not touched (DFLT-00326).
- If several members share one database, update everyone's graph-engine at the same time: an older graph-engine neither records its autopilot runs in the database nor looks at the ones recorded there, so a member still on it can start a tree someone else is running, and the other way round (DFLT-00326).
- The database schema gains five nullable columns on `nodes` -- `claimed_by_name`, `claimed_by_name_is_fallback`, `claim_token`, `claim_session_id`, `claimed_at` -- and one table, `processing_sessions` (SQLite and MySQL). Both are added by graph-engine's usual start-up schema step; existing data is not touched (DFLT-00327).
- If several members share one database, update everyone's graph-engine at the same time for this too: an older graph-engine neither records nor clears node claims, so while versions are mixed a node can show a stale holder, and its claims are not protected (DFLT-00327).
- **API change: `PATCH /api/nodes/{id}` no longer accepts `status`.** The Web UI server now answers `400 VALIDATION_ERROR` to a node patch that sets `status`, as it already did for `name`, `type` and `iteration_count`; change a node's status with `complete-node`, `get-executable` or `unstick-node`, which keep its claim record consistent. The Web UI itself never sent it; the other fields (`max_iterations`, `assignee`, `is_manual`) are unchanged (DFLT-00327).
- The database schema gains four nullable columns on `nodes` -- `decided_by_name`, `decided_by_name_is_fallback`, `decided_at`, `decided_by_autopilot` (SQLite and MySQL). They are added by graph-engine's usual start-up schema step, which tolerates two members starting at once; existing nodes read as "not decided" (DFLT-00329).
- If several members share one database, update everyone's graph-engine at the same time for this too: an older graph-engine completes nodes without the new conditions and neither records nor clears a decider, so while versions are mixed an approve and a reject can still both get through and a stale decider can be shown (DFLT-00329).
- **HTTP data source plugins that report 1.2 must implement `applyNodeTransition`, `if_status` and `if_updated_at`, and change `updated_at` to a new sub-second string on every node and ticket write** (`if_updated_at` and the ticket rule: DFLT-00330) (see the plugin-author item under Changes). A 1.2 plugin without the endpoint makes `complete-node` fail rather than fall back (DFLT-00329).
- The database schema gains one table, `graphops_schema` (SQLite and MySQL), which records the database's schema version and the oldest graph-engine allowed to use it. It is created and filled by graph-engine's usual start-up schema step; existing data is not touched (DFLT-00331).
- If several members share one database, update everyone's graph-engine at the same time for this too -- here it cannot be enforced: graph-engine 0.10.x and earlier does not read the new record, so it is not stopped with `CLIENT_TOO_OLD` and keeps writing to a database 0.11.0 has migrated, and so does a member who goes back to 0.10.x after updating. Only versions from 0.11.0 on are stopped when they fall behind the database. Restart any UI server started before the update, too (see "Updating to a new release" in the README) (DFLT-00331).
- **MySQL: a server that writes binary logs must not use `binlog_format=STATEMENT`.** 0.11.0 creates a ticket's graph (the seed on the first `get-executable`, and `expand-graph`) in a READ COMMITTED transaction on MySQL, which such a server refuses with Error 1665, so those commands fail there. Before upgrading, check with `SELECT @@global.binlog_format, @@global.log_bin;` and, if `log_bin` is `ON` and `binlog_format` is `STATEMENT`, set it to `ROW` (the default since MySQL 8.0) or `MIXED`. A server without binary logging, or already on `ROW` or `MIXED`, needs nothing. Existing tickets, their graphs and other data are not affected, and a refused creation is rolled back and writes nothing (DFLT-00328, DFLT-00346).
- The Web UI now needs Safari 16.4+, Chrome 111+ or Firefox 128+ (Tailwind CSS v4). In older browsers its layout and colors break.
