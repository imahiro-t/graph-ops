## Changes

- **"Select all" in the ticket-list filters.** Each of the four filters of the Web UI's ticket list (status, assignee, priority, label) now has a "Select all" button next to "Clear selection" at the bottom of its panel. It checks every option of that filter in the order the panel lists them, including the assignee filter's "Unassigned", keeps any selected value that is no longer offered as an option (such as an assignee who disappeared on a refresh), and leaves the panel open, so you can uncheck the few options you do not want -- for example, show every status except Done and Closed. The button is disabled when every option is already checked or the filter has no options; focus stays in the panel when it becomes disabled, so Escape still closes the panel.
  - With every option checked, the filter still reads "n selected", not "All". Checking everything is not always the same as no filtering: the label filter matches tickets that have any of the selected labels, so it hides tickets that have no label at all, and an assignee who appears on a later refresh is not included. For status, priority and assignee, checking every option shows the same tickets as selecting none.
- **Screen readers hear what "Select all" and "Clear selection" did.** In each of the ticket-list filters, pressing "Select all" now announces "All options selected (n)" and pressing "Clear selection" announces "Selection cleared" (in Japanese: "n 件すべてを選択しました" / "選択を解除しました") through a polite live region. Before, only the control that received focus was read out -- the first checkbox or the filter button -- so it was not clear that the whole selection had changed. n is the number of options in the panel (DFLT-00267).
- **For contributors: a new worktree without `npm ci` fails fast.** In a checkout where dependencies are not installed (typically a fresh git worktree), `npm run lint`, `npm test` and `npm run build` in `packages/web` now stop at once with a message telling you to run `npm ci` in the checkout's root, instead of picking up the parent repository's tools and failing with `ERR_MODULE_NOT_FOUND` for `@eslint/js` (or hanging in vitest). The README's Troubleshooting section describes it (DFLT-00267).
- **For contributors: the Node.js version needed for development is declared and checked.** Developing GraphOps needs Node.js 24 or later, the version CI uses; it is now declared as `engines.node` in `package.json` and `packages/web/package.json` and in a new `.nvmrc`. On an older Node.js (such as 20.10), `npm run lint`, `npm test` and `npm run build` in `packages/web` stop before starting eslint, vitest or tsc, with a message showing the required and the current version and how to switch, instead of failing with dozens of fake-timer timeouts. Contributors who used Node.js 22 need to switch to 24. What you need to run the plugin itself is unchanged. The README's Troubleshooting section describes it (DFLT-00273). `npm run dev` and `npm run test:watch` in `packages/web` now run the same checks first (Node.js version, then dependencies), so they no longer start vite or vitest on an older Node.js or in a worktree without `npm ci`; the root `npm run dev:web` and `npm run dev` stop the Web UI side with the same message, while `npm run dev`'s Go server side keeps running (DFLT-00289).
- **Web UI dependencies updated: React 19, Vite 8 and Tailwind CSS v4.** The Web UI now builds with React 19, Vite 8 (with `@vitejs/plugin-react` 6) and Tailwind CSS 4, replacing Dependabot's separate major-update pull requests, which could not pass CI on their own. The UI is meant to look and work as before: Tailwind v3's colors, breakpoints, line heights and default font are kept, and so are its spacing between stacked items, its default border and placeholder colors, the pointer cursor on buttons and the browser's own form-field styling; a few shadows, rounded corners and the blur behind dialogs that v3 never drew (their class names did not exist in v3) stay undrawn. Tailwind is now configured in `packages/web/src/index.css` through `@tailwindcss/vite`; `tailwind.config.js` and `postcss.config.js` are gone. One small difference: on a touch-only device, `hover:` styles no longer stick after a tap. Building the Web UI from source needs Node.js 24 or later, the version CI uses (see the item above).
- **The Web UI's JavaScript is split into smaller files.** The Web UI used to ship as one 765 kB JavaScript file, and every build warned that it was over Vite's 500 kB limit. React is now in its own file and the other libraries in another (about 220 kB each), next to the app's own code (about 320 kB), so the build no longer warns and the browser can keep the rarely changing React file cached across releases. The UI looks and works as before (DFLT-00275).
- **For contributors: Web UI tests tolerate a heavily loaded machine.** `packages/web`'s Vitest time limit per test and per hook is now 30 seconds instead of 5. With a load average above 200 (for example while several autopilot reviews run at once), 40-56 async UI tests used to fail on the 5-second limit and pass again once the load dropped. A passing test takes as long as before; only a test that really hangs is reported up to 30 seconds later (DFLT-00275).
- **For contributors: `App.labels.test.tsx` and `App.family.test.tsx` no longer depend on which request the fake backend answers first.** Several of their steps checked something right after the first ticket appeared that comes from a different request -- the label filter's options (`GET /api/projects/{id}/labels`), the project list in the settings modal and the project switcher (`GET /api/projects`), and the page size (`GET /api/settings/app`) -- so they failed whenever that answer landed later. They now wait for the checkbox, option, button or page count they are about to use. With the fake backend's answers delayed at random, the two files failed in 9 of 20 runs before and in none of 42 runs after (DFLT-00284).
- **For contributors: `packages/web`'s Vite and Vitest config files are type-checked.** `npm run build` in `packages/web` now also runs `tsc -p tsconfig.node.json`, which type-checks `vite.config.ts` and `vitest.config.ts`, so a type error in either config file fails the build (and CI) instead of going unnoticed; the app's own `tsconfig.json` still covers only `src/`. `vitest.config.ts` now imports `defineConfig` / `mergeConfig` from `vitest/config`, so its `test` block is typed, and imports `./vite.config.ts` with its extension, so `vitest` no longer prints Vite's warning about an import without a file extension (DFLT-00291).
- **For contributors: the rest of the `App.*.test.tsx` files no longer depend on which request the fake backend answers first either.** Following DFLT-00284, all 16 `packages/web/src/App.*.test.tsx` files were run with the fake backend's answers delayed at random (0-30, 0-100 and 0-300 ms), and every step that checked something right after the first ticket appeared although it comes from a different request now waits for it: the label filter's options in `App.filters.test.tsx` (`GET /api/projects/{id}/labels`), the pager wherever a test sets a page size (`GET /api/settings/app`, in `App.filters`, `App.headerNarrowReflow`, `App.largeTextReflow` and `App.ticketDelete`), the project switcher's items and pending-approval badges (`GET /api/projects`, `GET /api/projects/pending-approvals`, in `App.largeTextReflow`, `App.pendingApprovals`, `App.projectSwitcher.a11y` and `App.project`), the settings modal's app-settings form (`App.project`), and the autopilot runs (`GET /api/autopilot/runs`, in `App.autopilot`). In `App.autopilot`, a test whose poll changed both a ticket's status and its runs now changes them in separate polls (their answers are separate requests too), and the tests where a poll closes the confirmation dialog wait for focus to come back. Waiting until the app has read a given answer's body is now one shared helper, `trackBodyReads` in `packages/web/src/test/waitForAnswers.ts`, instead of a copy per test file. With 0-100 ms delays the 16 files had 3-9 failing tests in each of 10 runs before and none in 10 runs after (DFLT-00296).
- **The Web UI supports windows down to 320 CSS px with text up to 200%.** The Web UI's supported range is now a window 320 CSS px wide with the browser's text at up to 200% (a 32px default font), the size WCAG 1.4.10 Reflow asks for. Adjustments that only took effect in narrower windows or with larger text were removed: the icon-only header and its touch long-press tooltips in a window of 200 CSS px or less, the smaller padding and extra wrapping of the page, the expanded ticket, its node rows, its Markdown lists and the untrusted-folder notice at 200 CSS px or less and from 7.5rem down, and the two-line items of the project switcher's popup below 8rem. Earlier release notes, including v0.10.0's, describe some fixes as measured in a 160px window; the parts of those fixes that still apply at 320px with 200% text stay, and anything narrower or larger is now out of scope and may scroll sideways or be cut off. At 320px and wider, with text up to 200%, the Web UI looks and works as before. For contributors: the `upto-200px:`, `upto-7_5rem:` and `cq-below-8rem:` Tailwind variants, `IconButton`'s `longPressTooltip` and `title` options, the `useMediaQuery` hook and the `touchLongPress` test helper are gone, and the Web UI's tests use windows of 320px or wider with a root font of at most 32px (DFLT-00319).
- **Autopilot drops open items not worth a ticket instead of filing them all in the backlog.** When an autopilot run hands off a ticket's open items, it used to sort them only as in scope (child tickets) or out of scope (one backlog ticket), so every review note ended up in a backlog ticket and each run left 4-6 more items behind. A third kind, **Drop**, is now checked first: an item that only happens outside the project's supported range (as the project states it, for example through the `autopilot-worker` skill's extension, its settings or its README/docs; not used when no range is stated), a wording or style difference with no real effect, a check that needs a real device or environment with no defect found, a problem that has not been reproduced or observed, or a risk or trade-off the plan or a review explicitly accepted. A dropped item gets no ticket: the `autopilot-decision-handoff` artifact keeps its kind and its Drop reason (the criterion it matched, or "no reason worth working on"), and the run's summary only gives the number of dropped items. Each item that does go into a backlog ticket now carries one line on why it is worth working on, and an item without one is dropped with the reason "no reason worth working on". With `autoCreateTickets` off, the list shown to you includes the dropped items with their kind and reason, and one you pick still goes into the backlog ticket. (DFLT-00324)
- **Autopilot runs are shared between members, so two members can no longer start the same tree.** On a database several members share -- MySQL, a shared SQLite file, or an HTTP data source of protocol 1.2 -- every autopilot run is now also kept in the database, and `graph-engine autopilot start` and the Web UI's launch refuse a start that overlaps another member's active run with `AUTOPILOT_ALREADY_RUNNING`. The error names who started that run (`started_by` in `details`, and in the message), and the Web UI shows another member's run as "<name> is running" and names them when it disables the "Autopilot" button; `GET /api/autopilot/runs` returns other members' runs with `started_by` and `mine`. On MySQL and SQLite two overlapping starts at the same moment never both pass. Another member's run stops blocking you once its heartbeat is more than 10 minutes old; nothing rewrites its state. A stopped or interrupted run is resumed only on the machine that started it: another member's neither blocks nor is taken over (your start creates a new run). What only means something on the running machine -- the terminal, worktree paths, branch names -- stays in the local run file, which remains each machine's source of truth. Git branches are still not shared: reflect finished work with `mainReflection` `pull_request` or `merge`, and update your local default branch before starting (docs/autopilot.md, "Runs shared between members") (DFLT-00326).
  - Each machine now has an ID, kept in `$HOME/.graph-ops/machine-id` and created the first time it is needed. Deleting it makes your interrupted runs impossible to resume; a copied home directory gives two machines the same ID. A machine-id file that is not a valid ID is never replaced silently: starts fail with `AUTOPILOT_MACHINE_ID_UNREADABLE` (the Web UI says which file to restore or delete) until you restore or delete it.
  - A run that comes back after its heartbeat expired -- the orchestrator's machine slept, say -- while another member started an overlapping run stops itself with the reason `overtaken` before its next launch, so the two do not go on side by side. A child session it had already launched keeps running until it reports; keep the machine awake during a run on a shared database.
  - The database keeps at most 20 settled runs (finished, stopped or expired) per project; older ones are deleted when a run starts, whoever started them. Run files on each machine are not affected.
  - The name shown for a member is their `myName` (App Settings), or `<OS user>@<host>` marked "(name not set)" when it is empty.
    - The name is cleaned before it is recorded and again before it is shown on any machine: tabs and line breaks become a space, other control characters (including ESC, so no terminal escape sequences) and all invisible format characters (Unicode category Cf: bidirectional controls, zero-width characters including ZWNJ and ZWJ, the BOM, ...) are removed, and the name is cut to 128 characters. Names written by an earlier version or straight into the database are cleaned when read. A name left empty is treated as unknown. Ordinary names are unchanged; an emoji joined with ZWJ shows as its separate emoji, and a name that spells with ZWNJ loses it (DFLT-00336).
- **For HTTP data source plugin authors: protocol 1.2.** graph-engine now speaks HTTP data source protocol 1.2, which adds the `autopilot-runs` endpoints: `GET /projects/{projectId}/autopilot-runs`, `PUT /autopilot-runs/{runId}` and `DELETE /autopilot-runs/{runId}` -- the latter also used for other members' settled records beyond the retention (see `docs/http-datasource/README.md` and `openapi.yaml`). A plugin that reports 1.1 or 1.0 keeps working unchanged: graph-engine sends none of the new requests, judges duplicate starts from each machine's own runs only, and says once per process that other members' runs cannot be seen. The Jira sample stays at 1.1 (DFLT-00326).

The tooltip stays closed while the popup is open, so one Escape still closes the popup. At the default text size the header, the popup and its items look exactly as before from 272px up (DFLT-00285).
- **The rest of the Web UI's small text grows with the browser's text size.** Small text that was still fixed at 9-11px now follows the browser's default text size (WCAG 1.4.4), as the ticket cards and the settings editors do since DFLT-00281 and DFLT-00287: the project prefix in the project switcher and its pending-approval count, label chips and the Edit labels button and its error, the Feature / Scenario tags in the Gherkin view, code and tables in Markdown artifacts, the notes and errors in the new-ticket and project-setup dialogs, the tooltips of icon buttons, the artifact names and links in the autopilot decisions, the parent/child badges of a ticket, and the "Default" badge in the Node Types list. At the default 16px they are exactly the same size as before. For contributors: no non-test source file under `packages/web/src` has a `text-[..px]` size outside comments any more (a test keeps it that way), and the last arbitrary at-rule prefixes are now named variants in `packages/web/src/index.css` with the same conditions: `[@container(max-width:12rem)]:` and `[@container(min-width:16rem)]:` are `cq-upto-12rem:` and `cq-from-16rem:`. They are declared after the other named variants, in the order the arbitrary prefixes were emitted, so the generated CSS keeps the same order and nothing renders differently; the comment next to their definition and `tailwindVariants.test.ts` pin the order down (DFLT-00294).
- **A missing `/assets/...` file now gets a 404 from the built-in Web UI server.** `graph-engine serve` answered a request for a file under `/assets/` that is not in the build with the Web UI's `index.html` and a 200. A page left open across an upgrade that then loaded one of its old, now removed, JavaScript files therefore failed with a confusing MIME-type error in the browser; it now gets a plain 404, which says what happened. Any other unknown path (such as `/artifacts/{id}/preview`) still opens the Web UI as before (DFLT-00291).
- **The label picker stays inside the ticket card with large text, and New Ticket explains why it is disabled to screen readers.** (1) The label picker opened by "Edit labels" in an expanded ticket was 14rem wide whatever the space, so with 200% text in a 320px window (where 14rem is 448px) most of it was cut off by the ticket card. It now stays inside the card and the window: it lines up with the button as before, moves left when it would end past the card, and when even that leaves less than 14rem it becomes narrower, its rows wrap and long label names are shown in full instead of being shortened with an ellipsis, so every label can be read and checked. Where 14rem fits, the picker looks as before; where it used to run past the card's right edge (for example at 320px, or at 1024px in English, at the default text size) it now moves left to stay inside, at the same width. (2) Without a project, screen readers now get the reason the New Ticket button is disabled alone as its description; the button's `title` still shows it on mouse hover. For contributors: the label picker's narrow layout is switched by a `data-narrow` attribute through `group-data-narrow:`, and `fitPopupHorizontally` in `packages/web/src/lib/popupPlacement.ts` takes optional left and right bounds (DFLT-00293).
- **Overlapping label reloads no longer bring back an older label list.** The Web UI re-reads the current project's labels after every ticket-list fetch (the 15-second poll, the refresh button, an edit) and after a change in the settings modal's labels tab, so two reads can be in flight at once. If the older one answered last, its list replaced the newer one -- a label just renamed or deleted could come back in the label filter and the label picker until the next poll. Only the latest read's answer is applied now, as the ticket list already did (DFLT-00296).
- **An expanded ticket's pulsing dots stop when you ask for less motion.** The pulsing dots of an IN PROGRESS node and of an approval waiting for you (in a node row and in the ticket header) no longer pulse when the system asks for reduced motion (prefers-reduced-motion, WCAG 2.3.3) (DFLT-00290).

## Upgrade notes

- The database schema gains one table, `autopilot_runs` (SQLite and MySQL). It is created by graph-engine's usual start-up schema step; existing data is not touched (DFLT-00326).
- If several members share one database, update everyone's graph-engine at the same time: an older graph-engine neither records its autopilot runs in the database nor looks at the ones recorded there, so a member still on it can start a tree someone else is running, and the other way round (DFLT-00326).
- The Web UI now needs Safari 16.4+, Chrome 111+ or Firefox 128+ (Tailwind CSS v4). In older browsers its layout and colors break.
