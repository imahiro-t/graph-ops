## Changes

- **"Select all" in the ticket-list filters.** Each of the four filters of the Web UI's ticket list (status, assignee, priority, label) now has a "Select all" button next to "Clear selection" at the bottom of its panel. It checks every option of that filter in the order the panel lists them, including the assignee filter's "Unassigned", keeps any selected value that is no longer offered as an option (such as an assignee who disappeared on a refresh), and leaves the panel open, so you can uncheck the few options you do not want -- for example, show every status except Done and Closed. The button is disabled when every option is already checked or the filter has no options; focus stays in the panel when it becomes disabled, so Escape still closes the panel.
  - With every option checked, the filter still reads "n selected", not "All". Checking everything is not always the same as no filtering: the label filter matches tickets that have any of the selected labels, so it hides tickets that have no label at all, and an assignee who appears on a later refresh is not included. For status, priority and assignee, checking every option shows the same tickets as selecting none.
- **Screen readers hear what "Select all" and "Clear selection" did.** In each of the ticket-list filters, pressing "Select all" now announces "All options selected (n)" and pressing "Clear selection" announces "Selection cleared" (in Japanese: "n 件すべてを選択しました" / "選択を解除しました") through a polite live region. Before, only the control that received focus was read out -- the first checkbox or the filter button -- so it was not clear that the whole selection had changed. n is the number of options in the panel (DFLT-00267).
- **For contributors: a new worktree without `npm ci` fails fast.** In a checkout where dependencies are not installed (typically a fresh git worktree), `npm run lint`, `npm test` and `npm run build` in `packages/web` now stop at once with a message telling you to run `npm ci` in the checkout's root, instead of picking up the parent repository's tools and failing with `ERR_MODULE_NOT_FOUND` for `@eslint/js` (or hanging in vitest). The README's Troubleshooting section describes it (DFLT-00267).
- **For contributors: the Node.js version needed for development is declared and checked.** Developing GraphOps needs Node.js 24 or later, the version CI uses; it is now declared as `engines.node` in `package.json` and `packages/web/package.json` and in a new `.nvmrc`. On an older Node.js (such as 20.10), `npm run lint`, `npm test` and `npm run build` in `packages/web` stop before starting eslint, vitest or tsc, with a message showing the required and the current version and how to switch, instead of failing with dozens of fake-timer timeouts. Contributors who used Node.js 22 need to switch to 24. What you need to run the plugin itself is unchanged. The README's Troubleshooting section describes it (DFLT-00273). `npm run dev` and `npm run test:watch` in `packages/web` now run the same checks first (Node.js version, then dependencies), so they no longer start vite or vitest on an older Node.js or in a worktree without `npm ci`; the root `npm run dev:web` and `npm run dev` stop the Web UI side with the same message, while `npm run dev`'s Go server side keeps running (DFLT-00289).
- **Web UI dependencies updated: React 19, Vite 8 and Tailwind CSS v4.** The Web UI now builds with React 19, Vite 8 (with `@vitejs/plugin-react` 6) and Tailwind CSS 4, replacing Dependabot's separate major-update pull requests, which could not pass CI on their own. The UI is meant to look and work as before: Tailwind v3's colors, breakpoints, line heights and default font are kept, and so are its spacing between stacked items, its default border and placeholder colors, the pointer cursor on buttons and the browser's own form-field styling; a few shadows, rounded corners and the blur behind dialogs that v3 never drew (their class names did not exist in v3) stay undrawn. Tailwind is now configured in `packages/web/src/index.css` through `@tailwindcss/vite`; `tailwind.config.js` and `postcss.config.js` are gone. One small difference: on a touch-only device, `hover:` styles no longer stick after a tap. Building the Web UI from source needs Node.js 24 or later, the version CI uses (see the item above).
- **The Web UI's JavaScript is split into smaller files.** The Web UI used to ship as one 765 kB JavaScript file, and every build warned that it was over Vite's 500 kB limit. React is now in its own file and the other libraries in another (about 220 kB each), next to the app's own code (about 320 kB), so the build no longer warns and the browser can keep the rarely changing React file cached across releases. The UI looks and works as before (DFLT-00275).
- **For contributors: Web UI tests tolerate a heavily loaded machine.** `packages/web`'s Vitest time limit per test and per hook is now 30 seconds instead of 5. With a load average above 200 (for example while several autopilot reviews run at once), 40-56 async UI tests used to fail on the 5-second limit and pass again once the load dropped. A passing test takes as long as before; only a test that really hangs is reported up to 30 seconds later (DFLT-00275).
- **For contributors: `App.labels.test.tsx` and `App.family.test.tsx` no longer depend on which request the fake backend answers first.** Several of their steps checked something right after the first ticket appeared that comes from a different request -- the label filter's options (`GET /api/projects/{id}/labels`), the project list in the settings modal and the project switcher (`GET /api/projects`), and the page size (`GET /api/settings/app`) -- so they failed whenever that answer landed later. They now wait for the checkbox, option, button or page count they are about to use. With the fake backend's answers delayed at random, the two files failed in 9 of 20 runs before and in none of 42 runs after (DFLT-00284).

## Fixes

- **The ticket list page reads and works better with very large text.** Five leftovers of the v0.10.0 reflow fixes (DFLT-00251) are fixed. (1) In English on a 320-336px screen with the page's text at 200%, the note "(Click to expand and view the graph and each node's artifacts)" in the summary above the list ran past the summary card; the heading now moves the note under the title and breaks it inside a word when the card is narrower than 12rem, following the text size however it is set. (2) At 1024px and wider with 200% text the header, pinned to the top of the window, grew to about 530px and covered the buttons of the ticket header rows as they scrolled under it (WCAG 2.4.11); the header is now pinned only while it takes at most a quarter of the window's height or is at most 128px tall (as it is at the default text size), and otherwise scrolls away with the page as it does on narrower screens. (3) In a 160px-wide window (a 320px screen at 200% zoom) with a three-digit page number ("100 / 123"), the page-navigation buttons ended 9px past their row; they now sit closer together there. (4) The labels under the summary's numbers ("Total Tickets", "In Progress", "In Review", "Done", "Node Progress") grow with the browser's text size (still 11px at the default size). (5) The summary's node progress breaks only after the slash, never inside a number, up to five digits ("99997/" / "99999"). At the default text size, 320px and wider, the page looks exactly as before, and the header is pinned from `lg` up as before, however low the window (DFLT-00258).
- **Focused elements and opened tickets no longer hide under the pinned header in a low window.** At the default text size the Web UI's header stays pinned to the top of the window from `lg` (1024px) up however low the window is, and at 114px it covered much of a low window (1280x400, say, or a laptop with the developer tools docked below). An element focused with Tab near the top of the window, and the top of a ticket's card opened from a parent/child link, could end up under it (WCAG 2.4.11). While the header is pinned, the page now keeps a scroll padding of the header's height at the top, so the browser scrolls them into view below the header; when the header is not pinned (below `lg`, or with large text) nothing changes. Checked in Chrome, Firefox and Safari's engine (DFLT-00268).
- **A long project name no longer widens the page with large text.** The project switcher in the header kept its full width (up to 14rem) however narrow the header was, so with 200% text on a 320px screen a long project name made the page scroll sideways, and in a 160px window with a 32px root font even "Graph Ops" widened the page to 283px. The name now truncates within the header's width. At the default text size the header looks exactly as before. Together with the header and pagination wrapping below (DFLT-00259), the ticket list page now fits a 160px window with a 32px root font in English and Japanese, with or without pagination (DFLT-00268, DFLT-00278).
- **The whole focus ring now shows below the pinned header.** The scroll padding kept at the top while the header is pinned (DFLT-00268) was exactly the header's height, so in Safari (Option+Tab) a focused button could stop right at the header's bottom edge with the top 2-3px of its focus ring hidden under the header. The padding is now the header's height plus 0.5rem (8px at the default text size, growing with the root font size), so the focused element, its focus ring, and the top of a ticket's card opened from a parent/child link stop a little below the header. When the header is not pinned nothing changes, and page layout is the same as before at every width. Checked in Chrome, Firefox and Safari's engine (DFLT-00278).
- **Autopilot child sessions open in a Terminal.app tab more reliably.** When the autopilot opens a child session as a new tab of the orchestrator's Terminal.app window, it now waits 0.2 seconds after seeing the window in front before sending Cmd+T (it used to send it right away), and waits up to about 6 seconds for the new tab, checking every 0.2 seconds (it used to give up after about 3 seconds and open a new window instead). To make room for the longer wait, the time limit on `osascript` goes from 10 to 15 seconds and the wait for the tab lock from 15 to 20 seconds, so a launch can now take about 45 seconds at worst instead of about 35 (DFLT-00269).
- **Node rows in a ticket's node list keep their badges apart, stay inside the card in a very narrow window, and grow with the browser's text size.** Leftovers of the v0.10.0 node-row fixes (DFLT-00253) are fixed. (1) At 1280px and wider, in a row whose node name is shortened with an ellipsis, the last badge (usually the artifact count) touched the status badge with no space between them; there is now always at least 4px (0.25rem) between them. A row with that much room to spare looks exactly as before; a row that had less than 4px to spare shortens its name by up to 4px more. (2) In a 160px-wide window (a 320px screen at 200% zoom), the retry, manual and artifact-count badges ran 3-26px past the node card, and in English the status badge ran up to 29px past it; these badges now wrap onto more lines below 1280px (80rem) instead, and stay on one line at 1280px and wider. (3) The node-type, status, retry, manual and artifact-count badges now grow with the browser's default text size (they were fixed at 10-11px, WCAG 1.4.4); at the default 16px they are exactly the same size as before. With 200% text on a 320-336px screen they stay inside the card. For contributors: the rem media-query prefixes `[@media_not_all_and_(min-width:80rem)]:` and `[@media(max-width:15rem)]:` are now the named Tailwind variants `below-80rem:` and `upto-15rem:` (`@custom-variant` in `packages/web/src/index.css`), with the same media conditions and the same place in the CSS. When both set the same property on an element the narrower `upto-15rem:` wins, and both win over core screen variants such as `max-sm:`; the comment next to their definition explains the order (DFLT-00260).
- **The ticket list page no longer scrolls sideways in a 160px window with 200% text, the instruction box's border turns indigo on focus in dark mode, and the untrusted-folder notice's dismiss button stays inside the notice in a very narrow window.** In a 160px-wide window with a 200% text size the page was 283px wide: the top header (the GraphOps name, the project switcher, the Launch Claude button, the update time and the other header buttons) and the pagination buttons kept the width of their longest words. They now wrap, and break inside a word only as a last resort, so the page fits the window; the pagination buttons may stack right-aligned in reading order, and the summary card's node progress and figure labels may break inside a number or word in a window of 200 CSS px or less. Wherever the header and the pagination fitted before, including 320-336px at 200% and every width above 200 CSS px at the default text size, they look as before. In dark mode the instruction box under an expanded ticket kept its slate border when focused; it now turns indigo as in light mode. In a window of 200 CSS px or less, at any text size, the top header and its buttons also use smaller padding (a button may put its label under its icon), and the expanded details, the Action Footer, the untrusted-folder notice and its dismiss button use smaller padding, so the button (and its label) no longer run past the notice's right edge (DFLT-00259).
- **The ticket description's expand button keeps one label, and a short description adds no extra tab stop.** In an expanded ticket's description card, the button that opens the whole text (which already tells screen readers whether the text is open, with aria-expanded, and which part of the page it opens, DFLT-00262) now always reads "Full text" (in Japanese: "全文") instead of switching between "Show all" and "Collapse", so screen readers no longer announce the open/closed state twice; a small chevron next to the label points down while the text is collapsed and up while it is open. While collapsed, the description body -- which DFLT-00262 made a named region you can reach with Tab and scroll with the keyboard -- is that region and tab stop only when its text is longer than the card's collapsed height, and it follows window resizes and text changes; a description that fits adds neither (DFLT-00272).
- **An expanded ticket's creation date, labels and closed reason stay inside the card in a 160px window with 200% text, and the search box's border turns blue on focus in dark mode.** In a 160px-wide window with a 200% text size, the creation date in an expanded ticket's metadata bar ran past the card's right edge and was cut off; in English the Edit labels button did too, and a long label or a closed reason made of one long word also ran past the card (at 320px with 200% text as well). They now wrap, breaking inside a word (so a date may break in the middle of a number) only when a word cannot fit on a line; a closed reason that does not fit beside its label moves onto the line below, so the label itself is never broken mid-word, and a long label name truncates inside the card. Only the values break inside a word: the labels ("Created:", "Closed reason:", "Labels:") never break inside a word or just before their colon (a word wider than the bar, such as "Created:" at 160px with 200% text, uses the card's padding instead), and the Edit labels button wraps between words ("Edit / labels", "ラベルを / 編集"), breaking inside a word only when that one word is wider than the card. A label save error breaks inside a word when needed and moves below the button instead of squeezing it. Wherever they fitted before they look as before. In dark mode the toolbar's search box kept its slate border when focused; it now turns blue like the other inputs, and the light theme is unchanged (DFLT-00276, DFLT-00292).
- **The rest of an expanded ticket's small text grows with the browser's text size.** Text in an expanded ticket that was still fixed at 10-11px now follows the browser's default text size (WCAG 1.4.4), as the node-row badges do since DFLT-00260: the Approve and Reject buttons of an approval node, the rejection-reason field and its buttons, the approval error under a node row, each node's update time, the creation time shown on each Gherkin artifact in the Gherkin tab, the note shown when a node has no artifacts, the "Open in new tab" and download links and the artifact-type labels in the artifact panels, an artifact's text preview, the graph's progress percentage, its parallel-execution hint and its legend, and the status message at the bottom of the card. At the default 16px they are exactly the same size as before. For contributors: `TicketItem.tsx` no longer has any `text-[..px]` size (a test keeps it that way), and the manual badge's `py-0.2`, which Tailwind never generated any CSS for, is gone, so the badge looks as before. The remaining rem media-query prefixes `[@media(min-width:80rem)]:`, `[@media(min-width:64rem)]:` and `[@media_not_all_and_(min-width:64rem)]:` are now the named variants `from-80rem:`, `from-64rem:` and `below-64rem:` in `packages/web/src/index.css`, with the same media conditions. As named variants they are emitted before every arbitrary variant, so their order relative to some arbitrary variants has changed: all three now come before `[@container(...)]:`, and `from-64rem:` and `from-80rem:` now also come before `[@media(max-width:200px)]:` (`below-64rem:` already did). Where such a pair sets the same property on an element, the arbitrary variant now wins; no element currently combines them that way, so nothing renders differently. The comment next to their definition and `tailwindVariants.test.ts` pin down the order (DFLT-00281).
