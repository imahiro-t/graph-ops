## Highlights

- **A failed review now rewinds the work in between, not just the loop target.** When a `review`/`review_gate` node fails and loops back, the engine used to change only two nodes: the loop target went back to `TODO` and the failing reviewer went to `AWAITING FIX`. Everything between them stayed `DONE`. In the default implementation+Gherkin shape (`test_review` looping back to `impl`) that had two consequences: `test_review` was handed out again in the very same `get-executable` call that reset `impl`, so the *previous* test run was judged a second time before the rework existed, and `code_review`, `qa_review`, `security_review`, `non_functional_review` and `gherkin_test` were never re-run at all -- an implementation that had never been tested or reviewed could reach `report` and `release_approval`. A loop-back now also resets every `DONE` node on a `success`-edge path from the loop target to the failing node, so `get-executable` offers the loop target first, then the rewound reviewers and tests, and only then the `AWAITING FIX` node. Nothing downstream of the failing node, and nothing upstream of the loop target, is touched.
- **`graph-engine grant-iterations` recovers a ticket blocked by an iteration limit.** `grant-iterations <ticketId> <nodeId1,nodeId2,...> [--extra <n>]` raises the given nodes' `max_iterations` by `n` (default 1, capped at 10 per call) and changes nothing else -- not their status, not their `iteration_count`, so the record of how many automatic attempts were already spent survives. Previously a ticket that hit its iteration ceiling had no defined way out: `reopen-nodes` refuses any call in which a node would exceed its budget, and the loop target is at its ceiling by definition in that state, so it always refused. The documented recovery is now three commands: `grant-iterations` (raise the budget) -> `reopen-nodes` (reset the loop target, clear `blocked`) -> `unstick-node` (release the reviewer that failed, which is still `IN REVIEW` because `reopen-nodes` only collects `DONE`/`REJECTED` nodes). An unknown node id, an id from another ticket, or an out-of-range `n` is an error that writes nothing. Like `reopen-nodes` and `unstick-node`, it is a CLI-only command; there is no HTTP API or Web UI equivalent.

## Changes

- **Which nodes a loop-back rewinds.** The set is the intersection of two closures over `success` edges: nodes reachable forward from the loop target, and nodes from which the failing node is reachable. The loop target and the failing node themselves are excluded, and only nodes currently `DONE` are reset. Two limits are deliberate: a node on that path that is `IN PROGRESS`/`IN REVIEW` is left alone (something is holding it; `unstick-node` is the way out if it stays that way), and sibling reviewers that *passed* keep their verdicts, because they are not on a path to the one that failed. An `approval_gate` on the path is rewound like any other node, so a human is asked to approve again after the rework.
- **Iteration counting is unchanged in meaning.** Only the loop target's `iteration_count` is incremented; the rewound nodes keep theirs, so an iteration still counts how many times the loop target was reworked.
- **Expect iteration budgets to be spent faster.** Because the rewound reviewers now actually run again, each of their failures loops back and spends another of the loop target's iterations. With the default `max_iterations: 3`, a ticket on the default workflow can reach its ceiling sooner than it did before this release; that is the point of the change, and `grant-iterations` is the way through it. A ticket that keeps exhausting its budget usually means the loop is not converging, so read the artifacts and verdicts before granting more retries.
- **Hitting the iteration limit still writes nothing.** When the loop target is already at `max_iterations`, the engine blocks the ticket and leaves every node exactly as it was -- the failing reviewer stays `IN REVIEW` rather than going to `AWAITING FIX`. The rewind set is computed after that check, so there is no half-rewound graph to reason about.
- **A loop-back now keeps the ticket's own status in sync**, as every other state-changing path already did. This is visible when a rewound `approval_gate` puts the ticket back into `IN REVIEW` (waiting on a human) instead of leaving a stale status behind.

## Known limitations

- **The rewind is not one transaction.** A loop-back writes the loop target, then each rewound node, then the failing node, as separate node updates. If the process dies or the database fails partway through, the graph is left partly rewound; `get-ticket` shows the actual state, and `reopen-nodes` / `unstick-node` bring it back. This is the same property the existing `ReopenNodes` (`reopen-nodes`) has always had -- the engine has no transaction handle to pass down -- so both are candidates for one fix later. Before this release a loop-back wrote 2 nodes; it now writes up to N+2, which makes the window wider without making it new.

## Documentation

- `graph-engine help` no longer implies that `reopen-nodes` can recover a ticket blocked by an iteration limit on its own. Its entry now says why it always refuses in that state, and the `grant-iterations` entry spells out the three-command recovery.
- The `process-ticket` skill documents the new loop-back behaviour where it describes `AWAITING FIX` (including the order `get-executable` hands nodes out in, the two deliberate limits, and the advice to confirm with `get-ticket` which nodes were actually rewound for graph shapes other than the ones the skill lists), and has a new "Recovery after an iteration limit" step, kept separate from the approval-gate rejection triage because the cause and the entry conditions differ.

## Upgrade notes

- No migration, no configuration change: the database, existing tickets and all three storage backends (SQLite, MySQL, HTTP) are unaffected. Update from the `/plugin` menu, or run `claude plugin update graph-ops@graph-ops` in a terminal.
- The new behaviour applies to tickets already in flight. A ticket that loops back after the update rewinds the intermediate nodes, so nodes that had already passed will be dispatched again, and their earlier artifacts stay on the node next to the new ones (artifacts are only ever appended).
- If a ticket is blocked at an iteration limit from before the update, recover it with `grant-iterations` -> `reopen-nodes` -> `unstick-node` as described above, rather than editing the database.
