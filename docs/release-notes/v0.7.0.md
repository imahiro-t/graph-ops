## Highlights


- **A failed review now rewinds everything downstream of the loop target, not just the loop target.** When a `review`/`review_gate` node fails and loops back, the engine used to change only two nodes: the loop target went back to `TODO` and the failing reviewer went to `AWAITING FIX`. Everything else stayed as it was. On the default workflow -- several review gates hanging off `impl` in parallel, plus `gherkin_test` and `test_review` -- that had two consequences. `test_review` was handed out again in the very same `get-executable` call that reset `impl`, so the *previous* test run was judged a second time before the rework existed. Worse, when one gate rejected, the sibling gates that had already passed kept their verdicts and were never re-run, so **an implementation that a gate had never seen went past that gate as "approved"** and could reach `report` and `release_approval` that way; `gherkin_test` was skipped the same way whenever the rejection came from a reviewer rather than from the tests. A loop-back now resets **every node reachable from the loop target along `success` edges**, whatever state it is in: the sibling gates that passed, the ones still being judged at that moment, `gherkin_test`, `test_review`, the documentation and report nodes, and the `release_approval` gate. Nothing upstream of the loop target is touched. `get-executable` offers the loop target first, then the rewound nodes and the `AWAITING FIX` reviewer again as their inputs come back -- in the default workflow all four gates depend on `impl` alone, so the gate that rejected is re-offered in the same call as the siblings it rewound.
- **Parallel review gates no longer eat the iteration budget several at a time.** The loop target's `iteration_count` is meant to count how many times that node was reworked, but the engine incremented it once per *failing reviewer*. Four gates hanging off `impl` and rejecting for the same single defect pushed `impl` from 0 to 4 in one round, so with the default `max_iterations: 3` a ticket could be `blocked` before its implementation had been reworked even once -- and it was then unrecoverable from the CLI, because the loop target was sitting at `TODO` and `reopen-nodes` accepted only `DONE`/`REJECTED` nodes. A round of rework now costs exactly one iteration no matter how many gates sent it back. In the default shape the later verdicts never reach the counter at all: the first rejection rewinds its sibling gates to `TODO` along with everything else downstream, so the `complete-node` calls their subagents make afterwards are refused with `INVALID_NODE_STATE` and write nothing (see "A verdict that arrives after its gate was rewound" below). The counting rule is the layer underneath that refusal, and it covers the cases where a second rejection *is* accepted -- a rewound gate that was handed out and claimed again while the target still sits at `TODO`, or a state reached by hand in the Web UI: the first rejection opens the round and bumps the count, and a later one rewinds nothing further, writes nothing to the target, and cannot block the ticket. The budget is checked only for a failure that opens a round, so a second rejection can never be the one that blocks. A *sideways* `loop_back_to` -- one whose failing node is not itself downstream of the loop target, so the loop-back does not rewind it -- still spends an iteration every time, deliberately: the failing node is re-offered without the target being redone, and the iteration limit is the only thing that stops such a loop. The default workflow has none of those.
- **`graph-engine grant-iterations` recovers a ticket blocked by an iteration limit.** `grant-iterations <ticketId> <nodeId1,nodeId2,...> [--extra <n>]` raises the given nodes' `max_iterations` by `n` (default 1, capped at 10 per call) and changes nothing else -- not their status, not their `iteration_count`, so the record of how many automatic attempts were already spent survives. Previously a ticket that hit its iteration ceiling had no defined way out: `reopen-nodes` refuses any call in which a node would exceed its budget, and the loop target is at its ceiling by definition in that state, so it always refused. The documented recovery is now `grant-iterations` (raise the budget) -> `reopen-nodes` (reset the loop target, clear `blocked`), followed by `unstick-node` only if something is still claimed -- the reviewer that failed is left `IN REVIEW` by the blocked loop-back, and `IN PROGRESS`/`IN REVIEW` is the one pair of states `reopen-nodes` still refuses to touch. `reopen-nodes` itself now also accepts a node at `TODO` or `AWAITING FIX`, so a ticket blocked with its loop target already rewound to `TODO` -- a state that used to have no CLI way out at all, only a hand-edit in the Web UI -- recovers by the same two commands. An unknown node id, an id from another ticket, or an out-of-range `n` is an error that writes nothing. Like `reopen-nodes` and `unstick-node`, it is a CLI-only command; there is no HTTP API or Web UI equivalent.
- **`complete-node` no longer accepts a verdict it cannot read.** The pass/fail argument was decided by `passed = arg != "false"`, so every spelling that was not exactly `false` recorded a **pass**: the `passed:`-prefixed form the command's own help told people to write, along with `False`, `0`, `no` and any typo. A review that had failed was recorded as passed and the graph moved on, with nothing left to show where it went wrong. The argument is now exactly `true` or `false`; anything else is a usage error that exits non-zero and changes nothing -- no status, no artifacts, not even the `rejection_reason` artifact a `--reason` would have written. Omitting the argument still means `true`. The help and usage lines now read `complete-node <nodeId> [true|false] [--reason "<text>"]`.
- **A node can now only be completed from a state it can be completed from.** `CompleteNode` never looked at the node it was closing. A `DONE` node could be completed again with `false`, blocking a ticket whose work was finished; a `TODO` node nobody had run could be marked `DONE`; and because artifacts were written before anything else was decided, a bogus call left its artifacts behind either way. The engine now checks before it writes anything: an automatic node must be `IN PROGRESS` or `IN REVIEW` (the states `get-executable` hands out), a manual node (`approval_gate`, `release`) may also be completed from `TODO`, where approvals legitimately sit, and a node of a `CLOSED` ticket is refused regardless of its own status. Anything else fails with `INVALID_NODE_STATE` and writes nothing at all. Two things are deliberately *not* checked: the ticket's `blocked` flag and whether the node's prerequisites are `DONE` -- in a parallel graph, one branch's rejection would otherwise throw away a sibling node's legitimate, already-running work. Until now this rule lived only as a warning in the `process-ticket` skill, which anyone completing a node by hand walked straight past.
- **The same node is no longer handed to two agents, and two updates no longer overwrite each other's columns.** `get-executable` claimed a node by reading it and then writing it back, so two `get-executable` calls running at the same time could both be given the same node and do the same work twice. Claiming is now a single conditional `UPDATE`, and the caller that loses the race is simply not offered that node -- not an error, just an ordinary outcome of parallel execution. Separately, `UpdateNode` and `UpdateProject` wrote back every column they had read, so two updates touching *different* columns -- an assignee changed in the Web UI while `complete-node` changed the status -- ended with the later write restoring the other's old value. They now write only the columns the patch names. `updated_at` still always moves, even for a patch that names no columns.
- **Settings are now read from your home config and environment variables, and from nothing else.** Every setting comes from `$HOME/.graph-ops/config.json` or the matching environment variable; the `graph-config.json` of the directory graph-engine starts in is not read at all. Until now the first file found won and the home config was skipped entirely, so opening a repository you had merely cloned let its `graph-config.json` decide which database is opened (`dbBackend`, `dbPath`, the MySQL connection fields), where tickets and artifacts are sent (`httpDataSourceUrl`, `httpDataSourceToken`), which directory agent instructions come from (`userExtensionsDir`), what "Launch Claude" runs (`terminalCommand` and `claudeBinary` are passed to `sh -c`), whether this unauthenticated API is published to your network (`host: "0.0.0.0"`) and which files may be read back as artifacts (`artifactsDir: "/"`). There is no per-key exception table in either direction -- no blocklist, no allowlist -- so a setting added later is covered by the same one rule, and a test walks `FileConfig`'s JSON tags with reflection to keep it that way. An environment variable still wins over the file, because setting one is a deliberate act by whoever starts the process. **If you keep settings in a working-directory `graph-config.json` today, read the upgrade notes below before updating** -- they stop taking effect, and the most visible symptom is a ticket list that looks empty.
- **A repository can no longer supply agent instructions or a workflow either.** The team tier used to default to the nearest `.graph-ops` directory found by walking up from the working directory, so a repository that merely contained `.graph-ops/workflow.yaml` or `extensions/node-types/*.md` handed its node instructions, review gates and workflow shape to whoever ran graph-engine inside it -- with no setting written anywhere, and therefore nothing to notice. That search is gone. The team tier is now exactly the directory `teamExtensionsDir` (or `GRAPH_TEAM_EXTENSIONS_DIR`) names in your own home config, and it has no default: point it at a shared directory to share settings with a team, and if you do not, there is no team tier. A team root that resolves to the same directory as the user root is still dropped rather than read twice.
- **Per-project settings are gone.** The settings screen no longer has a "Global Settings / Project Settings" switch, and the settings API no longer takes a `scope` or a `project_id` -- not as ignored parameters, but not at all, so nothing can be passed that silently does nothing. Settings are yours and apply on every project. Labels are the one thing that stays per project: they live in the database, not in a settings file, so the Labels tab now carries its own project selector and can edit any project's labels regardless of which project the header is showing. No database schema changed, and no label moved.
- **Windows: arguments no longer go back through `cmd.exe`.** `packages/plugin/bin/graph-engine.cmd` no longer passes `%*` to the shim. Each argument cmd.exe has already split is copied into an environment variable of its own and reassembled on the Node side, so a `%VAR%`, an `&`, a `!` or a `^` inside an argument -- a ticket description or an artifact body, say -- is no longer expanded, split off, or run as a second command (the BatBadBut class of problem). This narrows that class; it does not end it. See **Known limitations** below.
- **Two routes that let any web page reach this API through your browser are gone.** `GET /api/tickets/{id}/executable-nodes` changed state -- it seeded a ticket's graph and moved nodes to IN PROGRESS / IN REVIEW -- yet it was a `GET`, and `GET` is exempt from the CSRF header check every state-changing method has to pass, so `<img src="http://127.0.0.1:49173/api/tickets/PFX-00001/executable-nodes">` on any page you happened to open was enough to drive it; ticket IDs are sequential, so guessing one is not a barrier. `/artifacts-static/` served the artifacts directory (`~/.graph-ops/artifacts` by default) straight off the filesystem, on the app's own origin, with no sandbox and with directory listings enabled, so agent-authored HTML opened from there ran as same-origin script and could call this unauthenticated API -- `POST /api/claude/launch` included -- with the CSRF header attached. Both were undocumented and had no callers here: the Web UI never used either, and the CLI's `get-executable` calls the engine directly. `/artifacts-static/` now answers `404` (`ROUTE_NOT_FOUND`), and the unused Vite dev-server proxy for it is gone too. `GET /api/artifacts/{id}/content`, which serves artifacts with `Content-Security-Policy: sandbox allow-scripts` and `X-Content-Type-Options: nosniff`, is unaffected and remains how the UI reads artifact content.
- **Every response now carries framing, sniffing and referrer protections, and the Web UI sends a CSP of its own.** `X-Frame-Options: DENY` and `Content-Security-Policy: frame-ancestors 'none'` close a click-jacking route the existing defenses did not cover: an embedded frame loads the real app on its real origin, so the Host check passes and the app attaches the CSRF header itself, which is all it takes to click a user through a one-click action -- passing a review approval gate, or launching Claude Code in an external terminal. `GET /api/artifacts/{id}/content` is the one exception, keeping its sandbox and using `frame-ancestors 'self'` so the UI's own artifact preview keeps working. `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer` are now set in that same one place, so a route added later cannot miss them; `no-referrer` keeps the URL of an artifact preview -- which names the artifact being read -- from travelling to any host the page links to or loads from. In the UI, a remote image inside a markdown artifact is no longer fetched just because the artifact was rendered: the viewer shows the image's host and fetches nothing until the reader clicks. The click is what gates the request; the page's `img-src` allows `https:` so that the click does what it says, and refuses every other external source. A remote image the policy would refuse (a cleartext `http:` URL, for instance) is offered as a link to open in a new tab rather than as a button that could not deliver. Loading and failing are both announced to assistive technology, and keyboard focus stays where the reader put it.
- **"The current project" is now yours, not everyone's.** It was one value for the whole data source -- a single `app_state` row -- even though what it records is which project *one person* is looking at right now. A team sharing a MySQL database or an HTTP data source shared that value too, so one member switching projects changed what the others saw: the Web UI asked for `/api/tickets` with no project at all and let the server narrow the list by that shared value, so at the next 15-second poll the *list* became somebody else's project while the header and the label filter options still named the project you had chosen -- a screen contradicting itself, with nothing on it to say which project you were actually looking at. The same value decided where `graph-engine create-ticket` filed a ticket when you passed no `--project` and your working directory matched no project's local path, so a ticket could land in whatever project a colleague had selected last. The current project now lives in your own home config file (`$HOME/.graph-ops/config.json`), as `currentProjectId` beside `projectPaths`, and is never written to the database. `graph-engine use-project` and the header's project menu change only your own environment. The UI always fetches the list for the project its header is showing, and draws a list -- with its summary counts, assignee and label filter options -- only when it was fetched for that project, so the two cannot drift apart.
- **`GET /api/tickets` no longer guesses which project you meant, which is a breaking change.** Called with neither `project_id` nor `all`, it used to return the tickets of the shared current project; it now returns `[]`. The two explicit forms are unchanged and are what every caller should use: `?project_id=<id>` for one project's tickets, `?all=true` for every ticket in the data source (and if both are given, `all=true` wins, as before). This is the fallback that made the contradictory screen above possible, and removing it is what forces each client to say what it is asking for. `POST /api/tickets` keeps its fallback, now reading the home config of the user running the server: a ticket created with no `project_id` goes to that environment's current project, or fails with `NO_CURRENT_PROJECT` as it already did when none is set.
- **The Web UI's polling no longer costs one request per ticket.** The dashboard refreshed every 15 seconds by fetching the ticket list and then one `GET /api/tickets/{id}` for every ticket in it -- 102 requests per round with 100 tickets, counting the project's labels the round has always re-fetched alongside them, for every open tab and every viewer of a shared MySQL backend -- and each of those detail responses re-sent every text artifact's whole body, plans and review verdicts included, although only an expanded ticket's panel ever reads them. `GET /api/tickets` now carries each ticket's `nodes` and `edges`, which is what a collapsed card needs (progress bar, node status chips, the approval-gate highlight, the dashboard's totals across pages), and carries no `artifacts` at all. A polling round is now a fixed number of requests whatever the ticket count -- the list plus the project's labels, and one detail request per ticket the user has actually expanded -- so 3 tickets and 100 tickets cost the same. Artifact bodies are transferred only for an expanded ticket, fetched the moment it is expanded and then once per round. This changes the response shape of `GET /api/tickets`; see **Upgrade notes**. The 15-second interval itself is unchanged, and nothing about what the cards display changed.
- **Polling stops while the tab is hidden.** Nothing in the UI looked at `document.visibilityState`, so a dashboard left open in a background tab kept querying the database every 15 seconds indefinitely. While the tab is hidden no polling request is issued at all; when it becomes visible again the UI fetches once immediately -- so what you see when you switch back is current, not up to 15 seconds stale -- and then resumes the ordinary interval, counted from that fetch.

## Changes


- **Which nodes a loop-back rewinds.** The set is the loop target's forward closure over `success` edges: every node reachable from the target, minus the target itself and the failing node (which goes to `AWAITING FIX` as before). Status does not narrow it -- `DONE`, `IN PROGRESS`, `IN REVIEW`, `AWAITING FIX` and `REJECTED` nodes are all reset to `TODO`. Nodes already at `TODO` are skipped only because that is where a reset would put them anyway; the rule is "reset the whole closure", not "reset the finished ones". A node something is still working is reset too, so a gate whose subagent is mid-judgment goes back rather than staying claimed, and `unstick-node` is no longer part of recovering from an ordinary loop-back. An `approval_gate` in the closure is rewound like any other node, so a human is asked to approve again after the rework.
- **Iteration counting keeps its meaning, and now matches it.** Only the loop target's `iteration_count` moves; the rewound nodes keep theirs, so an iteration counts how many times the loop target was reworked -- which is why a whole round of rejections counts once. Whether a failure opens a new round is decided by two things: whether the failing node is inside the target's forward closure (so the target's rework is what re-offers it), and whether the target is already back at `TODO` from an earlier rejection in the same round. When *both* are true the round is already counted, so the failure opens none and writes nothing to the target at all -- it only goes to `AWAITING FIX`. Any other combination opens a round and bumps the count, which is why a sideways `loop_back_to`, whose failing node is outside the closure, still counts every time even against a target already at `TODO`.
- **Adding review gates no longer costs iterations.** Hanging N gates off the same loop target used to mean a single round of rework could spend N of its iterations; it now spends one, so a graph with four gates and `max_iterations: 3` really does get three rounds of rework rather than being blocked partway through the first. Rewound reviewers do of course run again and can fail again, and a ticket that keeps exhausting its budget usually means the loop is not converging -- read the artifacts and verdicts before reaching for `grant-iterations`.
- **Hitting the iteration limit still writes nothing.** When a failure that would open a new round finds the loop target already at `max_iterations`, the engine blocks the ticket and leaves every node exactly as it was -- the failing reviewer stays `IN REVIEW` rather than going to `AWAITING FIX`. The rewind set is computed after that check, so there is no half-rewound graph to reason about. A failure that opens no new round skips the check entirely, which is what keeps the second gate of a round from blocking a ticket the first gate just sent back.
- **A loop-back now keeps the ticket's own status in sync**, as every other state-changing path already did. This is visible when a rewound `approval_gate` puts the ticket back into `IN REVIEW` (waiting on a human) instead of leaving a stale status behind.
- **A verdict that arrives after its gate was rewound is refused, and writes nothing.** Because a loop-back now resets gates that are still being judged, the agent working such a gate finishes afterwards and calls `complete-node` on output that has since been redone. The node is back at `TODO` by then, so the existing state check refuses it with `INVALID_NODE_STATE` before anything is written -- no status change, no artifacts -- which is exactly what keeps a verdict on a superseded commit off the record. The message for an automatic node at `TODO` now names both reasons it can be there (`get-executable` never handed it out, or a loop-back rewound it mid-run) and says what to do: go back to `get-executable` and redo the node when it is handed out again. This refusal is routine after a rejection, not a fault, and `process-ticket` and the `graph-node-agent` definition both say so. Two things follow from it. The rewound gate's old agent may still be running when that gate is handed out again, so the same gate can briefly be worked twice -- accepted rather than prevented. And the refusal stops the *verdict*, not the write-up: an agent saves its review with `add-artifact` before calling `complete-node`, and `add-artifact` does not look at the node's status, so the superseded write-up stays on the node beside whatever the re-run produces. Artifacts are only ever appended, so read the most recent one as the current verdict.
- **`reopen-nodes` accepts two more starting states, and bumps fewer nodes.** It used to collect only `DONE` and `REJECTED` nodes, both as the ids you name and in its downstream sweep. It now also accepts `TODO` and `AWAITING FIX`, which is what makes a ticket blocked with its loop target already rewound recoverable from the CLI. Those two states spend no iteration when they are reset -- they had not been redone yet -- while `DONE`/`REJECTED` nodes are bumped as before, and the budget check now covers only the nodes that are actually bumped. `IN PROGRESS`/`IN REVIEW` are still refused, with a message pointing at `unstick-node`. One consequence worth knowing: because the sweep follows the same widened rule, it now passes *through* a `TODO` or `AWAITING FIX` node to reach finished work further downstream, so the same call can reset (and bump) more nodes than it would have before, and can therefore refuse on a budget it used to fit inside.
- **`reopen-nodes` and `grant-iterations` help text follows the new rules**, naming the four states `reopen-nodes` accepts, which of them spend an iteration, and the recovery sequence that works whether the loop target is `DONE` or `TODO`.
- **`POST /api/tickets/{id}/nodes/{nodeId}/complete` now answers with a status that says which kind of failure it was.** Every failure used to be `400`. `INVALID_NODE_STATE` is now `409 Conflict` -- the request was valid and the row exists; what stands in the way is the state the row is in right now -- and an unknown node is `404` with `NODE_NOT_FOUND`. A client can now tell "you called this wrong" from "this cannot be done from here", which is the difference between fixing the call and re-reading the ticket.
- **The Web UI has a message for the new error.** `errors.INVALID_NODE_STATE` was added to both the `en` and `ja` locales. It appears when the same approval gate is handled in the Web UI and in a terminal at once, and it names the next step for someone looking at a screen (reload and see where the node actually is) rather than a CLI recovery command.
- **Which statuses a claim may move from is unchanged.** The conditional `UPDATE` excludes exactly `DONE`, `IN PROGRESS` and `IN REVIEW`, the same set the old in-memory filter used, so `TODO`, `AWAITING FIX` and `REJECTED` nodes are still claimable and the order `get-executable` returns nodes in has not changed.
- **`runtimeconfig` has one reader and one writer.** `LoadEffective(cwd, home)` returns the effective config, the home config's path, whether that file could be read, and the path of a leftover working-directory `graph-config.json` if one exists -- and it no longer returns an `error` at all, because none of its outcomes is fatal. `UpdateHome` is the only write path. The candidate-path machinery (`CandidatePaths`, `ResolvePath`, `Load`, `Save`, `Update`) is gone, and so is the home-only key table with everything around it (`homeOnlyKeys`, `HomeOnlyKeys`, `HomeOnlyKeyList`, `clearHomeOnly`, `copyHomeOnly`) -- no allowlist replaced it. `LoadHomeConfig` is the new raw single-file read, used where the on-disk values themselves are needed (the MySQL connection test's secret re-entry check, and `internal/currentproject`, which has to tell an absent `currentProjectId` from an explicit empty one and must not mistake an unreadable file for "no project"). `cwd` now has exactly one purpose: spotting that leftover file so it can be named in a warning. It is never opened.
- **App Settings reads and writes one file, in one write.** `GET`/`PUT /api/settings/app` work against `$HOME/.graph-ops/config.json`; `config_path` is that file and is the only path the page shows, and a `PUT` is a single `UpdateHome` call rather than a main write plus a second one for `artifactsDir`. `GET` still leaves out the settings this page does not edit (`terminalCommand`, `claudeBinary`, `host`), so an unauthenticated response carries neither secrets nor anything that is executed. When the home directory cannot be resolved at all, `config_path` is the empty string and the page says the file could not be located rather than naming a path that does not exist.
- `powershellQuote` now doubles the four smart quotes (U+2018, U+2019, U+201A, U+201B) as well as the ASCII `'`, matching the set PowerShell itself treats as single quotes. A prompt containing `'; calc; '` written with smart quotes now stays inside the literal string in the generated `.ps1` instead of ending it. `shellQuote` (POSIX) is unchanged.
- **An unreadable home config is handled by one rule, whatever is in the current directory.** If `$HOME/.graph-ops/config.json` cannot be parsed, graph-engine prints one warning naming it and starts anyway, with every setting falling back to environment variables and built-in defaults. The current project is the exception, since it has no default to fall back to that would not be a guess: reading it fails with `current_project_read_failed`, which the Web UI shows as a load failure with a retry button, and `create-ticket` without `--project` stops with an error instead of filing the ticket somewhere. Whether a `graph-config.json` happens to exist where you started makes no difference -- previously it did, which meant dropping a file into a repository could make your own broken home config stop being reported, and deleting it could stop the CLI from starting at all. Writing keeps the opposite asymmetry on purpose: `UpdateHome` refuses to overwrite a file it could not parse, so a save fails loudly rather than discarding settings it could not read.
- **A leftover working-directory `graph-config.json` produces exactly one warning line.** It names the file, says settings come from the home config or environment variables, and says that deleting the file silences it. It lists no key names, so a file with 22 keys in it produces the same single line as one with a single key, and because the file is never opened, one that is not valid JSON produces that same line too -- no parse error, and nothing about a file we no longer read becomes the user's problem to fix. The path of that file is deliberately CLI-only: it is not in any HTTP response, so the Web UI cannot be used to enumerate what is lying around in the directory a server was started from.
- **Saving settings where there is no home directory is now an error, not a warning.** `PUT /api/settings/app` on a machine where `$HOME` cannot be resolved answers `500` with `HOME_CONFIG_UNAVAILABLE` and writes nothing, instead of returning `200` with a warning attached -- a response that said the save had succeeded when there had been nowhere to save it. An unparseable home config answers `500` with `HOME_CONFIG_UNREADABLE`, which now means every setting on the page is unreadable and nothing was saved, not just one field.
- **Error codes: three removed, one added.** `INVALID_SETTINGS_SCOPE`, `PROJECT_LOCAL_PATH_NOT_SET` and `PROJECT_TEAM_ROOT_IS_USER_ROOT` went with per-project settings. `HOME_CONFIG_UNAVAILABLE` is new. Their locale entries were removed and added to match, in both `en` and `ja`.
- **The settings API dropped `scope`, `project_id`, `team_root_resolved` and `has_team_override`** from its queries, bodies and responses, and `get-language-settings` no longer accepts `--project` (passing it is a usage error, so a script that still does stops visibly rather than silently reading different settings). `get-executable` and `expand-graph` resolve the workflow catalog from the configured roots directly, with no project local path involved. On the wire, a `PUT` body carrying the old `scope`/`project_id` fields is not rejected -- Go's JSON decoding drops unknown fields silently -- so an old client gets a `200` and a save that used the one scope there now is, rather than a `400`.
- **The merged preview in Settings shows the plugin default plus your own tier, and says so.** It never included the team tier, and now that a team tier only exists where you explicitly pointed at one, the old label ("what an agent actually sees") would have been wrong for exactly the people who configured one. Use `graph-engine get-node-type-context <nodeType>` (or `get-skill-context`, `get-plan-template`, `get-review-template`, `get-report-template`) to see the fully merged result an agent receives.
- **`projectPaths` is read from and written to the home config.** Reading and writing used to be able to target different files -- the read went through the resolved config, the write through `runtimeconfig.Update` -- so a local path saved from one directory could be invisible from another. Both now go through `UpdateHome`, and `create-ticket`'s "which project is this directory in?" resolution is unchanged. When the home config cannot be read, project local paths simply come back unset (with a `project_paths_load_failed` log line) instead of turning `GET /api/projects` into a `500`.
- **The API server sets `ReadHeaderTimeout` and `IdleTimeout`, and caps request bodies at 64 MiB.** Both matter when the server is deliberately exposed with `--host 0.0.0.0`. `ReadHeaderTimeout` ends the *header* phase of a Slowloris-style client, which is the phase a timeout can bound without also cutting off a legitimate slow upload or the artifact-zip download; a client that dribbles out a request *body* is still bounded in bytes by the 64 MiB cap but not in time, and closing that too needs per-route read deadlines, which is left to its own change. A body over the cap is answered `413` with `REQUEST_BODY_TOO_LARGE`, never a `5xx`. `IdleTimeout` bounds a keep-alive connection that is sitting between requests, so an idle client cannot hold one open for as long as it likes.
- **The two new rejections are recorded in the security log** (`REQUEST_BODY_TOO_LARGE`, `API_ROUTE_NOT_FOUND`), masked the same way the existing ones are: a path class, a status and the peer IP, never anything the caller sent. Repeated over-cap bodies are the only trace a memory-exhaustion attempt would leave.
- **`PATCH /api/tickets/{id}` and `PATCH /api/nodes/{id}` validate their input.** A ticket's `status` and a node's `status` now have to be values the engine understands, a ticket's `title` cannot be set to an empty string, and a node's `max_iterations` has to be 1 or greater. A rejected request changes nothing at all. Setting a ticket to `CLOSED` through `PATCH` is refused as well: use `POST /api/tickets/{id}/close`, which records the reason alongside it.
- **`PATCH /api/nodes/{id}` keeps the ticket's status in step with its nodes.** It was the one path that changed a node without re-deriving the owning ticket's status, so (for example) a PATCH that moved the last node to DONE left the ticket at IN PROGRESS indefinitely. A CLOSED ticket is still never resurrected, and its `closed_reason` is left untouched.
- **`PATCH /api/nodes/{id}` no longer accepts `name`, `type` or `iteration_count`**, and answers `400` if one is sent. A node's name and type come from the workflow catalog its graph was expanded from, and `iteration_count` is the engine's own bookkeeping as review gates loop. No caller in this repository set any of them.
- **An unknown `/api/` path returns a JSON `404`** (`API_ROUTE_NOT_FOUND`) instead of falling through to the SPA and answering `200` with `index.html`.
- **The home config gained `currentProjectId`, and an existing selection is inherited once.** On an environment whose config file has no `currentProjectId` yet, the first read of the current project copies the data source's `app_state.current_project_id` into the file and uses it from then on, so nobody has to re-select the project they were already working in. It happens once per environment and only when there is something to inherit: if the data source's value is empty, nothing is written at all, which is what keeps a fresh install from having a config file created for it by a read. An explicit `"currentProjectId": ""` -- what you get by deleting the project you had selected -- means "none selected" and does not re-trigger the inheritance. A successful inheritance is logged once at info (`event=current_project_inherited`, with the project ID and the config file path); if the value cannot be written afterwards, the read still succeeds and a warning names the file (`current_project_inherit_save_failed`).
- **`GET/PUT /api/current-project` keep their request and response shapes**; only where they read and write changed. `GET` still answers `200` with `null` both when nothing is selected and when the selection names a project that no longer exists, and it does not rewrite a selection that has gone dangling. `PUT` still checks the project exists and answers `404` otherwise, leaving the previous selection in place. Deleting a project still clears the selection if it pointed at it -- now by clearing `currentProjectId` and that project's `projectPaths` entry in a single write of the config file.
- **`graph-engine use-project <projectId>` writes the config file instead of the database.** How `create-ticket` resolves a project is deliberately unchanged -- the working directory matched against `projectPaths` first, the current project second, an error third -- but what step two reads is now this environment's own value. `graph-engine help` says so under `use-project`, and also that `GET /api/tickets` no longer narrows by it.
- **The Web UI tells "not loaded yet", "load failed" and "none selected" apart.** The current project is held as one value that is either loading, failed, or resolved (to a project or to none), so the screen cannot be in two of those at once. While it is still being resolved the UI shows a loading state and fetches no tickets, rather than briefly offering to create a project. If reading the current project fails, it says so in an alert with a retry button that re-reads both the project list and the current project, and it deliberately does *not* offer the "create your first project" button there, since that path invites creating a duplicate of a project that already exists; choosing a project from the switcher on that screen also clears the failure. A response to a read issued before you chose a project never undoes your choice.
- **Right after a switch, the Web UI shows "Loading tickets..." instead of the previous project's list.** The ticket list and the project's labels are kept tagged with the project they were fetched for, and anything tagged with another project is treated as not loaded yet: until the new project's list arrives, the body shows a loading message, and the summary counts, the assignee filter options and the label filter options are empty rather than the previous project's. A slower response for an earlier project, or an earlier fetch of the same project, is discarded when it finally arrives. The 15-second poll skips its turn while a fetch of the same project is still in flight, and so does the fetch made when a hidden tab becomes visible again, so a data source slower than the poll interval still gets its list shown instead of being overtaken forever; the fetch made on entering a project, and a manual refresh, are never skipped. An expanded ticket's detail that arrives after you switched projects replaces nothing in the new project's list. Three locale strings were added in `en` and `ja`: `projectSwitcher.loadFailed`, `projectSwitcher.retry` and `emptyState.loadingTickets`.
- **A failure to read the current project is logged with the config file's path** (`event=current_project_read_failed`, naming the file and the error, never its contents). It is the server-side counterpart of the UI's load-failure state and reaches both `GET /api/current-project` and `POST /api/tickets`, which answer `500` rather than silently behaving as though no project were selected.
- **The data source protocol's `/current-project` is deprecated, not removed.** `GET` and `PUT` are both marked `deprecated: true` in `openapi.yaml`, and `store.GraphRepository` keeps `GetCurrentProjectID`/`SetCurrentProjectID` with the `app_state` table behind them. graph-engine calls `GET` only while the user's own home config has no `currentProjectId` -- once on an environment upgrading with a selection to inherit, and on each read until a project is selected on one that has none -- and never calls `PUT`. Nothing about how a plugin lists tickets changed: `GET /tickets` still returns every ticket and has no `project_id` query -- narrowing is still `GET /projects/{projectId}/tickets`. The breaking change above is to graph-engine's own `GET /api/tickets`, which is a different endpoint. Existing plugins, including the Jira sample, need no change.
- **What `GET /api/tickets` returns.** The new `domain.TicketGraph` is a `Ticket` embedded alongside `nodes[]` and `edges[]`. It has no `Artifacts` field at all, so an artifact body cannot reappear in this response by accident; the tests check both the absence of the key and the absence of any artifact body in the whole response. Both paths through `handleListTickets` return the same shape, the scoped `?project_id=` one and the cross-project `?all=true` one, and a ticket with no graph yet gets `[]` rather than `null`. `GET /api/tickets/{id}` still returns `TicketDetail` with artifacts included, and `graph-engine get-ticket` is unchanged.
- **The bulk graph read is an optional store interface, not part of `GraphRepository`.** `store.TicketGraphLister` loads many tickets' graphs in a fixed number of queries -- one query for nodes and one for edges per chunk of 500 ticket ids -- so the HTTP N+1 is not simply pushed down into the database; `nodes(ticket_id)` and `edges(ticket_id)` are already indexed on both SQL backends. SQLite and MySQL implement it, and callers type-assert for it and otherwise fall back to one `GetTicketDetail` per listed ticket -- the only read every `GraphRepository` has that returns a whole graph at once -- keeping its nodes and edges and dropping its artifacts. Falling back to the per-ticket `ListNodesByTicket` / `ListEdgesByTicket` pair instead would cost a remote data source two sequential calls per ticket where the detail read costs one, so the fallback's test counts its downstream calls and pins them at one detail read per listed ticket and no node or edge reads. It is deliberately not on `GraphRepository` because `HTTPRepository` implements that interface against a remote data source, where a new method would demand a new endpoint of every existing data-source implementation (`docs/http-datasource/openapi.yaml`, `examples/jira-datasource`). It takes ticket ids rather than a project id because of the `?all=true` path, which no project-scoped API could serve.
- **A polling round keeps the artifacts the UI already has.** Because the list response no longer carries artifact bodies, merging a round into the UI state carries each ticket's previously fetched artifacts forward by id. An expanded ticket's artifact tabs therefore do not blank out in the window between the list response arriving and that ticket's detail response arriving.
- **Expanding a ticket fetches its detail immediately** instead of leaving its artifact tabs empty until the next round, up to 15 seconds later.
- **Dependency updates.** The `graph-engine` binary now builds against `github.com/go-sql-driver/mysql` 1.10.1 and `modernc.org/sqlite` 1.59.0. The Web UI moves to react-i18next 17 with i18next 26; the rest are development tools (ESLint 10, eslint-plugin-react-hooks 7, concurrently 10, autoprefixer 10.6), and building or linting from source now needs Node.js 22 or later.

## Known limitations


- **The rewind is not one transaction.** A loop-back writes the loop target, then each rewound node, then the failing node, as separate node updates. If the process dies or the database fails partway through, the graph is left partly rewound; `get-ticket` shows the actual state, and `reopen-nodes` / `unstick-node` bring it back. This is the same property the existing `ReopenNodes` (`reopen-nodes`) has always had -- the engine has no transaction handle to pass down -- so both are candidates for one fix later. Before this release a loop-back wrote 2 nodes; it now writes up to N+2, which makes the window wider without making it new. The loop target itself is two of those writes when a round opens (the claim that resets it, then the iteration bump), so a failure between them leaves the target at `TODO` with that round uncounted -- the graph stays usable and later rounds count normally, but that one round is not charged to the budget. The "nothing is written at all" guarantee applies to the case it was made for: a loop-back refused because the budget is exhausted.
- **One iteration per round is atomic on SQLite and MySQL only.** The first rejection of a round claims the loop target with a conditional update, which is what stops two gates finishing at the same instant from both counting a round. An HTTP data source cannot express a conditional update (see the claim limitation below), so against that backend graph-engine reads the node and writes it back over two round trips, and two gates that finish together can still add an iteration each. The deterministic half of the old problem -- gates completing one after another, each adding one -- is fixed on every backend, because each completion re-reads the target's current status. If you run this plugin against Jira or another HTTP data source, expect a parallel-gate round to occasionally cost more than one iteration, and `grant-iterations` to be needed sooner.
- **Node claims are atomic on SQLite and MySQL only.** The protocol an HTTP data source implements has no conditional update, so against that backend graph-engine still claims with `GET /nodes/{id}` followed by `PATCH /nodes/{id}`, and a claim landing between the two is invisible to it: the same node can be handed out twice. A plugin cannot close this from its side -- the PATCH carries no expected-current-status to check against. One `process-ticket` session issues its `get-executable` calls one at a time, so the exposure is two sessions driving the same ticket at once; and if it does happen, the second agent's `complete-node` is refused with `INVALID_NODE_STATE`, so the work is duplicated but the record stays correct. The limitation is written on the `ClaimNode` interface and in the custom data source manual's "Atomicity" section.
- **Completing a node is still check-then-act.** The state check and the writes that follow it are not one transaction, so two callers completing the same node at the same instant can both pass the check. What this release removes is the path that produced that situation in practice -- the same node being dispatched to two agents. Closing the remainder needs a transaction handle the engine deliberately does not have (`internal/engine` is DB-independent pure graph logic), the same reason `ReopenNodes` and the loop-back rewind are not transactional either.
- **One `complete-node` failure still answers `400` without a code**: a node whose ticket row is missing. Foreign keys cascade node deletion with the ticket, so this needs an orphaned node to reach at all; every other failure of that endpoint now carries a code and a matching status.
- **The Windows wrapper has not been exercised on a real Windows machine.** Its behaviour is pinned by static checks on the `.cmd` file and by unit tests that drive the win32 path with `process.platform` passed in, so what cmd.exe actually stores in the relay variables, and how PowerShell reads the doubled quotes, are assumptions. Verification on Windows (cmd.exe, PowerShell 5.1 and 7) is tracked separately.
- **The `.cmd` change narrows the BatBadBut class of problem rather than eliminating it.** An argument whose own text contains a `"` can still flip the quoting of the line that copies it, which no batch file can rule out; and the quoting of the command line that *invokes* the wrapper is the calling runtime's job (Node 18.20.2 and later escape it), not the wrapper's.
- **The current project now has two writers, and the last one wins.** The UI server writes `$HOME/.graph-ops/config.json` when you switch projects in the header; `graph-engine use-project` writes the same file from the CLI -- it is the same file whichever directory each was started from, since that is the only config file there is. Each write re-reads the file under a lock and replaces one key, so the file cannot be corrupted, but a switch and a `use-project` issued at the same moment simply leave whichever finished last. A running UI server does not notice a change made by the CLI until it next reads the file, which it does on every request that needs the current project.
- **Tabs in one environment are not kept in step with each other.** Two browser tabs on the same machine share one home config, so switching projects in one changes the stored selection for both -- but the other tab goes on showing, and fetching, the project it already had, and only picks up the change when it is reloaded. That is no longer the contradictory state this release removes -- each tab's header and its list still agree with each other -- it is simply not live synchronisation, which would need a channel the UI does not have, and is out of scope.
- **Environment variables still take precedence over the home config, and that is deliberate.** Anyone who can set `GRAPH_DB_BACKEND`, `GRAPH_HTTP_DATASOURCE_URL` or `GRAPH_TEAM_EXTENSIONS_DIR` in the environment graph-engine starts in -- a `direnv` `.envrc`, a `Makefile` target, any script from a repository that you run -- can still redirect those settings. The difference is the premise: all of those require executing something from the repository, which is a decision you make, whereas the path this release closes needed only a file to be *present*. Setting an environment variable stays the supported way to point graph-engine somewhere else on purpose, which is why the custom data source manual now uses exactly that for its verification steps instead of a scratch config file (together with a temporary `HOME`, since the current project and project paths are always written to the home config).
- **The Settings screen cannot show you a configured team tier.** Its merged preview is the plugin default plus your own tier; a shared directory named by `teamExtensionsDir` is read by the engine but not displayed there. Check the fully merged result with `graph-engine get-node-type-context <nodeType>` and the matching commands for skills and templates.
- **Nothing migrates a working-directory `graph-config.json` for you.** graph-engine will not read the file, so it also does not copy values out of it; moving what you need into `$HOME/.graph-ops/config.json` is a manual step (see the upgrade notes). This is on purpose -- a tool that silently imported settings out of whatever directory it was started in would reintroduce the problem this release removes.
- **With the `http` data source backend, one `GET /api/tickets` takes about `N × RTT`.** `HTTPRepository` does not implement `store.TicketGraphLister`, so the UI server takes the fallback path and issues one `GET /tickets/{id}/detail` per listed ticket **in series**, inside the single request the browser made. The number of remote calls a round costs the data source is not a regression: counting the current-project lookup, the list itself and the detail reads, a round reached the data source as `N+2` calls before this release -- the browser asked for each ticket's detail itself -- and reaches it as `N+1+E` now, where `E` is how many tickets the user has expanded. The current-project lookup is gone from the round because the Web UI now names the project it lists (`?project_id=`), and what is left over is a constant per expanded card, not a term that grows with the ticket count. (The one labels request a round also makes adds a further call to both of those counts.) What is worse than before is wall time, not call count. The browser used to issue those detail requests concurrently, about six at a time to one origin; the UI server now issues them one after another, so a list request takes roughly `N × RTT` and nothing caps the total -- the 30-second timeout in `store/http.go:41` is per call. At 200 ms RTT that passes the 15-second polling interval at around 75 tickets. One tab does not pile up requests past that point -- it skips a round while its previous fetch of the same project is still running -- so the list just refreshes less often, as often as a fetch completes; every other open tab and every other viewer still adds its own load. Adding a bulk graph read to the data-source protocol is the candidate for closing that. The fallback's detail responses also carry each ticket's artifact bodies, which travel from the data source to the UI server and are dropped there, never reaching the browser. That is the same hop, the same bodies and the same frequency as the per-ticket `GET /api/tickets/{id}` the Web UI made every round before this release, so it is not a regression either. The SQLite and MySQL backends are unaffected: both implement `store.TicketGraphLister`, read every ticket's graph in a fixed number of queries and never read artifacts at all.

## Upgrade notes

- **Stop the UI server you started before the update, then run `/graph-ops:ui` again from a Claude Code session started after the update. This release's server-side changes -- its security fixes, the per-environment current project in the UI, and the new completion checks for approvals and rejections made in the Web UI among them -- do not reach you until you do.** Updating the plugin replaces the `graph-engine` binary but not a server that is already running, and a UI server keeps running until it is stopped. `/graph-ops:ui` reuses whatever server answers `GET /api/health` on its port, and that response carries no version, so nothing notices that the server is the old one: it keeps serving the previous release indefinitely. If one started before the update is still running, stop it -- on macOS / Linux, `kill $(lsof -ti tcp:49173 -sTCP:LISTEN)` stops one on the default port (use your own port number instead if you changed `port` / `PORT`); on other operating systems, stop the process listening on the default port 49173 (or the port you configured) -- and then run `/graph-ops:ui` to start this version's server. Run it from a Claude Code session started after the update: a session that was already open when you updated may still run the previous version's `graph-engine`, which would start the old server again, so first restart every Claude Code session that was open when you updated (or start a new one) -- whether you updated from the `/plugin` menu or from a terminal. The changes to the `graph-engine` commands themselves -- the loop-back, iteration, `complete-node` and `get-executable` changes above -- take effect for the commands you and your agents run in any session started after the update, even while the old server is still running; approvals and rejections made in the Web UI do not, as described below. Every note below assumes the server has been restarted this way. If the old server keeps running:
  - **The UI and the CLI disagree about the current project.** The old server still reads and writes the current project in the database's shared `app_state` row, while this version's CLI -- `create-ticket` without `--project`, and `use-project` -- uses `currentProjectId` in `$HOME/.graph-ops/config.json`. Once the one-time inheritance described below has copied a selection into the file, switching projects in the old UI no longer changes where the CLI files tickets: the header can show one project while `create-ticket` puts the ticket in another -- the very problem this release set out to remove.
  - **This release's security fixes do not apply.** The old server still answers the state-changing `GET /api/tickets/{id}/executable-nodes` and serves `/artifacts-static/`, sends no framing or referrer protections and puts `X-Content-Type-Options: nosniff` only on artifact content responses rather than on every response, and still reads the `graph-config.json` of the directory it was started in. All of that changes only when this version's server is running.
  - **Approvals and rejections made in the Web UI follow the previous release's rules.** The Web UI does not run `graph-engine complete-node`: it sends `POST /api/nodes/{id}/complete`, and the server completes the node itself. So while the old server is running, an `approval_gate` approved or rejected in its UI goes through the previous release's code, so the new state check on completing a node (`INVALID_NODE_STATE`, described above) does not apply to it: the old server still lets a gate that is already `DONE` be rejected, blocking a ticket whose work was finished, or a gate of a `CLOSED` ticket be judged. That changes only when the server is restarted on this version.
- The new behaviour applies to tickets already in flight. A ticket that loops back after the update rewinds the loop target's whole forward closure, so nodes that had already passed -- review gates, tests, documentation, and any `approval_gate` downstream of the target -- are dispatched or asked for again, and their earlier artifacts stay on the node next to the new ones (artifacts are only ever appended). Expect a ticket to stop for a repeat human approval after a late rejection, and expect a rewound gate to raise the same findings it raised before if the rework did not address them.
- If a ticket is blocked at an iteration limit from before the update, recover it with `grant-iterations` -> `reopen-nodes` (then `unstick-node` only if a node is still `IN PROGRESS`/`IN REVIEW`) as described above, rather than editing the database. This now works for a ticket whose loop target was left at `TODO` -- the shape produced by the old one-iteration-per-gate counting, which used to have no CLI recovery at all.
- **Check any script or automation that calls `complete-node`.** A verdict argument that is not exactly `true` or `false` is now a usage error instead of a silent pass, so a caller that has been passing the old `passed:`-prefixed form stops working -- which is the point, since it was recording the opposite of what it meant. Nothing else about the command changed: omitting the argument still passes, and `--reason` keeps its existing rule (rejections of an `approval_gate` only).
- **`complete-node` is no longer idempotent.** A repeat of a call that already succeeded now fails with `INVALID_NODE_STATE` rather than completing the node a second time. If a call's outcome is uncertain -- a connection dropped, a notification arrived twice -- read the node's status with `get-ticket` instead of running the command again.
- **A node sitting at a status that can no longer be completed is reached the usual way**: `get-executable` hands out an automatic node still at `TODO`, `unstick-node` releases one stuck at `IN PROGRESS`/`IN REVIEW`, and `reopen-nodes` redoes a completed one. The refusal message names all three, so no ticket in flight needs a database edit to get past the new check.
- **If you kept `artifactsDir` in a working-directory `graph-config.json`**, artifacts now go to the home config's value, or to `$HOME/.graph-ops/artifacts` if it does not set one. Artifacts already registered are unaffected -- their bytes are stored in the database and are read back from there -- but files under the old directory can no longer be registered as new HTML or image artifacts. To keep using that directory, move the `artifactsDir` line into `$HOME/.graph-ops/config.json` (or set `GRAPH_ARTIFACTS_DIR`) before starting the UI again.
- **Windows: an empty argument (`""`) can no longer be relayed**, because cmd.exe cannot store an empty string in an environment variable. When one is followed by further arguments, nothing runs and the shim exits with status 2 explaining why, rather than running a prefix of what you typed -- pass that value on stdin, with `-` in its place. A trailing empty argument is dropped instead, since it cannot be told apart from the end of the list. Previously `%*` relayed both.
- The two removed routes were undocumented and had no callers in this project. If you built something that polled `GET /api/tickets/{id}/executable-nodes` to drive a graph, use the CLI's `graph-engine get-executable <ticketId>` instead; if something read files from `/artifacts-static/`, use `GET /api/artifacts/{id}/content`.
- A request to an existing `/api/` path with the wrong method now answers `404 API_ROUTE_NOT_FOUND` instead of `405` with an `Allow` header -- a side effect of the catch-all that turns unrouted `/api/` paths into a JSON 404. "No such endpoint" and "wrong method" are no longer distinguishable from the outside.
- The narrowed `PATCH /api/nodes/{id}` is a compatibility change for any external caller that set `name`, `type` or `iteration_count`. Nothing in this repository did.
- **Check anything that calls `GET /api/tickets` without `project_id`.** It now returns `[]` instead of the shared current project's tickets. Its elements also changed shape in this release -- see the note on what `GET /api/tickets` returns below. Add `?project_id=<id>` if you want one project, or `?all=true` if you wanted everything -- the latter is the closest thing to "give me the list" that no longer needs a project. The Web UI shipped in this release already passes `project_id` on every request.
- **Your existing selection carries over by itself, once per environment.** The first time this version reads the current project in an environment whose home config has no `currentProjectId`, it copies the value from the database into `$HOME/.graph-ops/config.json` and uses that file from then on. There is nothing to run and no migration to schedule: open the UI (on a server restarted after the update, as in the first note), or run any command that needs the current project, and it happens. On a shared database every member's first start inherits the same value, which is whatever was selected last; from that moment each of them has their own, so expect to switch to your own project once after the update. If the database's value is empty, nothing is written -- a fresh install does not get a config file created for it.
- **The migration is one-way.** Once `currentProjectId` is in the file, the database's `app_state.current_project_id` is never read again -- and it is never written again either, so it stays at whatever it held when you upgraded. Downgrading to an earlier version therefore puts you back on that stale shared value, not on whatever you have selected since; you would re-select the project once, and be back to everyone sharing one. The table and the `Get/SetCurrentProjectID` storage methods are deliberately left in place, so a downgrade works, it just forgets. Nothing else in the database is touched, and no schema change is involved in either direction.
- **`GET /api/current-project` can write `$HOME/.graph-ops/config.json`, at most once.** That one write is the inheritance above, and it happens only when there is a selection to inherit. It is worth knowing if you monitor this server, put a proxy in front of it, or run it with a read-only home directory: a request that looks like a pure read does touch the file the first time, and never again. It writes a project ID that came from your own data source -- nothing from the request reaches the file.
- **If you relied on `graph-engine use-project` being visible to the whole team, it no longer is.** It sets your environment's current project only. The way to direct a command at a specific project regardless of environment is unchanged: pass `--project <projectId>` to `create-ticket`. Once the UI server has been restarted on this version (see the first upgrade note), the UI server and the CLI you run yourself always share it, whichever directories they were started from, because both read the same home config; a server left running from an earlier version still uses the database's shared value instead.
- **`GET /api/tickets` changed shape, so check anything that reads it.** Each element now carries `nodes` and `edges`, and no longer carries `artifacts`. Within this repository the only caller is the Web UI, which is updated with it -- the CLI subcommands go through the store directly -- but an external client of the HTTP API that read artifacts out of the list must now read them from `GET /api/tickets/{id}`, which is unchanged. There is no schema migration and no configuration change, and the custom data-source protocol is unchanged, so no data source implementation needs updating.

### Migrating a working-directory `graph-config.json`

If you have a `graph-config.json` in a directory you start graph-engine or the UI server from, nothing in it takes effect after this update, and startup prints one line naming the file. These three cases are what people actually hit; in all of them the fix is the same shape -- move the keys into `$HOME/.graph-ops/config.json` (creating it if it does not exist), or set the matching environment variables -- and then delete the old file to silence the warning.

- **If that file held your storage settings (`dbBackend`, `dbPath`, the MySQL connection fields, `httpDataSourceUrl`/`httpDataSourceToken`): your data is not gone.** Nothing was deleted, moved or rewritten -- the database that file pointed at is exactly as you left it. What happens is that graph-engine no longer reads that file, so with no storage settings in your home config it opens its built-in default instead: the SQLite file `$HOME/.graph-ops/graph.db`, which on a machine that has only ever used the repository's config is a new, empty database. **The symptom is a ticket list that looks empty** (or a project list, or a graph with nothing in it) even though startup succeeded and reported no error. Copy the storage keys from the old file into `$HOME/.graph-ops/config.json`, or export `GRAPH_DB_BACKEND` / `GRAPH_DB_PATH` / `GRAPH_HTTP_DATASOURCE_URL` / `GRAPH_HTTP_DATASOURCE_TOKEN` (and the MySQL variables) in the environment you start from, and your tickets are back on the next start. A `${ENV_VAR}` reference for the MySQL password or the data source token keeps working exactly as before, wherever the key now lives. If you would rather not edit JSON by hand, open the Web UI's Settings > App Settings, re-enter the storage settings there and save: that page now reads and writes the home config, and it names the file it saved to.
- **If you shared team settings through a `.graph-ops/` directory inside a repository** -- a `workflow.yaml`, `extensions/node-types/*.md`, `extensions/skills/*/SKILL.md`, review gates, templates -- they are no longer picked up. The team tier used to be found by walking up from the current directory; it is now only the directory `teamExtensionsDir` names in your home config (or `GRAPH_TEAM_EXTENSIONS_DIR` in your environment), and it has no default. To keep sharing them, put that directory somewhere every member can reach -- a checkout of a settings repository, a synced folder -- keeping the same layout (`workflow.yaml` at its root, `extensions/...` beneath it), and add `"teamExtensionsDir": "/absolute/path/to/it"` to each member's `$HOME/.graph-ops/config.json`. Anything you had written as per-project settings belongs in that same directory now: with the per-project scope removed, one shared directory is where team-wide node instructions, review gates and templates live. Settings that were only ever yours can equally go into your user tier (`$HOME/.graph-ops`), which needs no setting at all. Until one of those is done, agents run with the plugin defaults plus your user tier -- graph-engine will not tell you that a repository's `.graph-ops/` was skipped, because it no longer looks for one; `graph-engine get-node-type-context <nodeType>` shows what an agent is actually getting.
- **If that file held `projectPaths`**, every project's local path in this environment looks unset: `/graph-ops:ui` in a project directory opens the project setup dialog instead of that project, `create-ticket` falls back to the current project (or errors when there is none) instead of resolving one from the directory, and App Settings shows "Not set". Copy the `projectPaths` object into `$HOME/.graph-ops/config.json`, or simply set each path again from Settings > App Settings > project management, or by running `/graph-ops:ui` in the project's directory and choosing the existing project from the dialog. Paths now both save and load through the home config, so one that you set from any directory is found from every directory.

### Deliberate feature regressions

- **A team can no longer share database settings by committing them.** Putting `dbBackend: "mysql"` and the connection fields in a repository's `graph-config.json` -- with the password as a `${ENV_VAR}` reference, so "config in the repository, secret in the environment" was a workable arrangement -- no longer configures anything for anyone who clones it. This is accepted: each member writes those settings once into their own `$HOME/.graph-ops/config.json`, and it is the same path that let a repository nobody had read redirect where tickets and artifacts are stored.
- **Node and workflow settings can no longer differ per project.** There is one user tier and at most one team tier, both configured from your home config, so a workflow shape or a set of node instructions that applies to one repository only is no longer expressible. This was decided to be unnecessary rather than merely traded away.
