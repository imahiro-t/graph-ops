## Highlights

- **A failed review now rewinds the work in between, not just the loop target.** When a `review`/`review_gate` node fails and loops back, the engine used to change only two nodes: the loop target went back to `TODO` and the failing reviewer went to `AWAITING FIX`. Everything between them stayed `DONE`. In the default implementation+Gherkin shape (`test_review` looping back to `impl`) that had two consequences: `test_review` was handed out again in the very same `get-executable` call that reset `impl`, so the *previous* test run was judged a second time before the rework existed, and `code_review`, `qa_review`, `security_review`, `non_functional_review` and `gherkin_test` were never re-run at all -- an implementation that had never been tested or reviewed could reach `report` and `release_approval`. A loop-back now also resets every `DONE` node on a `success`-edge path from the loop target to the failing node, so `get-executable` offers the loop target first, then the rewound reviewers and tests, and only then the `AWAITING FIX` node. Nothing downstream of the failing node, and nothing upstream of the loop target, is touched.
- **`graph-engine grant-iterations` recovers a ticket blocked by an iteration limit.** `grant-iterations <ticketId> <nodeId1,nodeId2,...> [--extra <n>]` raises the given nodes' `max_iterations` by `n` (default 1, capped at 10 per call) and changes nothing else -- not their status, not their `iteration_count`, so the record of how many automatic attempts were already spent survives. Previously a ticket that hit its iteration ceiling had no defined way out: `reopen-nodes` refuses any call in which a node would exceed its budget, and the loop target is at its ceiling by definition in that state, so it always refused. The documented recovery is now three commands: `grant-iterations` (raise the budget) -> `reopen-nodes` (reset the loop target, clear `blocked`) -> `unstick-node` (release the reviewer that failed, which is still `IN REVIEW` because `reopen-nodes` only collects `DONE`/`REJECTED` nodes). An unknown node id, an id from another ticket, or an out-of-range `n` is an error that writes nothing. Like `reopen-nodes` and `unstick-node`, it is a CLI-only command; there is no HTTP API or Web UI equivalent.
- **`complete-node` no longer accepts a verdict it cannot read.** The pass/fail argument was decided by `passed = arg != "false"`, so every spelling that was not exactly `false` recorded a **pass**: the `passed:`-prefixed form the command's own help told people to write, along with `False`, `0`, `no` and any typo. A review that had failed was recorded as passed and the graph moved on, with nothing left to show where it went wrong. The argument is now exactly `true` or `false`; anything else is a usage error that exits non-zero and changes nothing -- no status, no artifacts, not even the `rejection_reason` artifact a `--reason` would have written. Omitting the argument still means `true`. The help and usage lines now read `complete-node <nodeId> [true|false] [--reason "<text>"]`.
- **A node can now only be completed from a state it can be completed from.** `CompleteNode` never looked at the node it was closing. A `DONE` node could be completed again with `false`, blocking a ticket whose work was finished; a `TODO` node nobody had run could be marked `DONE`; and because artifacts were written before anything else was decided, a bogus call left its artifacts behind either way. The engine now checks before it writes anything: an automatic node must be `IN PROGRESS` or `IN REVIEW` (the states `get-executable` hands out), a manual node (`approval_gate`, `release`) may also be completed from `TODO`, where approvals legitimately sit, and a node of a `CLOSED` ticket is refused regardless of its own status. Anything else fails with `INVALID_NODE_STATE` and writes nothing at all. Two things are deliberately *not* checked: the ticket's `blocked` flag and whether the node's prerequisites are `DONE` -- in a parallel graph, one branch's rejection would otherwise throw away a sibling node's legitimate, already-running work. Until now this rule lived only as a warning in the `process-ticket` skill, which anyone completing a node by hand walked straight past.
- **The same node is no longer handed to two agents, and two updates no longer overwrite each other's columns.** `get-executable` claimed a node by reading it and then writing it back, so two `get-executable` calls running at the same time could both be given the same node and do the same work twice. Claiming is now a single conditional `UPDATE`, and the caller that loses the race is simply not offered that node -- not an error, just an ordinary outcome of parallel execution. Separately, `UpdateNode` and `UpdateProject` wrote back every column they had read, so two updates touching *different* columns -- an assignee changed in the Web UI while `complete-node` changed the status -- ended with the later write restoring the other's old value. They now write only the columns the patch names. `updated_at` still always moves, even for a patch that names no columns.

## Changes

- **Which nodes a loop-back rewinds.** The set is the intersection of two closures over `success` edges: nodes reachable forward from the loop target, and nodes from which the failing node is reachable. The loop target and the failing node themselves are excluded, and only nodes currently `DONE` are reset. Two limits are deliberate: a node on that path that is `IN PROGRESS`/`IN REVIEW` is left alone (something is holding it; `unstick-node` is the way out if it stays that way), and sibling reviewers that *passed* keep their verdicts, because they are not on a path to the one that failed. An `approval_gate` on the path is rewound like any other node, so a human is asked to approve again after the rework.
- **Iteration counting is unchanged in meaning.** Only the loop target's `iteration_count` is incremented; the rewound nodes keep theirs, so an iteration still counts how many times the loop target was reworked.
- **Expect iteration budgets to be spent faster.** Because the rewound reviewers now actually run again, each of their failures loops back and spends another of the loop target's iterations. With the default `max_iterations: 3`, a ticket on the default workflow can reach its ceiling sooner than it did before this release; that is the point of the change, and `grant-iterations` is the way through it. A ticket that keeps exhausting its budget usually means the loop is not converging, so read the artifacts and verdicts before granting more retries.
- **Hitting the iteration limit still writes nothing.** When the loop target is already at `max_iterations`, the engine blocks the ticket and leaves every node exactly as it was -- the failing reviewer stays `IN REVIEW` rather than going to `AWAITING FIX`. The rewind set is computed after that check, so there is no half-rewound graph to reason about.
- **A loop-back now keeps the ticket's own status in sync**, as every other state-changing path already did. This is visible when a rewound `approval_gate` puts the ticket back into `IN REVIEW` (waiting on a human) instead of leaving a stale status behind.
- **`POST /api/tickets/{id}/nodes/{nodeId}/complete` now answers with a status that says which kind of failure it was.** Every failure used to be `400`. `INVALID_NODE_STATE` is now `409 Conflict` -- the request was valid and the row exists; what stands in the way is the state the row is in right now -- and an unknown node is `404` with `NODE_NOT_FOUND`. A client can now tell "you called this wrong" from "this cannot be done from here", which is the difference between fixing the call and re-reading the ticket.
- **The Web UI has a message for the new error.** `errors.INVALID_NODE_STATE` was added to both the `en` and `ja` locales. It appears when the same approval gate is handled in the Web UI and in a terminal at once, and it names the next step for someone looking at a screen (reload and see where the node actually is) rather than a CLI recovery command.
- **Which statuses a claim may move from is unchanged.** The conditional `UPDATE` excludes exactly `DONE`, `IN PROGRESS` and `IN REVIEW`, the same set the old in-memory filter used, so `TODO`, `AWAITING FIX` and `REJECTED` nodes are still claimable and the order `get-executable` returns nodes in has not changed.

## Known limitations

- **The rewind is not one transaction.** A loop-back writes the loop target, then each rewound node, then the failing node, as separate node updates. If the process dies or the database fails partway through, the graph is left partly rewound; `get-ticket` shows the actual state, and `reopen-nodes` / `unstick-node` bring it back. This is the same property the existing `ReopenNodes` (`reopen-nodes`) has always had -- the engine has no transaction handle to pass down -- so both are candidates for one fix later. Before this release a loop-back wrote 2 nodes; it now writes up to N+2, which makes the window wider without making it new.
- **Node claims are atomic on SQLite and MySQL only.** The protocol an HTTP data source implements has no conditional update, so against that backend graph-engine still claims with `GET /nodes/{id}` followed by `PATCH /nodes/{id}`, and a claim landing between the two is invisible to it: the same node can be handed out twice. A plugin cannot close this from its side -- the PATCH carries no expected-current-status to check against. One `process-ticket` session issues its `get-executable` calls one at a time, so the exposure is two sessions driving the same ticket at once; and if it does happen, the second agent's `complete-node` is refused with `INVALID_NODE_STATE`, so the work is duplicated but the record stays correct. The limitation is written on the `ClaimNode` interface and in the custom data source manual's "Atomicity" section.
- **Completing a node is still check-then-act.** The state check and the writes that follow it are not one transaction, so two callers completing the same node at the same instant can both pass the check. What this release removes is the path that produced that situation in practice -- the same node being dispatched to two agents. Closing the remainder needs a transaction handle the engine deliberately does not have (`internal/engine` is DB-independent pure graph logic), the same reason `ReopenNodes` and the loop-back rewind are not transactional either.
- **One `complete-node` failure still answers `400` without a code**: a node whose ticket row is missing. Foreign keys cascade node deletion with the ticket, so this needs an orphaned node to reach at all; every other failure of that endpoint now carries a code and a matching status.

## Documentation

- `graph-engine help` no longer implies that `reopen-nodes` can recover a ticket blocked by an iteration limit on its own. Its entry now says why it always refuses in that state, and the `grant-iterations` entry spells out the three-command recovery.
- The `process-ticket` skill documents the new loop-back behaviour where it describes `AWAITING FIX` (including the order `get-executable` hands nodes out in, the two deliberate limits, and the advice to confirm with `get-ticket` which nodes were actually rewound for graph shapes other than the ones the skill lists), and has a new "Recovery after an iteration limit" step, kept separate from the approval-gate rejection triage because the cause and the entry conditions differ.
- The `graph-node-agent` definition now says what a node agent must do when `complete-node` is refused with `INVALID_NODE_STATE`: do not retry it (the call is not idempotent and the refusal is not transient), read the node's real status with `get-ticket`, leave the recovery commands to the session driving the ticket, and never report a node as completed when the call was refused. The `process-ticket` skill's approval-gate step records that the engine now enforces the rule the step already asked for, as a safety net rather than a replacement for its `get-ticket` check.
- The custom data source manual gained a paragraph under "Atomicity" on claiming nodes, and the project README says in both its English and Japanese sections, where it describes the `dbBackend` setting, that this guarantee differs between the SQLite/MySQL backends and the HTTP one.
- `dev/mysql/README.md` now records what the MySQL suite costs and why: 4 to 5 minutes for all three TLS modes, about a third of it the four new concurrency tests. It also states the rule that goes with them -- the deterministic tests beside them pass against the pre-fix code, so those four are the regression detection, and lowering their round counts means redoing the check that the old code fails, on MySQL in particular (one of them can pass by luck on SQLite, where `SetMaxOpenConns(1)` narrows the window).

## Upgrade notes

- No migration, no configuration change: the database, existing tickets and all three storage backends (SQLite, MySQL, HTTP) are unaffected. Update from the `/plugin` menu, or run `claude plugin update graph-ops@graph-ops` in a terminal.
- The new behaviour applies to tickets already in flight. A ticket that loops back after the update rewinds the intermediate nodes, so nodes that had already passed will be dispatched again, and their earlier artifacts stay on the node next to the new ones (artifacts are only ever appended).
- If a ticket is blocked at an iteration limit from before the update, recover it with `grant-iterations` -> `reopen-nodes` -> `unstick-node` as described above, rather than editing the database.
- **Check any script or automation that calls `complete-node`.** A verdict argument that is not exactly `true` or `false` is now a usage error instead of a silent pass, so a caller that has been passing the old `passed:`-prefixed form stops working -- which is the point, since it was recording the opposite of what it meant. Nothing else about the command changed: omitting the argument still passes, and `--reason` keeps its existing rule (rejections of an `approval_gate` only).
- **`complete-node` is no longer idempotent.** A repeat of a call that already succeeded now fails with `INVALID_NODE_STATE` rather than completing the node a second time. If a call's outcome is uncertain -- a connection dropped, a notification arrived twice -- read the node's status with `get-ticket` instead of running the command again.
- **A node sitting at a status that can no longer be completed is reached the usual way**: `get-executable` hands out an automatic node still at `TODO`, `unstick-node` releases one stuck at `IN PROGRESS`/`IN REVIEW`, and `reopen-nodes` redoes a completed one. The refusal message names all three, so no ticket in flight needs a database edit to get past the new check.
