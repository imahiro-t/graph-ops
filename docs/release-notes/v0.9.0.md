## Highlights

- **One review iteration limit for the whole workflow, and review criteria that loosen round by round.** The limit on how many times a review may send work back is now a single workflow-wide setting, `max_iterations` (3, 4 or 5; 3 by default), counted in review rounds including the first review: with a limit of 3, a review runs at most three times, and a failure in the third round blocks the ticket instead of looping back again. `get-review-criteria` now tells the reviewer which round it is on and judges it at a matching tier -- Normal, then Important, then Final -- so a loop converges in a few rounds instead of repeating first-round strictness forever. A bug, regression or security problem newly introduced by the latest fixes is still judged as strictly as in the first round, at every tier.

## Changes

- **Workflow-wide `max_iterations`.** Set it at the top level of your user tier's `config.yaml` or a team tier's `workflow.yaml` (the team tier wins over the user tier), or in the Web UI: Settings → Review Gates now has a "Review iteration limit (rounds)" selector offering Inherit, 3, 4 and 5 above the gate list. Any other value is rejected -- a hand-edited file with an invalid value makes `get-executable`, `expand-graph` and `get-workflow-catalog` fail with an error naming the file and the value, and the settings API answers `400 INVALID_MAX_ITERATIONS`. The plugin default workflow sets `max_iterations: 3` at the top level. `get-workflow-catalog` now includes the resolved `max_iterations`.
- **The limit is stored on each node when the graph is built.** Changing the setting later does not affect tickets already in progress. The seed nodes (`plan`, `plan_review`) take the value in effect when the seed is created, the rest of the graph the value in effect at `expand-graph`. `grant-iterations` still raises the limit of individual nodes.
- **Convergence tiers by round.** `get-review-criteria` now prints the gate-specific criteria (for a `review_gate`), then a line `Review round: <r> / <limit> — tier: <Normal|Important|Final>`, the tier's definition, and the rules no tier relaxes. `review` and `review_gate` nodes are treated the same way. The round is the loop target's `iteration_count + 1`; a review with no loop target is always round 1. Tiers by limit:

  | Limit | Normal | Important | Final |
  |---|---|---|---|
  | 3 | round 1 | round 2 | round 3 |
  | 4 | rounds 1-2 | round 3 | round 4 |
  | 5 | rounds 1-2 | rounds 3-4 | round 5 |

  Normal fails a review for anything that needs fixing. Important fails it only for correctness bugs, unmet completion criteria, security problems or regressions, and records minor and style points as carry-over items instead. Final fails it only for critical bugs, security vulnerabilities, data corruption or unmet completion criteria. Every round granted past the original limit with `grant-iterations` is Final. At every tier, a bug, regression or security problem newly introduced since the previous round is judged as strictly as at Normal, and a serious issue flagged earlier that is still unfixed fails the review.
- **From round 2 on, reviewers look at their previous review and the changes since.** `get-review-criteria` says so from round 2, and the `review` / `review_gate` node-type instructions and the `graph-node-agent` now spell it out: fetch the node's previous review artifact and the diff since it (`git log` / `git diff` for code; the difference between the loop target's latest artifact and the one reviewed last time for a document) before judging.
- **Carry-over items go under the review template's last heading.** A point recorded without failing the review is written there with the unconditional-approval verdict, not turned into a conditional approval that requires code changes (nothing sends the work back to the implementation node from an approval). The review template's headings and verdict words are unchanged; only the guide text of its last heading now mentions carry-over items, in both the English and the Japanese template.

## Behavior changes

- **Tickets already in progress block one round earlier.** The limit used to be checked as "more rework than `max_iterations`", so a limit of 3 let a review run a fourth time. It is now checked in rounds: the review that fails in round `max_iterations` blocks the ticket. This applies to existing graphs as soon as you upgrade, because they are judged against the `max_iterations` already stored on their nodes.
- **`reopen-nodes` refuses a loop target one round earlier too.** For a node that some review loops back to, the check is now `iteration_count + 1 >= max_iterations`, matching the round meaning; every other node keeps the old check. Without this, reopening the loop target right after a round-limit block would start a round past the limit with no `grant-iterations` at all. The same comparison applies when you reopen an implementation node after an approval-gate rejection, so that path can now be refused where it used to succeed. When it is refused, run `grant-iterations` on the loop target first and then `reopen-nodes`; granting `k` lets exactly `k` more rounds run.

## Migration

- **Per-gate `max_iterations` is ignored.** A `max_iterations` under a review gate in your user or team tier, or in an `expand-graph` patch's inline gate, no longer has any effect. The CLI prints a `graph-ops: warning: ...` line on stderr naming the gate whenever it loads the catalog (`get-executable`, `expand-graph`, `get-workflow-catalog`); stdout and the exit status are unchanged. The Web UI's Review Gates tab shows the same warning for your user tier, and saving from that tab removes the per-gate values from `config.yaml`. The per-gate "Max Iterations" field is gone from the Web UI. Move the value to the top-level `max_iterations` (3, 4 or 5); a team tier's `workflow.yaml` has to be edited where it lives.

## Documentation

- The `process-ticket` skill describes the limit in rounds and the recovery after a round-limit block: the loop target stays at `iteration_count = max_iterations - 1`, and `grant-iterations +k` followed by `reopen-nodes` adds `k` rounds, all judged at the Final tier.
- `authoring-format.md` documents the round and tier `get-review-criteria` reports, the `onboarding` skill no longer mentions a per-gate `max_iterations`, and the README (English and Japanese) describes the workflow-wide limit in place of the per-gate one.
