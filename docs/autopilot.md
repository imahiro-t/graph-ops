# Autopilot

The autopilot takes a ticket from refinement to release without a person in the loop: `/graph-ops:autopilot-ticket` does it for one ticket, and `/graph-ops:autopilot-tree` does it for a ticket and then every ticket derived from it (its descendants, including the ones created along the way). This page is the reference: how a run works, the settings, the branch strategy, the `graph-engine autopilot` CLI, the HTTP API, the error codes, and the things to be careful about. The [README](../README.md#autopilot) has the short version.

## How a run works

A run has two kinds of Claude Code sessions:

- **The orchestrator** is the session you start the command in (or, from the Web UI, a session opened for you in a new terminal). It does no ticket work itself. It calls `graph-engine autopilot start`, then repeatedly `graph-engine autopilot next` and runs exactly the command `next` hands back, and finally prints `graph-engine autopilot summary`. Every decision -- which ticket comes next, the limits, skips, failures, merges -- is made by `graph-engine`, and each answer is one short JSON line, so the orchestrator keeps only a few hundred bytes per ticket. That is what lets one orchestrator drive a tree of 20 or more tickets.
- **Child sessions** do the work, one ticket at a time, each in a new terminal opened the same way as the Web UI's "Launch Claude" buttons (see [Troubleshooting](../README.md#troubleshooting) for how the terminal is chosen) -- except that in macOS's Terminal.app, a child session opens as a new tab of the orchestrator's window (see [Terminal.app: child sessions as tabs](#terminalapp-child-sessions-as-tabs)). A child session runs the internal `autopilot-worker` skill, which follows `refine-ticket` and `process-ticket` but replaces every point where those skills wait for a person with an automatic decision. A child session has one of three roles:
  - `work`: refine the ticket (only if it has not been refined and has no nodes yet), run its execution graph, release it (see [Branches](#branches)), decide which open items become follow-up tickets, and report.
  - `merge-up`: merge a finished subtree into its parent's branch when a fast-forward was not possible.
  - `finalize`: bring the tree root's branch into the main branch once the whole tree is done.

  When a child session ends, it reports its result (`done`, `failed` or `blocked`, a reason code, and a summary of at most three lines) with `graph-engine autopilot report`, tells you its terminal can be closed, and stops. Child terminals are not closed automatically.

Tickets are processed strictly one at a time within a run. Processing several tickets of one tree in parallel is not supported.

## Terminal.app: child sessions as tabs

On macOS, when no `terminalCommand` is set and the orchestrator is not inside tmux, the terminal is Terminal.app. There, every child session of a run -- `work`, `merge-up` and `finalize`, for the root, its children and their descendants at any depth -- opens as **a new tab of the Terminal.app window the orchestrator runs in**, instead of one new window per session. A run's sessions stay together in one window. tmux, a custom `terminalCommand` (iTerm2, WezTerm, ...), Windows, and Terminal.app launches outside the autopilot (the Web UI's "Launch Claude" buttons, and the orchestrator the Web UI's "Autopilot" button opens) are unchanged: they still open a new window.

**How the window is found.** When a run is started (`autopilot start`, including a takeover of an interrupted or stopped run, and the orchestrator adopting a run the Web UI reserved), `graph-engine` looks up the tty of the Terminal.app tab the orchestrator runs in (for example `/dev/ttys003`) with `ps`, walking up from its own process. This needs no permission, and is done only when `TERM_PROGRAM` is `Apple_Terminal` and `TMUX` is empty. The tty is kept in the run file as `terminal_tty`, and every later launch of the run -- including after resuming -- opens its tab in the window that has a tab on that tty. A takeover or an adoption replaces it with the new orchestrator's tty (or with nothing, when the new orchestrator is not in Terminal.app), so a tty left over from an earlier orchestrator is never used. The Web UI server itself never records a tty.

**Permissions.** Terminal.app has no scripting command that opens a tab, so `graph-engine` runs a fixed AppleScript with `osascript` that brings the window to the front and sends Cmd+T through System Events, then runs the session's command in the new tab. The new tab is recognized by its tty, which no tab of any Terminal window had before the Cmd+T, and only when it belongs to the orchestrator's window (current macOS reports each tab of a window to AppleScript as a window of its own, sharing the window's bounds; that is how it is matched: the new tab's window counts as the orchestrator's when its left, top and right edges are each within 4 points of the orchestrator's window, checked for about 2 seconds -- the bottom edge is not compared, because it moves when the tab bar appears). That needs two macOS privacy permissions for the app the orchestrator runs in (Terminal.app): **Accessibility** (to send the keystroke) and **Automation** (to control Terminal and System Events). macOS may ask for them the first time a tab is opened; you can also grant them beforehand in System Settings > Privacy & Security. Without them the sessions still open, in new windows (see below). The wording of the macOS prompts varies between versions; what matters is that Terminal is allowed both.

**Terminal comes to the front on every tab launch.** Opening a tab means bringing the orchestrator's Terminal window to the front and sending it a keystroke, so each child session's launch takes the focus away from whatever app you are using at that moment. Another app being in front does not stop it: on macOS 26.3, with the screen unlocked, Terminal came to the front within 0.25 seconds every time it was tried with another app in front, and with a child tab selected in the orchestrator's window. `graph-engine` sends Cmd+T only after it has seen Terminal frontmost with that window in front, and then waits about 0.2 seconds before sending it (giving Terminal time to be ready to open the tab); if you switch apps during those 0.2 seconds or so between that check and the keystroke (plus the up to 1 second it takes to read the frontmost app for the record, normally a few tens of milliseconds), the Cmd+T can still reach another app or window, in which case no new tab appears in the orchestrator's window and the session opens in a new window instead (an empty tab may be left where the keystroke went).

**While the screen is locked, no tab is tried.** Right before the tab script, `graph-engine` reads whether the screen is locked (`ioreg -n Root -d1 -a`: `CGSSessionScreenIsLocked` in this user's `IOConsoleUsers` session; a read only, bounded to 2 seconds, normally about 40-60 ms). When it is, the session opens in a new window at once, without running the script: while the screen is locked macOS lets no app but loginwindow come to the front, so Terminal cannot be brought forward by any means, and a Cmd+T would be typed into the lock screen instead. The screen counts as locked only when that key is `true` (or `1`); when it is missing or cannot be read, the tab is tried as before, so a misread can only leave things as they were before this check, never turn a launch that could have used a tab into a window. This is a limitation of macOS, not something `graph-engine` can work around; see [Fallbacks while the screen is locked](#fallbacks-while-the-screen-is-locked).

**When a tab is not used, the session opens in a new window** (the same `open -a Terminal <script>.command` as before), and the launch itself does not fail on the tab's account; only when the new window cannot be opened either does `launch` fail as before. Each launch that tries a tab and fails, gives up waiting for the tab lock (the lock row below), or finds the screen locked (the screen-lock row below), falls back with one warning to the orchestrator's stderr, `graph-engine: warning: the <role> session of <ticket> opened in a new Terminal window because a tab could not be opened (<reason>; <kind>, after <phase>, an empty tab may be left, frontmost app "<app>", the screen was locked by then)` (the parts after `<reason>` are left out when they do not apply: the frontmost app appears when the script read it as it gave up, and "the screen was locked by then" when the screen, read again after a failed tab, had been locked meanwhile; see [Tracing each fallback](#tracing-each-fallback) for the kinds and phases), it is recorded in the run file's `terminal_tab_failures`, and the one-line JSON on stdout is unchanged. When no tab is tried at all, nothing goes to `terminal_tab_failures` and no such warning is printed: when no tty was found (the first row below), and for the launches after the tab has been disabled for the run (the last row below; the launch that disabled it has already warned, saying so). Those launches are counted by reason in the run file's `terminal_window_launches` instead, and the first launch of an orchestrator that goes to a new window because the tab is disabled prints one more line, `graph-engine: warning: the <role> session of <ticket> opened in a new Terminal window without trying a tab: run <runId> disabled the tab earlier (<reason>); so do its later sessions`; the later ones print nothing. There are two kinds of fallback:

| Condition | What happens next |
| --- | --- |
| No tty was found when the run started: `ps` failed or was refused (for example by a sandbox around the orchestrator's commands), or the orchestrator is not in a Terminal.app tab. | Every session of the run opens in a new window, with no attempt and no warning. Why no tty was found is kept in the run file as `terminal_tty_reason`. |
| The screen was locked when the launch was about to run the tab script (read after taking the tab lock, since the screen may lock while a launch waits for it). No script runs, so Terminal is not activated and no keystroke is sent. | This launch opens a new window at once (with the warning above, kind `screen-locked`); the tab is not disabled, and the next launch reads the screen again and tries the tab once it is unlocked. |
| No Terminal window has a tab on the recorded tty any more (the orchestrator's tab or window was closed), or the window went away while the tab was being opened. | This launch opens a new window; the next launch tries the tab again. |
| Terminal did not come to the front with the orchestrator's window in front within about 2 seconds. No keystroke is sent. Every one of these in the v0.11.1 runs looked into happened while the screen was locked (see [Fallbacks while the screen is locked](#fallbacks-while-the-screen-is-locked)), which the row above now catches before the script runs; with the screen unlocked, another app in front did not cause it. | This launch opens a new window; the next launch tries again. |
| No new tab appeared within about 6 seconds of Cmd+T, nor in one more look 2 seconds later, it closed before the command could be run in it, or it opened in another Terminal window than the orchestrator's (the Cmd+T reached another window: its left, top or right edge stayed more than 4 points away from the orchestrator's window for about 2 seconds). The command is not run in it. The error message then gives both windows' bounds, and, when reading Terminal's tabs failed while waiting for the new tab, the last such error. | This launch opens a new window; the next launch tries again. A tab that opens late, or in another window, is left empty for you to close; `graph-engine` does not close it because a late tab may appear only after the tab script has finished and Terminal's scripting has no command that closes a single tab: typing `exit` into it does not close it under every profile and would mean typing into a tab the launch never confirmed as its own, and closing a window could close one of yours. The empty tab runs nothing but an idle shell. A tab that appears only in the last look 2 seconds after the 6-second wait is used as usual (the session runs in it, no new window opens), and is counted in the run file's `terminal_late_tabs` with one line on stderr, `graph-engine: warning: the <role> session of <ticket> opened in a new Terminal tab that appeared only after the usual wait`. |
| More than one new tab appeared in Terminal at once (another run, or you, opened a tab in any Terminal window at the same moment), so the new tab cannot be told apart. The command is run in none of them. | This launch opens a new window; the next launch tries again. The tab this launch opened is left empty among them, for the same reason. |
| For 25 seconds after this launch started waiting for the tab lock, other `graph-engine` processes (one, or several taking the lock between them) kept holding it while opening their Terminal tabs (see the lock below). | This launch opens a new window without running the tab script (with the warning above); the next launch tries again. |
| `osascript` did not finish within 20 seconds **after both Terminal and System Events had answered** (phase `system-events-ok` or later, see [Tracing each fallback](#tracing-each-fallback)): Terminal is answering slowly, not waiting for a permission. | This launch opens a new window; the next launch tries again. The second such timeout in a row disables the tab for the rest of the run (as in the next row), so a Terminal that stays slow does not cost 20 seconds on every launch. "In a row" counts only these timeouts: the count goes back to 0 only when a tab opens, and the other failures of this table leave it as it is. It is kept in the run file as `terminal_tab_slow_timeouts`. |
| Anything else: a missing Accessibility permission (macOS reports it as error 1002, "osascript is not allowed to send keystrokes") or Automation permission, a sandbox that refuses Apple events, `osascript` missing or failing in any other way, `osascript` not finishing within 20 seconds **before both Terminal and System Events had answered** (no phase, or phase `window-found`: for example while a permission prompt is left unanswered), or Terminal's state that cannot be read at all while waiting for it to come to the front. | This launch opens a new window, and **the tab is disabled for the rest of the run**: the warning of this launch says so, and later sessions go straight to new windows: the first of them prints the one line `... without trying a tab: run <runId> disabled the tab earlier (<reason>); so do its later sessions` (once per orchestrator), and the rest print nothing. |

The script's own failures (the third to sixth rows) all happen before the session's command is run, so a fallback never starts a session twice. A timeout is different: `osascript` is killed wherever it is, and one killed while the command was being sent to the new tab (phase `command-sending`) may have started the session in that tab as well as in the new window; its message says so.

**How timeouts are told apart.** The first Apple event to Terminal and the first one to System Events each wait for their Automation permission prompt, and a prompt nobody answers holds `osascript` until the 20-second limit. So a timeout before both have answered (no phase, or `window-found`) is taken as a permission prompt and disables the tab at once, as every timeout did before. That also takes in a Terminal that is merely slow between the two: after `window-found` the script still reads Terminal's tabs and brings the window to the front before its first event to System Events, and a timeout there disables the tab at once too, although Terminal may only have been slow. The record's `phase: window-found` shows which launch it was. From `system-events-ok` on, both permissions are known to be granted, so a timeout counts as a slow Terminal (the row above).

**Why tabs used to fall back so often.** Before v0.11.1 the script looked for the orchestrator's window, and for the window the new tab belongs to, with one Apple event per tab of every Terminal window. Each tab counts as a window, so with 20-30 tabs of busy `claude` sessions a launch could run past 15 seconds, and every timeout disabled the tab for the rest of the run: after one slow moment, all later sessions of a large tree opened in new windows. A timeout after Cmd+T also left the new tab empty, and an exact comparison of the window bounds sent some tabs that did open in the right window to a new window (9102), leaving them empty too. The script now reads all windows' ids and tabs' ttys in two Apple events (plus one to confirm the match), so its time no longer grows with the number of tabs; timeouts are told apart as above, and bounds are compared within 4 points. The fallbacks themselves are unchanged. The fallbacks that remained after that came from a locked screen; see [Fallbacks while the screen is locked](#fallbacks-while-the-screen-is-locked).

**The per-run disable.** When a tab is disabled, the reason (when longer than 300 characters, cut to 300 followed by `...`) is kept in the run file as `terminal_tab_disabled`, so the rest of the run does not wait for the same failure on every launch. It is cleared, and the tab tried again, when the run is taken over (running the same command again after an interruption) or adopted by a new orchestrator. So after granting a missing permission, interrupting the orchestrator and running the same command again brings the tabs back for that run. A `launch` that failed altogether (not even a new window opened) never disables the tab.

**One tab at a time across processes.** Tab launches are serialized through a lock on `$HOME/.graph-ops/autopilot/terminal-tab.lock` (an advisory `flock`, released when the process ends, so a crash never leaves it held), held only while the screen lock is read and `osascript` runs (at most about 22 seconds: 2 for the screen lock, 20 for `osascript`; the second read of the screen lock after a failed tab comes after the lock is released). Two runs whose orchestrators share a window therefore do not open their tabs at the same moment; a launch that waits more than 25 seconds for the lock falls back as in the table. The lock wait is longer than what one holder can keep it, so a launch waiting for one holder does not give up while that holder's `osascript` can still finish. If the lock file cannot be created, the tab is tried without the lock -- identifying the new tab by its tty, and refusing when there is more than one, is what keeps a command out of the wrong tab.

The wait covers one holder only. The lock is held by one launch at a time, so when several launches wait at once their waits effectively add up, but there is no queue: when the lock is released, whichever waiting launch tries first takes it, not the one that has waited longest. Each waiting launch counts its 25 seconds from when it started waiting, so if other launches keep taking the lock in between, any of the waiting launches (not necessarily the last to arrive) can fall back to a new window as in the table -- with the one-line warning, the tab not disabled, and the next launch trying the tab again. This is intended, and the wait is deliberately not extended with the number of waiting launches:

- An `osascript` normally finishes in a few seconds, so the lock comes free every few seconds, and with the few launches that usually wait at once, a waiting launch normally gets it within 25 seconds. This is not guaranteed: with no queue, a launch can keep missing the lock while others take it.
- The wait runs out when the `osascript` runs of the launches that take the lock while it waits add up to more than 25 seconds: one running close to its 20-second limit (a permission prompt left unanswered, for example), several failing after several seconds each (Terminal not coming to the front, no new tab appearing), or an unusual number of launches waiting at once. Most of these mean something is wrong with Terminal, and the waiting launch's own tab would then most likely fail for the same reason. Either way, the launch still opens its session in a new window.
- A wait that grew with the number of waiting launches would make a launch's worst case (about 59 seconds, below) grow in proportion and hold up the orchestrator for longer; a bounded wait keeps it fixed.

**How long a launch can take.** In the worst case, `launch` waits up to 25 seconds for the lock, up to 2 seconds to read the screen lock, up to 20 seconds for `osascript`, up to 2 seconds to read the screen lock again after a failed tab, and up to 10 seconds for `open -a Terminal`, about 59 seconds in all (about 45 seconds before v0.11.1: 20 + 15 + 10), however many launches are waiting for the lock. This happens outside the run registry's lock, so other commands are not held up.

Inside `osascript`, the fixed waits add up to about 12.2 seconds: about 2 seconds for Terminal to come to the front, 0.2 seconds before Cmd+T, about 6 seconds for the new tab, 2 seconds before the last look, and about 2 seconds to check the new tab's window bounds. The reads made only for the record are bounded to 1 second per Apple event: the frontmost app just before Cmd+T (on every launch) and, before a 9103 or 9102, at most four more. So even on the longest path -- a tab found only in the last look and then failing the bounds check -- the bounded parts stay under about 17.2 seconds; the 20-second limit leaves the rest for starting `osascript` and the reads that have no bound of their own. When every read ran into its 1-second bound, Terminal or System Events would be answering so slowly that the unbounded reads would use up the 20 seconds first anyway, which is the slow Terminal the slow-timeout count is meant to catch.

### Fallbacks while the screen is locked

Even with the changes above, a tree run on macOS 26.3 (17 launches) still opened 8 of its child sessions in new windows: 6 with 9103 (`phase: system-events-ok`) and 2 with 9102 (`phase: keystroke-sent`), sporadically, each followed by launches that used tabs again. Matching each launch's time against loginwindow's log of the screen lock (`-[LWScreenLock setScreenIsLocked:] setting to 1/0`) showed that all 7 launches made while the screen was locked had failed, and that only 1 of the 10 made while it was unlocked had. The pattern "now and then, and then tabs again" was you leaving the Mac (the screen locking, by hand or by the screen saver or display sleep) and coming back.

- **9103 while the screen is locked.** While the screen is locked, macOS lets only loginwindow come to the front; the unified log shows Terminal being refused (`launchservicesd: Application App:"<Terminal> ... tried to be brought forward, but isn't in fPermittedFrontApps ( ... "loginwindow" ... ), so denying.` and `WindowServer: [SetFrontProcessWithInfo]: CPS: Denying <Terminal> the right to be in front because it is not in the list of permittedFrontASNs`, with Terminal's name as the system's language gives it). The tab script's `activate` and `set frontmost`, and the fallback's `open -a Terminal` too, are all refused, so the 2-second wait for Terminal to come to the front runs out. In all 6 cases, the app in front when the screen locked was not Terminal (a browser in 5, Mail in 1).
- **9102 while the screen is locked.** When Terminal itself was in front as the screen locked, System Events still reported Terminal frontmost with the orchestrator's window in front, so the script went on and sent Cmd+T -- which reached the lock screen (loginwindow), not Terminal, and opened no tab.
- **9102 with the screen unlocked.** One launch, the first of the run: Cmd+T reached Terminal, but no new tab's tty appeared within the 6-second wait (one normally appears within 0.15-0.22 seconds). The tab most likely opened late (one more terminal session than expected was logged in that minute), but this was not reproduced and the cause is not known.
- **Ruled out.** With the screen unlocked, another app in front did not keep Terminal from coming to the front (9 tries, each within 0.25 seconds), nor did a child tab being selected in the orchestrator's window. Opening the tab through Terminal's "New Tab" menu item over Accessibility, without bringing Terminal forward first, is no alternative: while Terminal is not the active app, it opens a new window (and brings Terminal forward anyway).

So now the screen lock is read before the tab script (see [While the screen is locked, no tab is tried](#terminalapp-child-sessions-as-tabs)): a locked screen opens the session in a new window at once, as kind `screen-locked`, with no 2-second wait and no Cmd+T typed into the lock screen. For the unexplained late tab, the script takes one more look 2 seconds after its 6-second wait and uses a tab that appears then, and every failure records what the script saw (see [Tracing each fallback](#tracing-each-fallback)), so that a next occurrence can be told apart.

**Known limitation: a locked screen opens sessions in new windows.** The intent is that child sessions always open as tabs under normal conditions -- the permissions granted and the orchestrator's window still open -- even while you are working in another app. Counting a locked screen as outside those normal conditions is an interpretation made for DFLT-00362; the wording of that intent does not mention the screen lock. The reasons:

1. While the screen is locked, macOS itself lets no app but loginwindow come to the front, and bringing Terminal to the front is what opening a tab depends on. No way of activating Terminal works then (`activate`, `set frontmost` and `open -a Terminal` were all refused in the log).
2. Neither a keystroke nor the menu works instead: a keystroke goes to the lock screen, and the "New Tab" menu item opens a new window while Terminal is not active.
3. "While you are working in another app" means you are at the Mac and another app is in front, which macOS allows Terminal to take over. With the screen locked you are not there, and a macOS security restriction is in force: a different state, not a contest between apps.
4. Where macOS rules a tab out, the plan was to document it as a known limitation rather than work around it.

If sessions should open as tabs even while the screen is locked, the direction would be to wait for the screen to be unlocked before opening them. That was not done: the locks seen lasted from 30 minutes to 1 hour 46 minutes, and a wait would hold up the run for that long, and need a bound past which it opens a window anyway.

**How sure the screen-lock check is.** On macOS 26.3, `CGSSessionScreenIsLocked = true` was seen in `ioreg` while the screen was locked and no such key while it was unlocked; `graph-engine`'s reading returned `locked` and `unlocked` for them, and a real launch made while the screen was locked fell back as `screen-locked` without running `osascript`. Other macOS versions have not been checked. A misread falls on the side of trying the tab (see above), so it at worst brings back the 9103 / 9102 of a locked screen. To check it on another Mac, or after the fact, compare the times of a run's launches with loginwindow's log of the screen lock:

```bash
/usr/bin/log show --start "<YYYY-MM-DD HH:MM:SS>" --end "<YYYY-MM-DD HH:MM:SS>" \
  --predicate 'process == "loginwindow" AND eventMessage CONTAINS "setScreenIsLocked"'
```

Launches made while the screen was locked (`setting to 1` until the next `setting to 0`) should be in `terminal_tab_failures` as `screen-locked`; a 9103 or 9102 made while it was locked whose `diagnostics.screen_lock` is `unlocked` or `unknown` means the check missed it; a `screen-locked` record made while the screen was unlocked means it saw a lock that was not there.

### Tracing each fallback

Every launch that tried a tab and fell back to a new window, and every launch that did not try it because the screen was locked, is recorded in the run file (`$HOME/.graph-ops/autopilot/<projectId>/runs/<runId>.json`) under `terminal_tab_failures`, at most 50, oldest first (which ones are dropped beyond 50 is below). It is not shown by `autopilot status` or the Web UI, and it is not shared with other members; read the run file itself, for example with `jq '.terminal_tab_failures' <run file>`. Each entry has:

| Field | Meaning |
| --- | --- |
| `at`, `ticket_id`, `role` | When, and which session's launch. |
| `kind` | `script-error` (the script ended with an error: 9101-9104, a permission error, ...), `timeout` (`osascript` was killed at 20 seconds), `lock-busy` (the tab lock stayed busy for 25 seconds, so no script ran) or `screen-locked` (the screen was locked, so no script ran; see [Fallbacks while the screen is locked](#fallbacks-while-the-screen-is-locked)). For `lock-busy` and `screen-locked`, `phase` and `error_number` are empty and `keystroke_sent` is false. |
| `error_number` | `osascript`'s error number, when it reported one (9101-9104 are the rows of the table above; -1743 is a missing Automation permission, 1002 / -25211 / -1719 a missing Accessibility permission). Left out for a timeout. |
| `message` | The reason the warning gave (at most about 300 characters). A timeout's message says where it stopped and what may have been left behind. |
| `phase` | The last phase the script reached (below); left out when it reached none. |
| `keystroke_sent` | `true` when Cmd+T had definitely been sent. |
| `disabled_run` | `true` when this launch disabled the tab for the rest of the run (`terminal_tab_disabled` then holds the same reason). Always `false` for `screen-locked`. |
| `diagnostics` | What the launch saw around the failure (below); left out when nothing was read (`lock-busy`, and records written before DFLT-00362). |

`diagnostics` holds whichever of these were read; a key is left out when it was not:

| Key | Meaning | Recorded for |
| --- | --- | --- |
| `screen_lock` | The screen lock read right before the tab script: `locked`, `unlocked` or `unknown` (the key missing reads as `unlocked`; `unknown` is a read that failed or could not be parsed). | Every record but `lock-busy`. For `screen-locked` it is the only key, and is `locked`. |
| `screen_lock_after` | The same, read again after the tab failed. `locked` here with `unlocked` before means the screen locked while the script ran (the warning then adds "the screen was locked by then"). | Every launch that ran the script and failed (9101-9104, permission and other script errors, timeouts). |
| `frontmost_app` | The frontmost app as System Events saw it when the script gave up. | 9103 and the three kinds of 9102 (no new tab, the new tab closed, the new tab in another window). |
| `front_window_id`, `front_window_bounds` | Terminal's front window when the script gave up. | The same. |
| `target_window_id`, `target_window_bounds` | The orchestrator's window. | The same. |
| `frontmost_app_before` | The frontmost app just before Cmd+T. | Failures that got as far as Cmd+T (9102, 9104, a 9101 after Cmd+T, a timeout after Cmd+T). |
| `tabs_before` | How many Terminal tabs had a tty before Cmd+T (many tabs make Terminal's answers slower). | The same. |
| `late_tab` | `true` when the new tab was found only in the last look 2 seconds after the wait, and the launch failed after that (a 9102 for mismatching bounds, for example). | Those launches only. |

The app names and window values come from the script's `graph-ops-diag: <key>=<value>` lines on stderr (taken out of the message like the phase lines); line breaks in an app name are turned into spaces before it is logged, and every value is cleaned of control and invisible characters and cut to 128 characters. Each of those reads is bounded to 1 second and wrapped so that a failed read never replaces the script's own error. `tabs_after` was in early builds of DFLT-00362 and is no longer written; whether a tab opened late is told by `late_tab` and `terminal_late_tabs`.

**Which records are dropped beyond 50.** When a new record makes more than 50, the oldest `screen-locked` record among those that were there before it is dropped; when there is none, the oldest record is. The new record itself is never dropped, so the latest launch is always recorded, a `screen-locked` one included. `screen-locked` records are kept one per launch, rather than only counted, because their times are what can be compared with loginwindow's log; dropping them first keeps a long screen lock during an overnight run from pushing out the failures of tabs that were tried (9101-9104, timeouts). A row of `screen-locked` launches drops at most one such failure: the one that makes room for the first of them.

**Telling a 9102 apart.** With `diagnostics`:

- `frontmost_app_before` and `frontmost_app` differ, or `front_window_id` is not `target_window_id`: the Cmd+T may have reached another app or window (you switched apps at that moment).
- `screen_lock_after` is `locked`: the screen locked while the script ran (between the screen-lock read and Cmd+T there are up to about 3.2 seconds of fixed and bounded waits -- about 2 seconds for Terminal to come to the front, 0.2 seconds, and up to 1 second reading `frontmost_app_before` -- plus starting `osascript` and finding the window).
- Neither, and the message says no new tab appeared: the tab did not open within the 6-second wait and the last look 2 seconds later. Whether tabs open late at all is told by `terminal_late_tabs`: as long as it stays absent (no tab has been saved by the last look), the guess that the unexplained 9102 was a late tab has nothing to back it.

`terminal_tab_slow_timeouts` is the count of slow timeouts in a row described in the table. Three more fields describe launches that are not in `terminal_tab_failures`:

| Field | Meaning |
| --- | --- |
| `terminal_tty_reason` | Why the current orchestrator has no `terminal_tty`: `term-program` (not in Terminal.app), `tmux`, `not-darwin`, `ps-failed`, `ps-unparsable`, `invalid-tty` (what `ps` gave is not a `/dev/ttysN`) or `not-found`. Left out when there is a tty, and on a run the Web UI reserved that no orchestrator has adopted yet. |
| `terminal_window_launches` | The launches that opened a new window without trying a tab, counted by reason: `not-darwin`, `terminal-command`, `tmux`, `tab-disabled` (the tab was disabled for the run), `no-tty` or `invalid-tty`. Each reason has `count`, `first_at`, `last_at` and `last_ticket_id`. `screen-locked` launches are not counted here; they are in `terminal_tab_failures`. |
| `terminal_late_tabs` | The tabs found only in the last look 2 seconds after the 6-second wait (each would have been a 9102, an empty tab plus a new window, before), with the same `count`, `first_at`, `last_at` and `last_ticket_id`. |

A takeover or an adoption resets `terminal_tab_slow_timeouts` to 0, clears `terminal_tab_disabled`, `terminal_window_launches` and `terminal_late_tabs`, and sets `terminal_tty_reason` for the new orchestrator, since they describe the current orchestrator's launches (counts from before a takeover are not kept); it keeps `terminal_tab_failures`, whose history spans the run's orchestrators. All of these stay in the local run file and are left out of the copy shared with other members.

The script logs its progress as `graph-ops-phase: <phase>` lines on `osascript`'s stderr, which are kept even when `osascript` is killed; `graph-engine` takes them out of the message and records the last one. In order:

| Phase | Reached when | A timeout after it |
| --- | --- | --- |
| (none) | -- | Terminal never answered: probably its Automation prompt. Disables the tab at once. |
| `window-found` | Terminal answered and the orchestrator's window was found (the 9101 check passed). | System Events never answered: probably its Automation prompt, or Terminal slow while its tabs were read or it was activated. Disables the tab at once. |
| `system-events-ok` | The first Apple event to System Events (bringing Terminal to the front) succeeded. | Slow timeout (disables at the second in a row). No Cmd+T was sent. |
| `frontmost` | Terminal and the window were seen in front (the 9103 check passed). | Slow timeout. No Cmd+T was sent (only a local 0.2-second delay follows). |
| `keystroke-sending` | About to send Cmd+T. | Slow timeout. Cmd+T **may** have been sent. |
| `keystroke-sent` | Cmd+T was sent. | Slow timeout. A new tab may be left empty. |
| `tab-found` | The new tab was found by its tty; its window's bounds are checked next. A 9102 for mismatching bounds also stops here. | Slow timeout. A new tab may be left empty. |
| `command-sending` | About to run the command in the new tab (`do script`, the script's last statement). | Slow timeout. The session may have started in the new tab as well as in the new window. |

**Was an empty tab left?** Possibly when any of these holds: `keystroke_sent` is `true`; or `kind` is `timeout` with `phase: keystroke-sending` (`keystroke_sent` stays `false` there, because the keystroke may or may not have gone out, and the message ends with "Cmd+T may have been sent, so a new tab may have been left empty"); or the message ends with "a new tab may have been left empty". The stderr warning adds ", an empty tab may be left" in the same cases. A `script-error` at `keystroke-sending` (System Events refused the keystroke, such as 1002) opened no tab.

**What is not recorded here.** Launches that did not try a tab for another reason than a locked screen -- no tty, or the tab already disabled for the run -- are not in `terminal_tab_failures`; they are counted in `terminal_window_launches`. A launch whose tab failed and whose new window could not be opened either is not in `terminal_tab_failures`: it is a failed `launch` (`attempt n of 2`, and after the second failure in a row the ticket's `launch_failed`), handled like any other launch failure.

### Checking tabs on a real Mac

Terminal.app itself cannot be driven by the automated tests, so after changing the tab script or its handling, check by hand from a Terminal.app tab, with the plugin built from the branch. After each step, look at the run file's `terminal_tab_failures` (with their `diagnostics`), `terminal_tab_slow_timeouts`, `terminal_tab_disabled`, `terminal_window_launches`, `terminal_late_tabs` and `terminal_tty_reason`, and at the orchestrator's `graph-engine: warning:` lines.

1. **Normal use.** With the Accessibility and Automation permissions granted, start a tree run (or several ticket runs) from a Terminal.app tab. Every child session opens as a tab of the orchestrator's window, no warning is printed and `terminal_tab_failures` stays absent.
2. **Many tabs.** Keep the run going (or open more tabs in the same window) until the window has 20 or more tabs with `claude` running. Sessions still open as tabs; a slow Terminal may show up as a `timeout` from `system-events-ok` on with `disabled_run: false`, but not as a disabled run after one timeout.
3. **Another app in front.** With the screen unlocked, bring another app (a TextEdit document of your own, say) to the front just before a launch. Terminal comes to the front and the session still opens as a tab. Only switching apps at the very moment between the front check and Cmd+T makes it fall back, with 9102 (`keystroke_sent: true`) and `diagnostics.frontmost_app_before` / `frontmost_app` showing the other app; the tab is not disabled, and the next launch opens a tab again. A 9103 with the screen unlocked is not expected.
4. **Orchestrator's window not found.** Run the script on its own (step 7) with a tty no tab has, such as `osascript /tmp/tab.applescript /dev/ttys999 "echo hello"`. It fails at once with 9101 and prints no phase line; in a run, that launch falls back with `kind: script-error`, `error_number: 9101`, no `phase`, `disabled_run: false`.
5. **Accessibility removed.** Turn Terminal off in System Settings > Privacy & Security > Accessibility and launch. The launch falls back with 1002 (or -25211 / -1719), `phase: keystroke-sending`, `disabled_run: true`, and later sessions open in new windows: the first of them prints the one `without trying a tab: run <runId> disabled the tab earlier` warning, the rest print nothing, and the run file's `terminal_window_launches.tab-disabled.count` counts every one of them. Turn it back on and take the run over to get the tabs back.
6. **System Events prompt left unanswered.** Reset only Terminal's Automation permissions with `tccutil reset AppleEvents com.apple.Terminal` (a bare `tccutil reset AppleEvents` resets the Automation permissions of every app on the Mac, which then all ask again), start a run and do not answer the prompts. The first launch times out at 20 seconds with no phase (the Terminal prompt) or with `phase: window-found` (the System Events prompt, when Terminal was allowed), with `disabled_run: true` on that first timeout. Answer the prompts and take the run over to get the tabs back.
7. **The script on its own.** Write the script out and run it against the current tab, which opens one new tab running `echo hello` and prints the phase lines on stderr as it goes:

   ```bash
   cd packages/core-go
   GRAPH_OPS_TAB_SCRIPT_OUT=/tmp/tab.applescript go test ./internal/terminal -run TestAppleTerminalTabScript_Structure
   time osascript /tmp/tab.applescript "$(tty)" "echo hello"
   ```

   All seven phases should appear in order, along with `graph-ops-diag: frontmost_app_before=...` and `graph-ops-diag: tabs_before=...` just before `keystroke-sending` (they are logged on every launch), and the time should stay a few seconds whatever the number of tabs. Run the script on its own only with the screen unlocked: it does not read the screen lock itself (`graph-engine` does, before running it), so with Terminal in front of a locked screen its Cmd+T would go to the lock screen.
8. **A child tab selected.** Select one of the child tabs in the orchestrator's window (or, with step 7's script, a second tab of the target window) and launch. The orchestrator's tab is brought forward and the new tab opens in that window.
9. **Screen locked.** Lock the screen (Control-Command-Q) while a run is going, and leave it locked over at least one launch. That launch falls back at once, without Terminal coming to the front: `kind: screen-locked`, `diagnostics.screen_lock: locked`, `disabled_run: false`, and a warning ending in `; screen-locked)`. After you unlock, the next launch opens a tab. To see what `graph-engine` reads, run `ioreg -n Root -d1 -a | grep -A1 CGSSessionScreenIsLocked` (from another machine over ssh while locked, or from a script started before locking): `<true/>` while locked, nothing while unlocked. The times can also be checked afterwards against loginwindow's log, as in [Fallbacks while the screen is locked](#fallbacks-while-the-screen-is-locked).

**When other runs or your own work share the Mac.** Steps 3, 7 and 8 bring Terminal to the front and send keystrokes, so they can disturb a run that is opening its own tabs, or type into an app you are using. To keep out of their way:

- Make the target window yourself and touch only that window, its tabs and a document of your own (a TextEdit file, say): for example, `open -a Terminal probe.command` with a `probe.command` (made executable) that runs `tty; exec sleep 3600`, and run step 7's script against the tty it prints instead of `"$(tty)"`.
- Hold the same tab lock `graph-engine` uses while bringing anything to the front, opening a tab or closing a window, so no launch of a run is in the middle of its own tab at that moment. macOS has no `flock` command; Python's `fcntl.flock` takes the same lock:

  ```bash
  python3 -c 'import fcntl, os, subprocess, sys
  f = open(os.path.expanduser("~/.graph-ops/autopilot/terminal-tab.lock"), "a")
  fcntl.flock(f, fcntl.LOCK_EX)
  sys.exit(subprocess.call(sys.argv[1:]))' osascript /tmp/tab.applescript /dev/ttysNNN "echo hello"
  ```

  Keep each hold short (a few seconds); launches of other runs wait up to 25 seconds for it.
- Before each try, check that the app in front is Terminal or your own document, not an app someone is typing into.
- Space the tries out (20 seconds or more apart) and keep their number small (about 10 per condition, 60 in all).
- Never try anything that sends keys while the screen is locked (see step 7).

**Not yet checked on a real Mac with the screen unlocked.** The changes of DFLT-00362 were checked on a real Mac only while its screen was locked (the screen stayed locked for the whole check): there, `screen-locked` launches, the `terminal_window_launches` counts and a 9101 from the script on its own behaved as described. With the screen unlocked, these have been covered only by the investigation with the earlier script (on the same Mac), by the fact that the parts of the script that open the tab are unchanged, and by the automated tests, and are still to be checked by hand:

1. Tabs opening with the changed script in steps 1, 3 and 8: Terminal in front, another app in front, a child tab selected.
2. The read of `frontmost_app_before` before every Cmd+T returning a value, and the delay it adds before Cmd+T staying small.
3. A 9103 or 9102 printing its `graph-ops-diag` lines and phase lines on a real `osascript`'s stderr, and their values landing in `diagnostics` (so far checked only by the tests of the parsing).
4. The last look that saves a late tab (`late_tab`, `terminal_late_tabs`): the unexplained 9102 has not been reproduced, so this path has never run on a real Mac.
5. No launch made with the screen unlocked being taken for `screen-locked` in a real autopilot run (check it against loginwindow's log as above).

## Parent and child tickets

A ticket can have a parent ticket -- the ticket it was derived from. The autopilot uses this relation to find a tree's tickets, but the relation does not bind how a ticket is processed: a child ticket can still be run on its own with `/graph-ops:autopilot-ticket`, or with the usual `/graph-ops:refine-ticket` and `/graph-ops:process-ticket`.

- **Create a child ticket** with `graph-engine create-ticket "<title>" "<description>" --parent <ticketId>`. Without `--project`, the child goes into the parent's project; a `--project` other than the parent's is `VALIDATION_ERROR` and an unknown parent is `TICKET_NOT_FOUND`, and no ticket is created in either case. The parent is set at creation only; there is no command to change or remove it later. `POST /api/tickets` takes `parent_ticket_id` the same way; the Web UI's "New Ticket" form does not set a parent.
- **See the relation** with `graph-engine get-ticket <ticketId>`: its output has `parent_ticket_id`, `parent` (`{id, title, status}`, or `null`) and `children` (the same shape, in creation order; `[]` when there are none). `GET /api/tickets/{id}` returns the same, and every ticket in `GET /api/tickets` carries `parent_ticket_id`. In the Web UI, an expanded ticket shows a "Parent ticket" link and a "Child tickets (n)" list, each with its status; clicking one opens that ticket (clearing the filters if they hide it).
- **Deleting a parent** leaves its children in place with no parent.
- **Storage**: SQLite and MySQL store it in a new `tickets.parent_ticket_id` column, added automatically the first time the new version opens an existing database. An HTTP custom data source needs [protocol 1.1](http-datasource/README.md); a plugin that still speaks 1.0 keeps working for everything else, but creating a ticket with a parent fails with `PARENT_TICKET_UNSUPPORTED` before anything is sent, so a parent is never dropped silently. The [Jira sample plugin](../examples/jira-datasource/README.md) speaks 1.1 and keeps the parent in its `graphops.ticket` issue property.

In an autopilot run, the `work` session sorts the open items it hands off into three kinds before creating anything. It checks **Drop** first; only an item that is not dropped is sorted as in scope or out of scope:

- **Drop**: an item not worth a ticket. An item is dropped when it only happens outside the project's supported range (as the project states it: the `autopilot-worker` skill's user/team extension read through `get-skill-context`, the project's settings, or the repository's README, docs or CLAUDE.md; for example a Web UI supported down to a 320 CSS px window with text up to 200%; with no stated range this criterion is not used), when it is a difference in wording or style with no effect on behaviour, appearance or maintainability, when it is a check that needs a real device or an external environment and no defect has been found, when it has not been reproduced or observed, or when the plan or a review explicitly accepted it as a risk or an intended trade-off. An out-of-scope item with no one-line reason worth working on is dropped too, with the reason "no reason worth working on". This applies to items from the ticket's own changes too, but an observed defect never matches, and an item the session is unsure about is not dropped. A dropped item gets no ticket; the `autopilot-decision-handoff` artifact keeps its kind and its Drop reason (the criterion it matched, or "no reason worth working on"), and the summary only gives the number of dropped items.
- **In scope**: a problem the ticket's own changes introduced or left unfinished, or one that stands in the way of the purpose of the run's root ticket (`root_ticket` in `graph-engine autopilot worker-context`). These become child tickets (`--parent` set to the ticket it worked on) and are worked on later in the same run.
- **Out of scope**: everything else, typically a problem that was already there before the ticket, such as a layout break on a neighbouring screen found while testing. These all go into one low-priority ticket titled "Backlog: issues found while working on <ticketId>", each with one line on why it is worth working on (an item without one is dropped instead, with the reason "no reason worth working on"), created without a parent, so it stays out of the tree and the run never picks it up. No backlog ticket is created when there is nothing out of scope.

This keeps a tree from growing without end: reviews that test a change under demanding conditions (large text, narrow screens) tend to find older problems nearby, and turning each of them into a child ticket makes every ticket spawn more. Dropping items that nobody would work on keeps the backlog from growing the same way. The `autopilot-decision-handoff` artifact records each item's kind and where it went.

If creating a child ticket fails with `PARENT_TICKET_UNSUPPORTED`, it does not retry without `--parent` (the ticket would silently fall out of the tree) and creates no further tickets: the items that were not created are listed, with the title and description they would have had, in the `autopilot-decision-handoff` artifact, the ticket's result stays `done`, and its summary says how many items were left without a ticket.

## Starting a run

The project must have a **local path** in your environment (App Settings > project management, or `/graph-ops:ui` in the project's directory), because every child session works in a git worktree under it. Without one, starting from the Web UI fails with `PROJECT_LOCAL_PATH_NOT_SET` and launching a session from the CLI fails the same way.

**Trust the project's folder first.** Before your first run, open the project's folder (its local path) in Claude Code once and accept the workspace trust prompt. In a folder Claude Code does not trust yet, the first session the autopilot opens in a new terminal stops at that prompt and waits for a person: when you start from the Web UI, that is the orchestrator, opened in the project's local path; when you start from Claude Code, it is the first child session, opened in `<local path>/.claude/worktrees/<ticketId>`. Claude Code keys the trust on the git repository's root (for a worktree, on its main checkout's root), so trusting the project's folder once is enough -- the ticket worktrees under it are not asked again. Trusting a folder above the repository is not enough: if you trusted a working folder such as `~/dev` that is not itself a git repository, a repository cloned under it still needs its own trust, and so does a git repository nested inside another one. A git submodule counts as such a nested repository: the outer repository's trust does not cover it, and accepting the prompt anywhere inside it saves the trust for the submodule's root, which covers the submodule's subfolders but not the outer repository (confirmed on Claude Code 2.1.283). (Claude Code's permissions documentation also describes trusting a folder by hand, by setting `projects["<path>"].hasTrustDialogAccepted` to `true` in `~/.claude.json`; opening the folder once is simpler.)

**The untrusted-folder notice.** When a run starts, and each time it opens a child session, the autopilot checks whether Claude Code has trusted the folder, and tells you when it can tell that it has not:

- `graph-engine autopilot start` adds `untrusted_folder` -- the project's local path, with symbolic links resolved -- to its output, and `launch` adds it -- the ticket's worktree -- when the terminal opened. The slash commands relay it to you in one line (the terminal just opened is probably waiting at the trust prompt) and carry on without stopping or asking; this includes a Web UI run the orchestrator takes over with `--run`.
- From the Web UI, the start response carries `untrusted_folder`, and an amber notice under the ticket's "Autopilot" button says that the new terminal is probably waiting at the workspace trust prompt for that folder, and that accepting it there, or opening the folder in Claude Code once, lets the run go on. It stays until you dismiss it ("Dismiss notice") or start again.

The notice never stops or delays anything: the run is reserved, the terminal opens and the run carries on exactly as it would without it. The check reads `~/.claude.json`, the file Claude Code writes for itself, and looks for an entry with `hasTrustDialogAccepted` set to `true` for the folder or, inside a git repository, for a folder between it and the repository's root, or for the main checkout's root of a worktree; outside a repository, for the folder or any folder above it. The key is described in Claude Code's documentation, but the file as a whole belongs to Claude Code and its format is not published, so the check is best-effort: it gives the notice only when it can tell, and otherwise says nothing. There is no notice, and the start goes on as usual, when:

- `~/.claude.json` does not exist, cannot be read, is larger than 16 MiB, is not JSON, or does not have the shape the check knows (a `projects` object with at least one entry holding a true/false `hasTrustDialogAccepted`) -- for example after a Claude Code update changes the file;
- the folder is your home directory, where Claude Code does not save the trust;
- `CLAUDE_CONFIG_DIR` is set, or the machine runs Windows;
- the folder's path contains non-ASCII characters;
- the folder does not exist (yet), its path cannot be resolved, or the project has no local path;
- the folder's `.git` file cannot be read or does not lead to a main checkout (for example, a worktree of a bare repository).

Paths are compared ignoring case, so on a case-sensitive file system a trusted folder whose name differs only in case also counts as trusted. No notice is therefore not proof that the folder is trusted. The check runs in the process that starts the run -- the UI server when you start from the Web UI -- so if that process has a different `HOME` or `CLAUDE_CONFIG_DIR` from the terminal's, the notice can be off. The autopilot never writes to `~/.claude.json`.

If a session is already waiting at the prompt, accept it in that terminal and the session carries on from there. If it waited too long -- a child session with no activity for `stallTimeoutMinutes` is failed as `unresponsive` and `onFailure` applies, and a Web UI orchestrator that never started lets the run's heartbeat go stale -- trust the folder, close the terminals left over, and resume the run as described in [Interrupting, resuming and unresponsive sessions](#interrupting-resuming-and-unresponsive-sessions).

**From Claude Code**, in the project's directory:

```
/graph-ops:autopilot-ticket <ticketId>
/graph-ops:autopilot-tree <ticketId>
```

The session you type this in becomes the orchestrator, so it runs with your own session's permission mode. Leave it alone while it runs: it launches child terminals, waits for them in the background, and prints the tree's summary at the end. Do not invoke `/graph-ops:autopilot-worker` yourself; it is started by `graph-engine autopilot launch`.

**From the Web UI**, expand a ticket and press "Autopilot" at the right end of its action row (set apart from "Refine" and "Run"). The confirmation dialog asks what to run -- "Tree (this ticket and its descendants)", the initial choice, or "This ticket only" -- and its title, text and confirm button follow the choice; confirm to start. The server reserves a run and opens the orchestrator in a new terminal in the project's local path, with `--permission-mode` set to the project's `permissionMode` setting and the prompt `/graph-ops:autopilot-<ticket|tree> <ticketId> --run <runId>`. While a run is active, the Web UI shows, in the ticket list and on the expanded ticket (refreshed with the list, every 15 seconds):

| Badge | Shown on |
| --- | --- |
| "Autopilot running" | the root ticket of an active run of yours |
| "<name> is running" | the root ticket of another member's active run (on a shared database), with "(name not set)" after the name when that member has no display name set and `<OS user>@<host>` is shown instead |
| "Processing" | the ticket whose session is running now |
| "Waiting for a person" | the running ticket, when its session waits for your decision (the hover text and the expanded ticket say what it waits for) |
| "Waiting" | tickets the run is still going to process |

A mode whose start would be refused cannot be chosen: in the dialog its choice is disabled with the reason, and the other mode becomes the initial choice. When neither mode can start, the "Autopilot" button itself is disabled, with the reasons shown under the button and as a tooltip. A start is refused when:

- the ticket belongs to an active run (it is that run's root, or in tree mode one of its descendants): both modes;
- a descendant of the ticket is the root of an active run: the tree only;
- the ticket is `DONE` or `CLOSED`, unless the latest run of that mode from this ticket is stopped or interrupted -- then choosing that mode resumes the run (the dialog's title, text and confirm button say so; this is decided for each mode separately). Only the five most recent inactive runs of the project are considered here; an older stopped run can still be resumed from the CLI (run the same slash command again).

The active runs include other members' runs on a shared database (see [Runs shared between members](#runs-shared-between-members)); the reason then names the member whose run blocks the start. Only your own stopped or interrupted runs are offered for resuming: another member's is neither resumed nor in the way.

## Which tickets a run processes

In `ticket` mode a run processes just its root. In `tree` mode it walks the tree depth first, children in creation order, and it re-reads the tree from the database at every step, so tickets created while the run is going are picked up. For each ticket:

- **`DONE` / `CLOSED`** tickets are skipped (`already_done` / `closed`), but their children are still processed.
- **A ticket that is `IN PROGRESS`, `IN REVIEW` or `IN RELEASE`** and was not launched by this run is taken to be worked on elsewhere, for example on another machine sharing the database: it is skipped (`in_progress_elsewhere`), and so is everything under it (`ancestor_in_progress`). A ticket left `IN PROGRESS` by an earlier run of this machine's registry does not count as "elsewhere".
- **The root is never skipped.** Starting a new run from a `DONE` or `CLOSED` ticket is refused with `AUTOPILOT_ROOT_FINISHED` (start from the descendant you want instead); a root that is `IN PROGRESS` is processed. See [Cautions and limitations](#cautions-and-limitations).
- **Limits**: `maxDepth` skips tickets deeper than the limit (`limit_depth`; the root is depth 0, counted by actual depth even across skipped tickets). `maxTickets` caps the number of tickets a run launches as `work`, the root included (`limit_tickets`). A ticket counts once: launching the same ticket again (a retry after a failure, or a relaunch in a run that was taken over) does not count again, a launch that fails is given back, and `merge-up` and `finalize` sessions do not count. Reaching a limit is not a failure: what was done is still merged up and finalized.
- **Failures** (`failed` or `blocked`, including a session judged unresponsive and a session that could not be launched twice in a row) follow `onFailure`:
  - `stop` stops the run (`ticket_failed`): nothing more is launched, merged up or finalized. Running the same command again resumes it.
  - `continue` skips the failed ticket's not-yet-started descendants (`parent_failed`), leaves its branch out of its parent's (`not_merged`), treats its parent's subtree as finished, and carries on with the rest. The summary lists the failed tickets' branches under "Work not in the root branch".
- **Retries**: a ticket that failed or was blocked in an earlier run is launched once more each time you start the same run again (after you have removed the cause); the child session continues from the ticket's node states in the database. Skips caused by a limit or by a ticket's status are re-evaluated with the current settings at that point, so raising `maxTickets` and running the command again processes the tickets it skipped.

## Branches

Every ticket is worked on in its own git worktree and branch, named the way Claude Code's `EnterWorktree` names them, so you can step into one yourself afterwards:

- worktree: `<project local path>/.claude/worktrees/<ticketId>`
- branch: `worktree-<ticketId>`

An existing worktree or branch of that name is reused (this is how a resumed run continues). A ticket ID that cannot name a branch -- anything other than letters, digits, `.`, `_` and `-`, starting with a letter or digit -- fails the launch.

- **Base branch**: a `ticket` run and a tree's root branch off the repository's default branch (the branch `origin/HEAD` points at, or `main` when that cannot be read). A child in a tree branches off the branch of its nearest ancestor that this run launched as `work` -- normally its parent. A skipped ancestor is passed over, so a leftover branch of a skipped ticket is never used.
- **A child merges into its parent's branch as part of its release, without approval**: its session merges the parent's branch into its own (`git merge`), resolves any conflicts, re-runs the tests, and then calls `graph-engine autopilot merge-into-parent`, which fast-forwards the parent's branch. If the conflicts cannot be resolved, or the fast-forward is refused (`NOT_FAST_FORWARD`, or `PARENT_WORKTREE_DIRTY` when the parent's worktree has uncommitted changes to tracked files), the child ends `blocked` with reason `merge_conflict` and `onFailure` applies.
- **Merge-up on the way back**: a child creates its own children only after it has merged into its parent, so a grandchild's work lands in the child's branch after that merge. To carry it up, when a ticket's whole subtree is finished, `next` returns `merge-up` for it and `graph-engine autopilot merge-up` fast-forwards the ticket's branch into its parent's again. Done bottom-up, one level at a time, this brings every finished descendant's work, at any depth, into the root's branch. When the fast-forward is not possible for any reason (not a fast-forward, a dirty target worktree, or another git error such as an untracked file in the way), nothing is changed and the result is `needs_merge_session`; the next `next` launches a `merge-up` session in the parent's worktree, which merges, resolves conflicts and re-runs the tests, or ends `blocked` (`merge_conflict`, or `merge_failed` when `git merge` fails before any conflict).
- **Reflection into the main branch** (`mainReflection`) applies only to the root -- in `ticket` mode, the ticket itself:
  - `branch` (default): leave the branch as it is. Nothing is pushed.
  - `pull_request`: push the branch and open a pull request into the default branch, without merging.
  - `merge`: open the pull request and merge it (through the pull request when the repository requires pull requests or protects the branch).

  In `ticket` mode the `work` session does this in its release step. In `tree` mode the root's release step only commits, and once every ticket of the tree has been merged up, `next` launches a `finalize` session in the root's worktree that does it for the whole tree. When a stage cannot be done (no remote, no `gh`, merge refused), the session stops at the last stage that worked and says so; a `finalize` that could not reflect anything beyond the local branch ends `blocked` (`reflection_failed`) and the run stops with `finalize_failed`. With `branch`, no `finalize` session is launched. When the root itself fails, nothing is reflected.
- A child ticket processed on its own (by `autopilot-ticket` or `process-ticket`) is not tied to its parent: it branches off the default branch as usual.

Do not move the tree's branches by hand while a run is going: a commit on an ancestor's branch turns the next fast-forward into a merge session.

**Git branches are not shared between members.** On a shared database, runs that overlap in time are refused, but the branches a run creates live in the git repository of the machine that ran it. If another member finishes part of a tree first -- say a descendant's subtree, run on its own -- a later run of an ancestor's tree finds those tickets `DONE` and skips them as `already_done`, and their work reaches your tree only if it is already in your local default branch. So:

- whoever runs first reflects the work into the shared default branch: set `mainReflection` to `pull_request` (and merge the pull request) or `merge`. A branch left with `branch` exists only on that member's machine, and nobody else's run can take it in;
- whoever runs later brings the local default branch up to date with the remote (for example `git pull` on it) before starting.

## Automatic decisions

Every decision the autopilot makes on your behalf is saved on the ticket as a `text` artifact, with its reasons, so you can review it afterwards. An expanded ticket in the Web UI lists them in an "Automatic decisions (n)" section, each with a link that opens it in a new tab.

| Artifact | Saved on | Contents |
| --- | --- | --- |
| `autopilot-decision-refine` | the first node of the graph | the completion criteria, "why", priority and labels adopted in refinement, and why (not saved when the ticket was already refined) |
| `autopilot-decision-approval` | each `approval_gate` | approve or reject, and why |
| `autopilot-decision-iteration` | the failing review node | at a review iteration limit: whether one more round was granted (at most once per loop target) or the ticket was reported blocked |
| `autopilot-decision-release` | the `release` node | how the work was reflected, and the result |
| `autopilot-decision-handoff` | the `release` node | each open item, whether it became a follow-up ticket or was dropped, why (for a dropped item, the Drop criterion it matched or "no reason worth working on"), and the created ticket's ID |
| `autopilot-tree-summary` | the root's `release` node | the run's summary (see `summary` below) |

The refinement decision is recorded in the run first (`record-decision`) and attached to the plan node once the graph exists (`attach-decisions`), so it survives an interruption and is never saved twice.

## Settings

Autopilot settings are per project. Edit your own values in the Web UI under Settings > Autopilot (for the project shown in the header); they are saved in your `$HOME/.graph-ops/config.json` under `autopilotSettings.<projectId>` and are never written to the database. `graph-engine autopilot settings [--project <id>]` prints the values in effect; it is read-only.

| Key | Values | Default | Meaning |
| --- | --- | --- | --- |
| `mainReflection` | `branch` / `pull_request` / `merge` | `branch` | How the root's work reaches the main branch (see [Branches](#branches)). |
| `permissionMode` | `acceptEdits` / `auto` / `dontAsk` / `bypassPermissions` | `auto` | The `claude --permission-mode` of every child session, and of the orchestrator when it is started from the Web UI. `default` and `plan` are not accepted, since a session in those modes cannot run on its own. |
| `autoApproveGates` | `true` / `false` | `true` | Whether the child session decides `approval_gate`s. When off, it waits for your decision as `process-ticket` does. |
| `autoCreateTickets` | `true` / `false` | `true` | Whether the child session decides which open items become follow-up tickets and creates them (in-scope items as child tickets, out-of-scope items in one backlog ticket outside the tree, dropped items in no ticket; see [Parent and child tickets](#parent-and-child-tickets)). When off, it lists the items in its terminal, dropped ones included with their kind and reason, and waits for you to pick; a dropped item you pick goes into the backlog ticket. |
| `maxTickets` | 1-100 | 20 | Tickets launched as `work` per run, the root included. Relaunching the same ticket does not count again, a failed launch is given back, and `merge-up` / `finalize` sessions do not count. |
| `maxDepth` | 0-10 | 3 | How deep derived tickets are processed (the root is 0). |
| `onFailure` | `stop` / `continue` | `stop` | Stop the whole run on a failure or block, or skip only that ticket's subtree and continue. |
| `stallTimeoutMinutes` | 15-1440 | 60 | A child session with no sign of activity for this long is failed as unresponsive. |

When `autoApproveGates` or `autoCreateTickets` is off, a child terminal asks you for input while the run is going. Such a session is marked "Waiting for a person" and is never judged unresponsive while it waits.

### Team settings and precedence

A team can set autopilot settings in `autopilot.yaml` at the root of the shared directory `teamExtensionsDir` points at (next to `workflow.yaml`). Each person points at that directory with Settings > App Settings > "Team Settings Directory" (saved as `teamExtensionsDir` in `$HOME/.graph-ops/config.json`; the environment variable `GRAPH_TEAM_EXTENSIONS_DIR` takes precedence when set, and a change takes effect immediately for the `graph-engine` CLI, including `graph-engine autopilot` and the agents' commands, while an already-running UI server picks it up only after it restarts). When it is not set, or names your own settings directory, there is no team tier and no team file is read. The file looks like this:

```yaml
version: 1
defaults:            # every project
  mainReflection: pull_request
projects:
  proj-64195d2b:     # a project ID
    maxTickets: 10
```

Each key is resolved on its own, first match wins:

1. the team file's `projects.<projectId>`
2. the team file's `defaults`
3. your local value (`autopilotSettings.<projectId>` in `$HOME/.graph-ops/config.json`)
4. the built-in default

A key the team file sets is **locked**: the Web UI shows it read-only as "Fixed by team settings (shared default)" or "(this project)", with your own local value, if you have one, in parentheses. The local value stays in your file and takes effect again once the team file stops setting the key.

- **`bypassPermissions` is never taken from the team file.** A shared directory must not be able to make everyone's child sessions run without confirmation. The value is ignored with the warning `AUTOPILOT_TEAM_BYPASS_PERMISSIONS_IGNORED`, the key is not locked, and resolution falls through to your local value or the default. You can still choose `bypassPermissions` locally; the Web UI shows a warning when you do.
- **Invalid team values are ignored, not fatal.** An unreadable file or a `version` other than 1 ignores the whole file (`AUTOPILOT_TEAM_FILE_INVALID`); an invalid value or a value of the wrong type (`"10"` for a number, `yes` for a boolean) ignores that key (`AUTOPILOT_INVALID_VALUE`); an unknown key is reported as `AUTOPILOT_UNKNOWN_KEY`. The same warnings apply to hand-edited local values. They are shown in the Web UI and returned in `warnings`.
- **Saving** (`PUT /api/projects/{id}/autopilot-settings`) takes a partial object of the keys to store locally: a key with a value is stored, a key set to `null` removes your local value, and a key left out is unchanged. A body that contains a locked key -- even with the team's own value, or `null` -- is refused as a whole with `400 AUTOPILOT_SETTING_LOCKED` (`details.keys` names the keys), and so is an invalid value (`400 VALIDATION_ERROR`); nothing is saved in either case.

## Interrupting, resuming and unresponsive sessions

- **Resuming**: a run is resumed only on the machine that started it (see [Runs shared between members](#runs-shared-between-members)). If the orchestrator is interrupted (the terminal closed, the session ended), run the same command again -- `/graph-ops:autopilot-tree <root>` or `/graph-ops:autopilot-ticket <root>`, or the same Web UI button. A run is active while its heartbeat is less than 10 minutes old; the orchestrator's commands (`start`, `next`, `launch`, `wait`, `merge-up`) refresh it, and a waiting `wait` refreshes it every 30 seconds. Once the heartbeat is older, the latest run with the same root and mode is taken over: the same run continues, with the settings as they are now, and the work to do is recomputed from the database. A stopped run is taken over the same way. A child session that was still marked running is waited for first, not relaunched. **Close the child terminals left over from the interrupted run before resuming**, so that no ticket is worked on twice.
- **Unresponsive sessions**: a child terminal is not a process the engine can watch, so a session that ends without reporting (a crash, a closed terminal, a refused permission, a question to a person, an overflowing context) is detected from the absence of activity. Activity is any `graph-engine autopilot` call of the child session, any change to the ticket, its nodes or its artifacts in the database, and any change to its worktree (new commits, changed or new files). When none of these changes for `stallTimeoutMinutes`, the ticket is failed with reason `unresponsive` and `onFailure` applies; the summary names the worktree and asks you to check the terminal if it is still open. A report that arrives after that is kept as a late report in the summary and does not change the run.
- **`wait` never blocks forever**: it returns after `--timeout` (10 minutes by default) with exit code 2, and the orchestrator goes back to `next`, so every wait ends within `stallTimeoutMinutes` plus the timeout.

## The run registry

Each machine keeps its runs in local files, per project:

```
$HOME/.graph-ops/autopilot/<projectId>/runs/<runId>.json   one file per run
$HOME/.graph-ops/autopilot/<projectId>/.lock                the project's lock
$HOME/.graph-ops/autopilot/terminal-tab.lock                 serializes Terminal.app tab launches (all projects)
```

Every project has its own directory and lock, so runs in different projects never interfere. Within a project, a start is refused with `AUTOPILOT_ALREADY_RUNNING` when an active run owns the ticket (the run's root and, for a tree run, all of its descendants) or, for a tree start, when an active run's root is among the ticket's descendants.

- **The lock** is held for milliseconds (reading, deciding and writing run files; git, database and network work happen outside it -- except the one short database transaction a start makes to decide together with the shared runs, see below). Its holder refreshes it every 10 seconds, and a lock not refreshed for 2 minutes is treated as left behind by a process that is gone and removed (the removal is logged). A command that cannot get the lock within 60 seconds, or finds it was taken over while it held it, fails with `AUTOPILOT_REGISTRY_LOCKED` and saves nothing; run it again.
- **Old runs are pruned** whenever a new run is created: of the settled runs -- finished ones, and ones replaced by a newer run with the same root and mode -- the newest 20 are kept. The latest run for each root and mode that is stopped or interrupted is kept however old it is, because running the same command again resumes it. So a stopped run you do not intend to resume stays until you delete it: when it is not active (check with `graph-engine autopilot status`), delete its `runs/<runId>.json` by hand. A ticket that a deleted run left `IN PROGRESS` then counts as "in progress elsewhere" for later runs.
- **Terminal.app fields**: a run file also keeps `terminal_tty`, the tty of the orchestrator's Terminal.app tab, `terminal_tab_disabled`, the reason the tab was disabled for the run, `terminal_tab_slow_timeouts`, the number of slow `osascript` timeouts in a row, `terminal_tab_failures`, up to 50 launches whose tab fell back to a new window or was not tried because the screen was locked, `terminal_tty_reason`, why the orchestrator has no tty, `terminal_window_launches`, the launches that opened a new window without trying a tab, by reason, and `terminal_late_tabs`, the tabs found only in the script's last look, all left out when empty (see [Terminal.app: child sessions as tabs](#terminalapp-child-sessions-as-tabs) and [Tracing each fallback](#tracing-each-fallback)). They stay in the local run file and are never shared with other members. Run files written by an earlier version are read as having none of them.
- **A run file that cannot be read** is skipped with a warning naming its path (on stderr as `graph-engine: warning: ...` for the CLI, in the server log with `event=autopilot_registry` for the Web UI), and every start in that project is refused with `AUTOPILOT_REGISTRY_CORRUPT` until you repair or delete the file, since the duplicate-run check cannot be made without it.
- **Who started a run**: a run file also keeps `started_by` (the display name and the machine ID of whoever started, took over or adopted it), `revision` (a number that grows with every save), and `begun_at` (when it was last started, taken over or adopted, which decides which of two overlapping runs stops as `overtaken`; see [Runs shared between members](#runs-shared-between-members)). Run files written by an earlier version have none of them: they are read as this machine's, with `created_at` standing in for `begun_at`.

### Runs shared between members

With a database several members share -- MySQL, a shared SQLite file, or an HTTP data source of protocol 1.2 or newer -- every run is also kept in the database's `autopilot_runs` table (the HTTP data source's `autopilot-runs` endpoints), so each member's graph-engine sees the others' runs:

- **What is shared**: the run's ID, project, root, mode, state, heartbeat, who started it (name and machine ID), its revision, and a snapshot of the run -- its tickets and their states, the settings, the stops. What only means something on the machine running it is not: the terminal tty and tab state, worktree paths, branch names, fingerprints, and the local registry's lock. The local run file stays the source of truth for your own runs; every time it is saved (so at least every 30 seconds while a run waits for a session) its shared copy is written too. A shared copy that arrives late never overwrites a newer one (the revision decides).
- **Duplicate starts across members**: `autopilot start` and the Web UI's launch judge overlaps on your runs and the shared ones together, and refuse an overlap with another member's active run with `AUTOPILOT_ALREADY_RUNNING`, naming that member (`started_by` in `details`, and in the message). On MySQL and SQLite the decision and the saving of the new run are one transaction, so two members starting overlapping runs at the same moment never both pass. An HTTP data source cannot do that (a list and a save are two requests), so there two starts at the very same moment may both pass.
- **Expiry**: another member's run blocks you only while its heartbeat is less than 10 minutes old. A run whose heartbeat is older is treated as interrupted: it no longer blocks anyone, and nothing rewrites its state -- it stays as its machine left it until that machine resumes it. Heartbeats are compared with each member's own clock, so this assumes the members' clocks are not minutes apart.
- **A run that comes back after it expired**: a heartbeat stops while the orchestrator's machine sleeps, or while its session is suspended for more than 10 minutes. If another member starts an overlapping run in the meantime and the machine then wakes up, the old run would count as active again, and both would go on with the same tickets. So before every `next` and `launch`, a run checks the shared runs: when an active run that overlaps it was begun after it, it stops with the reason `overtaken` -- `next` answers `stopped`, a `launch` in flight fails (`AUTOPILOT_INVALID_STATE`) without opening a session and the following `next` answers `stopped` -- and the stop's detail names the other run and who started it. The run begun later goes on. A child session the old run had already launched is not stopped: it keeps working until it reports (or you close its terminal), so look at its ticket before you resume. Running the same command again resumes the stopped run once the other run has ended (until then the start is refused with `AUTOPILOT_ALREADY_RUNNING`). Of two runs started at the same moment on an HTTP data source (see above), the same rule stops the one begun first. If the shared runs cannot be read at that point, the run goes on (the failure is logged).
- **Resuming is per machine**: a stopped or interrupted run is taken over only by a start on the machine that started it. Another member's stopped or interrupted run with the same root and mode does not block you, but is not taken over either: your start creates a new run. Naming it with `--run` is refused with `AUTOPILOT_INVALID_STATE` (or `AUTOPILOT_ALREADY_RUNNING` while it is active). The machine is identified by a random ID kept in `$HOME/.graph-ops/machine-id`, created the first time it is needed: if you delete it, your machine gets a new ID and can no longer resume its interrupted runs; if you copy your home directory to another machine, both machines have the same ID. A machine-id file that is not a valid ID is never replaced silently: until you restore or delete it, starts fail with `AUTOPILOT_MACHINE_ID_UNREADABLE` (the runs list still works).
- **Display names**: the name shown is your `myName` (App Settings), or `<OS user>@<host>` with "(name not set)" when it is empty. It is only displayed, never used to tell members apart. Before a name is recorded, and again before any member's name is shown (in the CLI, error messages and their `details`, stop reasons, and the Web UI / `GET /api/autopilot/runs`), tabs and line breaks become a space, every other control character (including ESC, so no terminal escape sequences) and every invisible format character (Unicode category Cf: bidirectional controls, zero-width characters such as ZWSP, ZWNJ and ZWJ, the BOM, ...) is removed, runs of white space are collapsed, and the name is cut to 128 characters. Names written by an earlier version or straight into the database are cleaned the same way when they are read. A name left empty by this is treated as unknown (no name is shown), and an empty `myName` falls back to `<OS user>@<host>`. Ordinary names such as `山田 太郎` or `taro@mac01` are unchanged, but removing format characters changes some: an emoji joined with ZWJ (a family emoji, say) shows as its separate emoji, and a name that uses ZWNJ as part of its spelling (in Persian or Indic scripts, for example) loses it.
- **Other strings of a run record**: the rest of what another member's run record puts on your screen is cleaned the same way before it is shown (in the CLI, error messages and their `details`, logs, and the Web UI / `GET /api/autopilot/runs`), so no member can put terminal escape sequences or fake lines on another's terminal through them either. IDs -- the run ID, the root ticket ID, the project ID, the ticket IDs of a run (its tickets, its current ticket, the tickets of its tree and the ones still pending) -- are shown as they are when they have the shape graph-engine gives them (ASCII letters, digits and `. _ : -`, at most 191 characters), and as `(invalid id)` otherwise; an empty one (a run without a project, a run with no session running) stays empty. The mode, the state, the stop reason, each ticket's status and the current session's role follow the display-name rules above, cut to 128 characters, and a session's `awaiting_human` follows them with a limit of 500 characters, so a line break in it shows as a space. This is also what `autopilot status` shows for this machine's run files. When a run stops as `overtaken`, the other run's ID and root are cleaned before they are written into the stop's detail. Only what is shown changes: overlap checks, resuming, deleting settled records and every other lookup still use the values stored in the database, and ordinary IDs, states and Japanese `awaiting_human` texts look as before. The other fields of another member's record -- ticket reasons, summaries, branch names, stop details and so on -- are never shown on your machine, and what only belongs to the machine that runs it (the terminal, worktree paths, branch names) is dropped when a record is read.
- **When the database cannot be read**: a start fails (it cannot tell whether it would duplicate a run). The Web UI's runs list, by contrast, still answers with your own runs only, so while the database is down other members' runs do not show and their tickets' buttons look enabled; a start there is refused all the same.
- **When a write to the database fails**: a failure to write a run's shared copy after a local save is only logged -- the run goes on, and other members may see it as interrupted until a later save gets through. When a start's local save fails after its shared record was written, or a cancelled Web UI launch cannot put its record back, the record is undone on a best-effort basis; if even that fails, the record left behind blocks overlapping starts by other members until its heartbeat is 10 minutes old. A record that was put back carries a higher revision than the run file on the machine, so it keeps showing the run as it was put back (stopped or interrupted) until the run is next started. A repeated failure is logged once until the database answers again, which is logged too ("the shared autopilot runs are reachable again"). This is tracked separately for each kind of operation -- listing the shared runs, sharing a run, putting back a cancelled launch's record, and deleting settled records -- so while listing keeps failing, a successful write of a run does not log "reachable again"; only a success of the same kind does.
- **How long settled runs are kept**: every start keeps at most 20 settled records per project in the database -- runs that are finished, stopped, or whose heartbeat has expired -- whoever started them, deleting the ones updated longest ago (on MySQL and SQLite in the start's own transaction; on an HTTP data source one `DELETE` per record, at most 2 per start and the oldest first, so that a slow data source does not hold up this machine's other autopilot operations for long -- the rest are deleted by later starts). Active runs are never deleted. The run files on each machine are not touched by this (they are pruned as before, and when a start prunes this machine's old run files, the shared records of those runs are deleted too), so a member can still resume its own stopped run; its record comes back when it does. This way records of members who left, or of a machine whose `machine-id` was replaced, do not pile up. On an HTTP data source a delete that fails does not fail the start (on MySQL and SQLite it fails the start with its transaction): it is logged ("deleting settled shared autopilot runs of project <id>: <runId>: <error>; ... (they are deleted by a later start)"), once while the same failure repeats, and the record is deleted by a later start.
- **Node claims of a run**: each worker's `process-ticket` begins its processing session with `graph-engine begin-session <ticketId> --run <runId>`, so the nodes it takes record the run. Claims made in any session of the same run count as the run's own: a worker relaunched for the same ticket (after a failure, or a retry) releases the nodes an earlier worker left `IN PROGRESS` without `--force`. Such a claim stays live while the run is running -- neither stopped nor finished -- and its heartbeat is at most 10 minutes old; once the run stops or finishes, its claims expire at once, and another member can release them without `--force`. When the run's record cannot be read or found, the session's own heartbeat decides instead, with a person's 60-minute lease. A worker never uses `--force`: a live claim of another run or of a person (`NODE_CLAIMED_BY_OTHER`) makes it report the ticket `blocked`, naming the holder. See the README's notes ("Several members on the same tickets") for the rules for everyone.
- **HTTP data sources older than 1.2** (including the Jira sample, which speaks 1.1) do not share runs: each machine judges from its own runs only, so duplicate starts by other members are not detected. graph-engine says so once per process (on stderr for the CLI, in the server log for the Web UI).
- **Everyone updates together**: an older graph-engine neither writes nor reads the shared runs, so a member still on it neither sees nor is seen by the others.

## The `graph-engine autopilot` CLI

The slash commands and the Web UI drive these subcommands; you rarely need to run them yourself, except `status` and `settings`. Every run subcommand prints one line of compact JSON (`summary` prints Markdown; `status` and `settings` print indented JSON). Errors go to stderr after `Error:` -- most of them start with their code, as in `Error: AUTOPILOT_ALREADY_RUNNING: ...` -- with exit code 1.

Orchestrator side:

| Subcommand | Output |
| --- | --- |
| `start <ticketId> --mode ticket\|tree [--run <runId>]` | Creates a run, takes over the latest interrupted or stopped run with the same root and mode, or (`--run`) adopts a run the Web UI reserved. `{"run_id","project_id","mode","root","state","created","resumed","adopted","next"}`, plus `untrusted_folder` when Claude Code has not trusted the project's local path (see [Starting a run](#starting-a-run)); `next` is the command to run next. |
| `next <runId>` | The one next action: `{"action","ticket","role","reason","detail","worktree","command"}`, with empty fields left out. `action` is `launch` (`command` is the `launch` to run, with `--role work`, `merge-up` or `finalize`), `wait` (`worktree` is where that session runs), `merge-up`, `done` or `stopped` (`reason` and `ticket` say why; `command` is the `summary` to run). |
| `launch <runId> <ticketId> [--role work\|merge-up\|finalize]` | Prepares the worktree and opens the child session. `{"launched","role","worktree","branch","base_branch","next"}`, plus `untrusted_folder` when Claude Code has not trusted the worktree; `next` is the `wait` command. A failure prints the error with `attempt n of 2`; the second failure in a row records the ticket as failed (`launch_failed`). In Terminal.app, when a tab was tried and failed and the session opened in a new window instead, it also prints a `graph-engine: warning:` line on stderr (see [Terminal.app: child sessions as tabs](#terminalapp-child-sessions-as-tabs)). |
| `wait <runId> <ticketId> [--timeout <duration>]` | Blocks until the session reports. Exit 0 with `{"state":"reported","ticket","role","result","reason","detail","summary"}` (also when the session was just failed as `unresponsive`); exit 2 on timeout with `{"state":"waiting","ticket","idle_minutes","stall_timeout_minutes"}` or `{"state":"awaiting_human","ticket","awaiting"}`; exit 1 on an error. The default timeout is 10 minutes (a Go duration such as `30s` or `10m`). |
| `merge-up <runId> <ticketId>` | `{"result","ticket","branch","target_branch","reason","detail"}`. `result` is `merged`, `up_to_date` or `needs_merge_session`; with `needs_merge_session`, `reason` is `NOT_FAST_FORWARD`, `PARENT_WORKTREE_DIRTY` or `GIT_ERROR`, and for `GIT_ERROR` `detail` holds the git message (up to 300 characters). |
| `summary <runId>` | The run's summary as Markdown: each ticket's result, reason, branch, merge state and summary, the stop reason, the main-branch reflection, "Work not in the root branch", unresponsive sessions with their worktrees, and late reports. It is also saved on the root's `release` node as `autopilot-tree-summary` (not saved again when unchanged). |
| `status [--project <id>]` | `{"project_id","runs":[{"run_id","project_id","mode","root","state","active","heartbeat","current","current_role","awaiting_human","stop_reason","tickets":{"<ticketId>":"<state>"}}]}`, newest first. It lists this machine's runs only; other members' runs on a shared database are in the Web UI's runs list (`GET /api/autopilot/runs`, see [HTTP API](#http-api)). |
| `settings [--project <id>]` | `{"project_id","settings","items":[{"key","value","source","locked","local","team","default"}],"warnings","team_file"}`; `source` is `default`, `local`, `team_defaults` or `team_project`. |

`status` and `settings` pick the project the way `list-labels` does (`--project`, else the current directory's local path, else the current project).

Child-session side (used by the `autopilot-worker` skill):

| Subcommand | Output |
| --- | --- |
| `worker-context <runId> <ticketId>` | `{"run_id","ticket","root_ticket","mode","run_state","position","role","branch","worktree","base_branch","target_branch","target_ticket","default_branch","merge_source_branch","merge_worktree","settings","pending_decisions"}`; `root_ticket` is the ticket the run started from; `position` is `single`, `tree_root` or `tree_child`. |
| `record-decision <runId> <ticketId> <kind> <content\|->` | Keeps a decision in the run until it can be saved as an artifact. `{"recorded","ticket"}` |
| `attach-decisions <runId> <ticketId> <nodeId>` | Saves the kept decisions on the node, skipping any already on the ticket. `{"attached":[...],"skipped":[...]}` |
| `touch <runId> <ticketId> [--awaiting-human <what>]` | Records activity; `--awaiting-human` marks the session as waiting for a person. `{"touched","awaiting_human"}` |
| `report <runId> <ticketId> --result done\|failed\|blocked [--reason <code>] --summary <text\|->` | Records the session's result; the summary is cut to 3 lines and 500 characters, and the last report wins. `{"recorded","late_report","ticket","result"}` |
| `merge-into-parent <runId> <ticketId>` | Fast-forwards the ticket's branch into its parent's. `{"result","ticket","branch","target_branch"}` with `merged` or `up_to_date`; fails with `NOT_FAST_FORWARD`, `PARENT_WORKTREE_DIRTY` or a git error, changing nothing. |

Exit codes follow `wait-node`: 0 success, 1 error, 2 a `wait` timeout.

## Error and reason codes

Errors of the CLI and the HTTP API (HTTP status in parentheses):

| Code | Meaning |
| --- | --- |
| `AUTOPILOT_ALREADY_RUNNING` (409) | An active run overlaps the ticket or its tree. `details` names the run (`run_id`, `root_ticket_id`) and, when known, who started it (`started_by`, and `name_is_fallback` when that name is the `<OS user>@<host>` fallback); the message names them too. |
| `AUTOPILOT_ROOT_FINISHED` (409) | A new run cannot start from a `DONE` or `CLOSED` ticket. |
| `AUTOPILOT_REGISTRY_CORRUPT` (409) | A run file of the project cannot be read; repair or delete it (its path is in the warning and in `details`). |
| `AUTOPILOT_MACHINE_ID_UNREADABLE` (409) | With runs shared through the database, a start needs this machine's ID, and `$HOME/.graph-ops/machine-id` cannot be read or created (for example, it does not hold a valid ID). Nothing is started. Restore the file from a backup, or delete it to get a new ID (this machine then can no longer resume its interrupted runs). Its path is in `details`. |
| `AUTOPILOT_REGISTRY_LOCKED` (409) | The project's lock could not be taken within 60 seconds, or was taken over; nothing was saved. Run the command again. |
| `AUTOPILOT_INVALID_STATE` (409) | The command does not fit the run's current state (for example `next` on a run the Web UI reserved but no orchestrator has adopted yet, or `start --run` naming another member's stopped or interrupted run, which only its own machine can resume; `details` then has `run_id` and `started_by`). |
| `AUTOPILOT_RUN_NOT_FOUND` (404) | No run with that ID in any project's registry. |
| `AUTOPILOT_SETTING_LOCKED` (400) | A settings save contained a key the team file sets. |
| `PROJECT_LOCAL_PATH_NOT_SET` (400) | The project has no local path in this environment. From the Web UI nothing is reserved. During a run, a `launch` fails with it and counts as a failed launch, so the second one in a row records the ticket as `launch_failed`. |
| `PARENT_TICKET_UNSUPPORTED` (400) | `create-ticket --parent` against an HTTP data source that speaks protocol 1.0. |
| `NOT_FAST_FORWARD`, `PARENT_WORKTREE_DIRTY` | A fast-forward into a parent's branch was refused: the branches have diverged, or the parent's worktree has uncommitted changes to tracked files. Untracked files do not count as uncommitted changes; if one is in the way of the fast-forward, git itself fails instead (`GIT_ERROR` for a merge-up). |

Reasons in a run (in `next`, `wait`, `status`, the summary and the Web UI):

- Skips: `already_done`, `closed`, `in_progress_elsewhere`, `ancestor_in_progress`, `limit_tickets`, `limit_depth`, `parent_failed`.
- Failures recorded by the engine: `unresponsive` (no activity for `stallTimeoutMinutes`), `launch_failed` (the session could not be launched twice in a row; `detail` has the error), `merge_conflict` (a merge-up session could not merge).
- Reported by child sessions: `merge_conflict`, `merge_failed`, `gate_rejected`, `iteration_limit`, `blocked`, `error`, `permission_denied`, `reflection_failed`.
- Run stops: `ticket_failed`, `finalize_failed`, `overtaken` (another member's overlapping run was begun while this run's heartbeat had expired; see [Runs shared between members](#runs-shared-between-members)).
- Merge states of a ticket's branch: `merged_self` (merged into its parent by its own release), `merged_subtree` (merged up with its subtree), `not_merged` (left out after a failure).

## HTTP API

The Web UI uses these endpoints of the local UI server. Like every state-changing route, `POST` and `PUT` require the CSRF header and the loopback checks the server already applies.

- `POST /api/tickets/{id}/autopilot` with `{"mode":"ticket"|"tree"}`: checks the mode (`400 VALIDATION_ERROR`), the ticket (`404 TICKET_NOT_FOUND`) and the project's local path (`400 PROJECT_LOCAL_PATH_NOT_SET`) before reserving anything; then reserves a run through the same check as `autopilot start` -- taking over the latest stopped or interrupted run of the same root and mode, then refusing a new run from a `DONE` / `CLOSED` ticket, then refusing an overlap (the 409 codes above) -- and opens the orchestrator's terminal. If the terminal does not open, the reservation is undone (a taken-over run returns to its previous state) and the answer is `500`. On success: `{"run_id","mode","root","state","created","resumed"}`, plus `untrusted_folder` when Claude Code has not trusted the project's local path (it never changes whether the run starts). Launches and launch failures are logged (`event=autopilot_launched` / `autopilot_launch_failed`).
- `GET /api/autopilot/runs?project_id=<id>`: a JSON array of the project's active runs and its five most recent other runs, newest first -- other members' runs on a shared database included. Each has the fields of `autopilot status` plus:
  - `started_by`: `{"name","name_is_fallback"}`, who started the run; left out for a run file from an earlier version. The machine ID is never sent.
  - `mine`: whether the run is this machine's (and so can be resumed here). With a data source that does not share runs, every run is `mine`.
  - `members`: every ticket an active run owns -- the root and, for a tree run, all of its descendants as the database has them now, including those not reached yet. This is the set the duplicate-start check uses, and the Web UI disables the "Autopilot" button on those tickets. `[]` for a run that is not active.
  - `pending`: the members the run may still launch as `work`, in processing order -- leaving out `DONE` / `CLOSED` tickets and tickets beyond the limits, under a ticket in progress elsewhere, or under a failed ticket. The Web UI's "Waiting" badge. `[]` for a run that is not active.
- `GET /api/projects/{id}/autopilot-settings` and `PUT /api/projects/{id}/autopilot-settings`: see [Settings](#settings). `GET` answers in the shape `autopilot settings` prints.

## Cautions and limitations

- **Trust the project's folder before the first run.** In a folder Claude Code does not trust yet, the first session the autopilot opens in a new terminal stops at the workspace trust prompt and the run does not go on by itself. Open the folder in Claude Code once and accept the prompt; the ticket worktrees under it are not asked again, but a repository cloned under a trusted folder that is not itself a repository is. The autopilot tells you (`untrusted_folder`) when it can tell that the folder is not trusted, but only on a best-effort basis and never stopping the start. See [Starting a run](#starting-a-run), which also says when there is no notice and what to do when a session is already waiting there.
- **Shared backends run other people's tickets with your permissions.** With MySQL, Jira or another HTTP data source, `autopilot-tree` processes every unfinished descendant in the database -- including child tickets other people created, even while the run is going -- on your machine, with your child sessions' permission mode, and with approval gates decided automatically. Use tree mode on a shared backend only when you trust whoever can create tickets under the root, and do not combine it with `permissionMode: bypassPermissions`.
- **Do not start from a ticket someone is working on elsewhere.** On a shared database, a start that overlaps another member's active autopilot run is refused (see [Runs shared between members](#runs-shared-between-members)), but work done by hand -- `process-ticket` in someone's session -- is not detected. Descendants that are `IN PROGRESS` elsewhere are skipped, but the root is not, since you named it explicitly: starting from a ticket that is being worked on on another machine by hand works on it a second time.
- **Git branches are not shared.** Another member's finished part of a tree reaches your run only through the shared default branch; see [Branches](#branches).
- **Keep the orchestrator's machine awake on a shared database.** A run whose heartbeat stops for 10 minutes (a sleeping laptop, a suspended session) no longer blocks other members, so one of them may start the same tree. When your machine wakes up, your run stops itself (`overtaken`) before launching anything more, but a child session it had already launched keeps working alongside the other member's run until it reports. Prevent sleep during a run, or, after waking up, check the runs list and close that session's terminal if the other run has taken the ticket over.
- **Check the permission mode before `pull_request` or `merge`.** Pushing and opening or merging a pull request run `git push` and `gh` in the child session. If its permission mode refuses them (the default `auto` may), the session reports `failed` with `permission_denied` (or stops at the last stage that worked). Make sure your permission settings allow those commands for the child sessions before choosing these values.
- **Close leftover terminals before resuming**, and do not move the tree's branches by hand while a run is going (see above).
- **Untracked files and the dirty check**: `PARENT_WORKTREE_DIRTY` looks only at uncommitted changes to tracked files; untracked files in the parent's worktree are ignored unless the fast-forward would overwrite them, in which case git fails.
- **`.claude/worktrees`**: in a repository that does not ignore `.claude/worktrees/`, the ticket worktrees show up as untracked files in the main working tree. Add it to `.gitignore` if that bothers you.
- **Many terminals**: a 20-ticket tree opens about 20 child terminals, which stay open until you close them. In Terminal.app they are tabs of the orchestrator's window (when the permissions allow it); elsewhere, a `terminalCommand` that opens tmux windows (or tabs) keeps them manageable.
- **Terminal.app takes the focus** each time a child session opens as a tab, and needs the Accessibility and Automation permissions to do so; without them, or when a tab cannot be opened, sessions open in new windows. **While the screen is locked**, sessions always open in new windows: macOS lets no app come to the front then, so no tab is tried. See [Terminal.app: child sessions as tabs](#terminalapp-child-sessions-as-tabs).
- **Wrong-but-busy sessions**: a legitimate step that shows no activity at all for longer than `stallTimeoutMinutes` (a very long test run with no file changes, say) is failed as unresponsive; raise the setting (up to 24 hours) for such projects. Running the same command again retries the ticket once.
- **Automatic decisions can be wrong.** Review the "Automatic decisions" of important tickets. At a review iteration limit, the autopilot grants at most one extra round per loop target before reporting the ticket blocked.
- **The "Waiting" badge can briefly miss tickets** that a run will relaunch after a retry (children skipped as `parent_failed` whose parent is being retried). Processing is not affected.
